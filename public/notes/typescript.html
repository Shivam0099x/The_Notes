01

Why TypeScript

what it is · what it adds · what it does not do

TypeScript is JavaScript with a static type system on top. You write typed code, the compiler checks it at build time, then it erases the types and emits plain JavaScript. The browser never sees a type.

The one sentence

TypeScript catches type errors before your code runs. It adds no runtime cost, has no runtime features of its own, and does not change how your program behaves — it only prevents you from writing programs that would have broken later.

What TypeScript fixes

Problem in plain JSWhat TS does
user.name.toUpperCase() when name is nullErrors at compile time: "Object is possibly null."
Passing a string where a number was expectedArgument type mismatch, caught while writing
Typo in a property name: user.adress"Property does not exist."
Forgot to handle a switch case on a union of possible valuesExhaustiveness check fails the build
Refactoring a function signature, then a dozen callers silently breakAll callers become errors at once — the compiler finds them

What TypeScript is not

  • Not a runtime checker. If data comes from fetch(), TypeScript trusts your declared type. Runtime validation is your job (or Zod's).
  • Not a separate language. Every valid JS file is valid TS. The only additions are types (erased) and a few TS-only features (enums, decorators, parameter properties, namespace).
  • Not a guarantee of correctness. It catches type errors, not logic errors. A function typed (a: number) => number can still be a wrong formula.
Quick check · 01
What ships to the browser after TypeScript compiles?
Browsers don't understand types. TypeScript erases them — the output is ordinary JS with no type information.
02

Type basics

primitives · any vs unknown · arrays · tuples · enums · inference

The primitive types

primitives.ts
let name: string     = 'Aarav';
let age:  number     = 22;
let ok:   boolean    = true;
let big:  bigint     = 123n;
let sym:  symbol     = Symbol('id');

// null and undefined — under strictNullChecks, they're their own types
let nothing: null      = null;
let missing: undefined = undefined;

any vs unknown

Both mean "this could be anything". The difference is what you're allowed to do with the value:

anyunknown
Allowed to call methods, access properties?Yes — no checksNo — must narrow first
Safe when data comes from fetch / user input?No — you're disabling the type checkerYes — forces you to validate
Typical useMigrating old JS files (a temporary escape hatch)Anything genuinely unknown: JSON.parse, catch, third-party data
⚠️
Prefer unknown over any. any turns off the type checker for that value everywhere it flows. unknown requires you to narrow it, which is exactly what you want from data you didn't create.

Arrays and tuples

arrays-and-tuples.ts
let nums:  number[]              = [1, 2, 3];
let names: Array<string>        = ['Aarav', 'Priya'];

// Tuple — fixed length, fixed types, per position
let point: [number, number] = [10, 20];

// Optional and rest elements in a tuple
let entry: [string, number?, ...boolean[]];

Enums — TS-only, careful

Enums do generate runtime code (unlike most TS). They're useful for named constants, but many teams prefer unions of string literals:

enums.ts
enum Status { Active, Inactive, Banned }   // numbers 0,1,2 by default

enum Role { Admin = 'ADMIN', User = 'USER' }

// Preferred: string literal union — no runtime, easier to serialise
type Status2 = 'active' | 'inactive' | 'banned';

Inference — when you don't need to write the type

inference.ts
let a = 'hello';        // inferred: string
let b = 42;             // inferred: number
const c = 'hi';         // inferred: 'hi'  (literal, because const)
let d = [1, 2, 3];       // inferred: number[]
let e = null;           // inferred: any (until strictNullChecks + assign)
💡
Let inference work. Add annotations on function parameters, return values of exported functions, and boundaries (module APIs, external data). Inside a function body, let the compiler infer — you get the same safety with less noise.
Quick check · 02
What is the inferred type of const x = 'hello'?
const values get a literal type because they can never change. A let x = 'hello' widens to string because it could later be reassigned to any string.
03

Unions, intersections & narrowing

typeof · instanceof · in · discriminated unions · exhaustiveness

A union A | B means "one of these". An intersection A & B means "all of these at once". Narrowing is how TypeScript follows your if checks and updates the type inside each branch.

The basic narrowing operators

CheckNarrows to
typeof x === 'string'string
x instanceof DateDate
'name' in objobj has a name property
x === 'error'literal 'error'
Array.isArray(x)any[] (or specific T[])
if (x)removes null, undefined, '', 0, false
narrowing.ts
function format(value: string | number | Date) {
  if (typeof value === 'string') {
    return value.toUpperCase();     // value: string
  }
  if (typeof value === 'number') {
    return value.toFixed(2);     // value: number
  }
  return value.toISOString();        // value: Date (only one left)
}

Discriminated unions — the killer pattern

Give each member a shared literal property (the "discriminant") and TypeScript can narrow the whole shape from one check. This is how you model state, API results, and actions cleanly.

discriminated.ts
type Result<T> =
  | { status: 'loading' }
  | { status: 'success'; data: T }
  | { status: 'error';   message: string };

function render(r: Result<User>) {
  switch (r.status) {
    case 'loading': return '…';
    case 'success': return r.data.name;    // r.data exists only here
    case 'error':   return r.message;      // r.message exists only here
  }
}

Exhaustiveness checks — the compiler catches missing cases

exhaustive.ts
function assertNever(x: never): never {
  throw new Error(`Unhandled case: ${x}`);
}

function handle(r: Result<User>) {
  switch (r.status) {
    case 'loading': break;
    case 'success': break;
    case 'error':   break;
    default: assertNever(r);   // fails to compile if a new case is added
  }
}
Why this matters

Adding a new member to a union (say, a 'cancelled' status) should make the compiler flag every switch that forgets it. assertNever is how you get that guarantee.

Quick check · 03
What is the pattern where a shared property like status: 'success' | 'error' lets TypeScript narrow a union, called?
A "discriminant" is the shared literal field. Checking its value narrows the whole union to one member.

Functions in TypeScript

parameters · optional · default · rest · return · overloads

functions.ts
// Basic — parameter and return types
function add(a: number, b: number): number {
  return a + b;
}

// Optional (?), default (=), rest (...)
function greet(name: string, title?: string): string {
  return `Hi ${title ?? ''} ${name}`.trim();
}

function sum(...nums: number[]): number {
  return nums.reduce((s, n) => s + n, 0);
}

// Arrow functions
const double = (n: number): number => n * 2;

// Function type — used as a variable's type
type Mapper<T, U> = (x: T) => U;
const toString: Mapper<number, string> = (n) => n.toString();

Function overloads

When the return type depends on the argument shape, use overloads. Multiple signatures, one implementation:

overloads.ts
function parse(input: string): number;
function parse(input: number): string;
function parse(input: string | number): string | number {
  if (typeof input === 'string') return Number(input);
  return String(input);
}

const a = parse('42');     // number
const b = parse(42);       // string
Quick check · 04
Why would you use function overloads instead of a union return type string | number?
Overloads give callers a precise type per input. A union return makes the caller narrow every time. Overloads have no runtime cost — they're erased like any other type.
05

Objects, type aliases & interfaces

shapes · optional · readonly · index signatures · type vs interface

shapes.ts
// Type alias for an object shape
type User = {
  id: number;
  name: string;
  email?: string;              // optional
  readonly createdAt: Date;    // cannot be reassigned after construction
};

// Index signature — an object with arbitrary string keys
type ScoreBoard = {
  [player: string]: number;
};

// Same shape as an interface
interface User2 {
  id: number;
  name: string;
}

type vs interface — when to use which

typeinterface
Object shapeYesYes
Union / intersectionYes — type X = A | BNo
Tuples, primitives, mapped typesYesNo
Declaration merging (same name, multiple declarations)NoYes
Implements by a classYesYes
Good defaultUnions, computed typesPublic API shapes, extendable contracts
Rule of thumb

Use interface for object-shaped contracts you might extend or augment (libraries, public APIs, service shapes). Use type for everything else — unions, intersections, mapped types, function types, tuples. Both work fine day to day.

Extending

extend.ts
interface Admin extends User2 {
  permissions: string[];
}

// Type aliases use intersection
type Admin2 = User & { permissions: string[] };
Quick check · 05
Which of these can only be done with a type, not an interface?
Interfaces describe object shapes only. Unions, tuples, primitives, and mapped types are type-only. Interfaces do have one thing types don't: declaration merging.
06

Generics

type parameters · constraints · defaults · inference

Generics are how you write code that works for any type while still keeping the type relationship between input and output. Without them, "a function that returns the first element" would have to return any — losing all safety.

generics.ts
// Generic function
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}

const n = first([1, 2, 3]);       // number | undefined
const s = first(['a', 'b']);       // string | undefined

// Constraint — T must have a .length property
function lengthOf<T extends { length: number }>(x: T): number {
  return x.length;
}

// Default type parameter
type ApiResponse<T = unknown> = { data: T; ok: boolean };

// Multiple type parameters
function pair<A, B>(a: A, b: B): [A, B] {
  return [a, b];
}

Keyof and indexed access

keyof.ts
interface User { id: number; name: string; email: string }

type Keys       = keyof User;                 // 'id' | 'name' | 'email'
type IdType    = User['id'];                // number

// The classic safe accessor
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const u = { id: 1, name: 'Aarav' };
const name = get(u, 'name');               // inferred: string

Conditional types — a taste of the advanced side

conditional.ts
type IsString<T> = T extends string ? true : false;

type A = IsString<'hello'>;       // true
type B = IsString<42>;            // false

// Distributive conditional — applied over a union
type ToArray<T> = T extends unknown ? T[] : never;
type Arr = ToArray<string | number>;   // string[] | number[]
Quick check · 06
What does <T extends { length: number }> mean on a generic function?
extends on a type parameter is a constraint: T can be any type, as long as it's compatible with the right-hand shape. The caller still gets their specific T back.

Utility types — the ones you'll actually use

Partial · Required · Pick · Omit · Record · Readonly · ReturnType

utility.ts
interface User {
  id: number;
  name: string;
  email: string;
  password: string;
}

type UpdatePayload    = Partial<User>;                 // every field optional
type PublicUser       = Omit<User, 'password'>;        // safe to send to client
type UserPreview      = Pick<User, 'id' | 'name'>;      // card view
type UsersById        = Record<number, User>;

function fetchUser(id: number): PublicUser { /* ... */ return {} as any; }
type UserResult = ReturnType<typeof fetchUser>;       // PublicUser
💡
Never redeclare what a utility can derive. If PublicUser is just User without password, say so. If User gains a field, PublicUser automatically gains it — no drift.
Quick check · 07
You have User with a password field. What is the safest way to define the type returned by your API, which excludes password?
Omit keeps the two types in sync. A hand-written copy will drift the moment someone adds a field to User, and password could sneak back in.

Modules & tsconfig

ESM vs CommonJS · strict mode · the tsconfig you want

ES modules

modules.ts
// Named exports — the default in modern code
export function add(a: number, b: number): number { return a + b; }
export const PI = 3.14159;

// Default export — use sparingly; named is easier to search
export default class Calculator { /* ... */ }

// Importing
import { add, PI } from './math';
import Calculator from './calculator';
import type { User } from './types';   // TS 4.5+, erased at compile

The tsconfig that respects you

tsconfig.json
{
  "compilerOptions": {
    "target": "ES2022",
    "module": "ESNext",
    "moduleResolution": "bundler",
    "strict": true,                  // enables all strict checks
    "noUncheckedIndexedAccess": true,  // arr[i] is T | undefined
    "exactOptionalPropertyTypes": true, // ?: means "absent", not "undefined"
    "noImplicitOverride": true,        // must write `override` when overriding
    "esModuleInterop": true,
    "skipLibCheck": true,
    "outDir": "./dist"
  },
  "include": ["src"]
}
⚠️
Turn on strict from day one. Enabling it later on an existing codebase is painful — hundreds of possibly null errors at once. strict enables strictNullChecks, noImplicitAny, and a few more. Without it, TypeScript behaves like a slightly type-aware JavaScript, which defeats most of the point.
Quick check · 08
What does strictNullChecks change?
It's a type-level rule. Without it, null was a member of every type — the source of countless runtime crashes. With it, string | null is a different type from string, and the compiler forces you to narrow.

OOP fundamentals

the four pillars · how TypeScript supports each

Object-oriented programming is about bundling state (data) and behaviour (methods) into units called objects, and letting those objects interact through well-defined interfaces. TypeScript is a class-based language — unlike JavaScript, it has real access modifiers, interfaces, abstract classes, and generic classes.

PillarMeaningIn TypeScript
EncapsulationHide internal state; expose a controlled surfaceprivate, protected, readonly, getters/setters
AbstractionModel only what matters; hide the restabstract class, interface
InheritanceReuse state and behaviour from a base typeclass A extends B, super(), override
PolymorphismSame call, different behaviour per typeMethod overriding, interface-based dispatch
The trap

OOP is a tool, not a religion. The strongest TS codebases use classes only where identity and behaviour actually belong together — services, models, SDK clients, state machines. A pure function that takes input and returns output does not need to live inside a class.

Classes in depth

fields · constructor · parameter properties · static · getters & setters

A complete class

class.ts
class User {
  static count = 0;                    // shared across all instances

  readonly id: number;                  // cannot change after construction
  name: string;
  private password: string;            // only this class can read it

  constructor(id: number, name: string, password: string) {
    this.id = id;
    this.name = name;
    this.password = password;
    User.count++;
  }

  greet(): string {
    return `Hi, ${this.name}`;
  }

  checkPassword(attempt: string): boolean {
    return attempt === this.password;
  }

  static createGuest(): User {           // factory method
    return new User(0, 'Guest', '');
  }
}

Parameter properties — TS-only shorthand

If a constructor only assigns parameters to fields with the same name, use a parameter property. It's one of TypeScript's most-loved features:

parameter-props.ts
// Before — verbose
class Point1 {
  x: number;
  y: number;
  constructor(x: number, y: number) {
    this.x = x;
    this.y = y;
  }
}

// After — same thing, one line
class Point2 {
  constructor(
    public x: number,
    public y: number,
    private meta: string = '',
  ) {}
}

Getters and setters

accessors.ts
class Temperature {
  private _celsius = 0;

  get celsius(): number {
    return this._celsius;
  }
  set celsius(v: number) {
    if (v < -273.15) throw new Error('Below absolute zero');
    this._celsius = v;
  }

  get fahrenheit(): number {
    return this._celsius * 9 / 5 + 32;
  }
}

const t = new Temperature();
t.celsius = 25;                  // runs the setter
console.log(t.fahrenheit);        // 77
💡
Getters and setters are properties at the call site. Consumers don't call t.getCelsius() — they write t.celsius. Behind it, your method runs. This is how you add validation to a property without breaking the API.
Quick check · 09
In class User { constructor(public name: string) {} }, what does public on the parameter do?
That's a parameter property: TS automatically creates the field with the modifier's visibility and assigns the argument to it. It's a TS-only feature and a huge boilerplate saver.

Inheritance

extends · super · override · composition vs inheritance

extends.ts
class Animal {
  constructor(public name: string) {}

  speak(): string {
    return '…';
  }
}

class Dog extends Animal {
  constructor(name: string, public breed: string) {
    super(name);                        // must run before using `this`
  }

  override speak(): string {
    return 'Woof';                    // replaces Animal.speak for Dog instances
  }

  parentSpeak(): string {
    return super.speak();              // can still call the parent version
  }
}
Why override

With noImplicitOverride, TypeScript requires the override keyword whenever a subclass member shadows a base-class member. This prevents accidental overrides when a base class later adds a method with the same name. Turn it on.

Composition vs inheritance

Inheritance (extends)Composition (has-a)
Relationshipis-a: Dog is an Animalhas-a: Car has an Engine
CouplingTight — changing the parent affects every childLoose — swap the part without touching the whole
Fragile whenDeep hierarchies (Animal → Mammal → Pet → Dog → ...)Rarely; you can always replace a composed part
Use whenThere is a real, stable is-a relationshipAnything else
⚠️
Prefer composition. "Favour composition over inheritance" is a rule because inheritance creates the tightest coupling in OOP: a base-class change ripples through every subclass silently. Inherit only for real is-a hierarchies, and keep those shallow.
Quick check · 10
In a subclass constructor, what must you do before touching this?
Until super() runs, the instance isn't fully constructed — this isn't valid yet. TypeScript enforces this at compile time; JavaScript throws at runtime if you skip it.

Encapsulation

public · private · protected · readonly · #fields · closures

Access modifiers

ModifierAccessible fromUse for
public (default)AnywhereThe class's contract
protectedThis class and subclassesState meant to be inherited, not exposed externally
privateThis class onlyInternal implementation detail
readonlyCan be set at declaration or in constructorImmutable after construction — combine with any of the above
encapsulation.ts
class BankAccount {
  private balance = 0;
  protected ownerId: string;
  readonly accountNumber: string;

  constructor(ownerId: string, accountNumber: string) {
    this.ownerId = ownerId;
    this.accountNumber = accountNumber;
  }

  deposit(amount: number) {
    if (amount <= 0) throw new Error('Must be positive');
    this.balance += amount;
  }

  getBalance(): number {
    return this.balance;
  }
}

const acc = new BankAccount('u1', '123');
acc.deposit(100);
// acc.balance = 1_000_000;   ❌ compile error — private
⚠️
private is a TypeScript-only guarantee. It's enforced by the compiler, not the runtime. At runtime the field still exists on the object and can be accessed via (obj as any).balance. If you need genuine runtime privacy, use JavaScript private fields with # — TS supports them natively.

True privacy with #fields

hash-private.ts
class Counter {
  #count = 0;                 // JS private field — truly inaccessible

  increment() { this.#count++; }
  get value() { return this.#count; }
}

const c = new Counter();
c.increment();
// c.#count         ❌ SyntaxError
// (c as any).#count ❌ still fails — # is runtime-enforced

The closure pattern — TS's older form of encapsulation

Before classes were nice in JS, encapsulation was achieved with closures. You still see this in factory functions and modern "class-free" code:

closure.ts
function createCounter() {
  let count = 0;                 // only visible inside this function
  return {
    increment: () => ++count,
    value: () => count,
  };
}
Quick check · 11
You need a field that subclasses can access but callers outside the class hierarchy cannot. Which modifier?
private is class-only — subclasses can't see it. protected extends visibility to the entire hierarchy.

Abstract classes & interfaces

abstraction in practice · when to use which

Both abstract class and interface describe a contract that a concrete class must fulfil. But they differ in what they can contain and how they're used.

Abstract classes — the "half-built base"

abstract.ts
abstract class Shape {
  constructor(public name: string) {}

  // must be implemented by every subclass
  abstract area(): number;

  // shared concrete behaviour
  describe(): string {
    return `${this.name} with area ${this.area().toFixed(2)}`;
  }
}

class Circle extends Shape {
  constructor(private r: number) { super('circle'); }
  area(): number { return Math.PI * this.r ** 2; }
}

class Square extends Shape {
  constructor(private s: number) { super('square'); }
  area(): number { return this.s ** 2; }
}

// const s = new Shape('x');   ❌ can't instantiate an abstract class
const shapes: Shape[] = [new Circle(2), new Square(3)];
shapes.forEach(s => console.log(s.describe()));

Abstract class vs interface

Abstract classInterface
Can have concrete methods & fields?YesNo (only signatures)
Can have a constructor?YesNo
Multiple inheritance?No — one abstract parentYes — implements A, B, C
Emits runtime code?Yes (it's a class)No — erased
Use whenYou want to share implementation and enforce a contractYou want pure contract, especially across unrelated types
Rule of thumb

If subclasses should inherit shared code, use an abstract class. If you only need a shape (e.g. Serializable, Comparable), use an interface. You can also do both: interface for the contract, abstract class for a reusable implementation.

Quick check · 12
Why can't you write new Shape() when Shape is abstract?
An abstract class may have abstract methods with no body. Instantiating it would leave those methods unimplemented. Subclasses must fill them in, and only then can you instantiate.

Polymorphism

subtype · interface-based · parametric · overloading

Polymorphism means "many shapes" — one interface, many implementations, chosen by the actual type of the value. TypeScript gives you all four common kinds.

1. Subtype polymorphism (classic OOP)

A variable typed as the base class can hold any subclass instance. Calling a method on it dispatches to the subclass's implementation:

subtype.ts
class Notification { send(msg: string) { console.log('base'); } }
class Email extends Notification { override send(msg: string) { console.log('email:', msg); } }
class SMS   extends Notification { override send(msg: string) { console.log('sms:', msg); } }

const channels: Notification[] = [new Email(), new SMS()];
channels.forEach(c => c.send('hi'));   // each does its own thing

2. Interface-based polymorphism (structural)

No shared base class required — any object that has the right shape qualifies. This is TypeScript's superpower:

interface-poly.ts
interface Shape {
  area(): number;
}

class Circle { area() { return Math.PI * 4; } }
class Rect   { area() { return 12; } }
const plain = { area: () => 42 };      // an ordinary object qualifies too

function totalArea(shapes: Shape[]): number {
  return shapes.reduce((sum, s) => sum + s.area(), 0);
}

totalArea([new Circle(), new Rect(), plain]);   // all fine — no inheritance needed

3. Parametric polymorphism (generics)

A function or class that works for any type, without losing type information. Already covered in section 06:

parametric.ts
function identity<T>(x: T): T { return x; }

const n = identity(42);        // number
const s = identity('hi');      // string

4. Overloading (ad-hoc polymorphism)

Same name, different signatures — covered in section 04. TypeScript uses it heavily in the standard library, e.g. Array.prototype.concat.

Quick check · 13
A function accepts Shape[] where Shape is an interface with area(). Which argument will TypeScript reject?
TypeScript is structural: anything with the right shape qualifies. A plain object with area() is fine; a class instance without it is not, no matter its name.

OOP + generics

generic classes · generic constraints · typed repositories

Generic classes combine the two biggest TS features: reusable structures that keep their type precision. The classic use is a repository or service layer that works for any entity.

repository.ts
interface Entity {
  id: string;
}

class Repository<T extends Entity> {
  private items: Map<string, T> = new Map();

  save(item: T): T {
    this.items.set(item.id, item);
    return item;
  }

  findById(id: string): T | undefined {
    return this.items.get(id);
  }

  findAll(): T[] {
    return [...this.items.values()];
  }
}

interface User extends Entity { name: string }

const users = new Repository<User>();
users.save({ id: '1', name: 'Aarav' });
const found = users.findById('1');   // User | undefined
What just happened

One class. Works for User, Post, Order, or anything else with an id. Because of the constraint T extends Entity, the class can safely use item.id. Because of the generic, the caller gets their specific T back — not Entity, not unknown.

Quick check · 14
In class Repository<T extends Entity>, why is the extends Entity constraint necessary?
Without the constraint, T could be anything — including number — and item.id would be an error. The constraint gives the class body a minimum shape it can rely on, while the caller keeps their specific T.

Interview questions

what you'll actually be asked

Q1What is TypeScript, and what is the benefit over JavaScript?

TypeScript is JavaScript with a static type system layered on top. It catches type errors at compile time, gives better editor autocompletion and refactoring, and produces self-documenting code. The types are erased during compilation — the runtime output is plain JavaScript.

Q2What's the difference between any and unknown?

Both represent "any value". any disables type checking on the value everywhere it flows — you can call methods and access properties without checks. unknown is the safe version: you can assign anything to it, but you must narrow it before use. Use unknown for external data; reserve any as an escape hatch.

Q3What's the difference between type and interface?

Both describe shapes. type can also express unions, intersections, tuples, and mapped types. interface supports declaration merging (multiple declarations with the same name combine) and is the conventional choice for public, extendable object shapes. Use interface for object contracts you might augment; type for unions, computed types, and everything else.

Q4What are generics, and why do they matter?

Generics are type parameters — placeholders that are filled in by the caller. They let you write one function or class that works for any type while preserving the precise type relationship between input and output. Without them, reusable code returns any and loses all safety. With them, first([1, 2, 3]) returns number while first(['a']) returns string — same code, precise types.

Q5Explain keyof and T[K] (indexed access).

keyof T is a union of all keys of T. T[K] is the type of the property at key K. Together they let you write type-safe accessors: function get<T, K extends keyof T>(obj: T, key: K): T[K] — the return type is exactly the type of the property at the given key, whatever it is.

Q6What is a discriminated union, and why is it useful?

A union where every member has a shared literal field (the discriminant) — like status: 'loading' | 'success' | 'error'. Checking that field narrows the union to one member, so you get the exact fields of that member in each branch. It's the cleanest way to model state, API results, and reducers in TypeScript.

Q7What are the four pillars of OOP, and how does TypeScript implement each?

Encapsulation — private, protected, #fields. Abstraction — abstract class and interface. Inheritance — extends, super, override. Polymorphism — method overriding for subtype polymorphism, interfaces for structural polymorphism, generics for parametric polymorphism.

Q8What's the difference between an abstract class and an interface?

An abstract class can have concrete fields, methods, and a constructor — it's a partial implementation. An interface only declares signatures, produces no runtime code, and can be implemented in multiples. Use an abstract class when you want to share implementation while enforcing a contract; use an interface when you only need the shape, especially across unrelated types.

Q9Does private prevent access at runtime?

No. private is a compile-time rule — TypeScript prevents you from writing obj.privateField, but at runtime the field still exists and can be reached via (obj as any) or reflection. For genuine runtime privacy, use JavaScript private fields with the # prefix, which are enforced by the engine itself.

Q10When would you prefer composition over inheritance?

Almost always. Inheritance is appropriate only for stable is-a hierarchies where the subclass genuinely is a more specific version of the base and will never need to break that. Composition ("has-a") is looser — you can swap parts, test them independently, and change one without touching the whole. "Favour composition over inheritance" exists because inheritance creates the tightest coupling in OOP.

Q11What are utility types? Name three you use regularly.

Built-in type transformations. Partial<T> makes all fields optional (great for update payloads). Omit<T, K> removes fields (great for hiding password before sending to clients). Pick<T, K> keeps only some fields (great for DTOs). Others worth knowing: Record, Readonly, ReturnType, Parameters, Exclude, Extract, NonNullable.

Q12What does strict mode in tsconfig enable, and why turn it on?

It enables a group of stricter checks, including strictNullChecks, noImplicitAny, strictFunctionTypes, and strictPropertyInitialization. Without strictNullChecks in particular, null and undefined are assignable to every type — which is the source of a huge class of runtime crashes. Turn it on at project start; retrofitting it later is painful.

Q13How does TypeScript's type system differ from Java's or C#'s?

TypeScript is structural — type compatibility is based on the shape of a value, not its declared name or class. If two unrelated interfaces have the same structure, a value of one is assignable to the other. Java and C# are nominal — you must explicitly implement or extend the right types. TypeScript also has erased types (no runtime presence), which is why it can't do things like instanceof MyInterface.
