01

The four problems these patterns solve

re-render cost · network spam · bundle size · data loading

Every React performance problem you'll ever face falls into one of four buckets. Each of these patterns is the standard answer to one bucket.

BucketSymptomPattern
Re-render cost Typing in one input re-renders the whole tree; a parent update re-renders unrelated children; expensive calculations run every render Memoization — React.memo, useMemo, useCallback
Event spam A search fires an API call per keystroke; scroll handlers run 100× per second; resize handlers thrash the layout Throttle / debounce — collapse many events into one
Bundle size First load is 2 MB of JS; heavy editors or charts delay time-to-interactive Lazy loading — React.lazy + Suspense, route-level splits
Data loading Fetching all rows at once; a huge list locks up the browser; no way to load more as you scroll Pagination / infinite scroll — fetch a page at a time
The structure of this note

Each of the four patterns gets its own section. Inside, you'll find: what it is, the raw React implementation (with code you can copy), the same feature rebuilt with TanStack Query, and a head-to-head of what the library saves you. The last section is interview Q&A.

02

Memoization

React.memo · useMemo · useCallback · what each one actually caches

Memoization means remembering a previous result so you don't recompute it. In React there are three separate memos, each caching a different thing. Mixing them up is the number-one source of useless optimizations.

ToolCachesTriggers re-render?Use for
React.memoThe rendered output of a componentSkips render if props shallow-equalExpensive child that re-renders from parent updates
useMemoA computed valueN/A — it's not a componentExpensive derived data in render
useCallbackA function referenceN/A — it's not a componentStable handler for a memoized child or a deps array

The problem, before memo

before.jsx
function Parent() {
  const [count, setCount] = useState(0);
  const [query, setQuery] = useState('');

  // 💥 New array, new function every render — even when query didn't change
  const items = [1, 2, 3].map(n => n * count);
  const handleSearch = q => setQuery(q);

  return (
    <>
      <button onClick={() => setCount(c => c + 1)}>{count}</button>
      <ExpensiveList items={items} onSearch={handleSearch} />
    </>
  );
}

Every click of the button re-renders Parent, which recreates items and handleSearch. That means ExpensiveList receives brand-new props and re-renders — even though its actual data didn't change.

Fix 1 — React.memo on the child

child.jsx
const ExpensiveList = React.memo(function({ items, onSearch }) {
  // runs only when `items` or `onSearch` changes by Object.is comparison
  return <ul>{items.map(i => <li key={i}>{i}</li>)}</ul>;
});

React.memo wraps a component so React skips rendering it if its props are shallow-equal to the previous render. The problem: items is a new array and onSearch is a new function every render — so memo alone doesn't help. You need the other two.

Fix 2 — useMemo on the array

usememo.jsx
const items = useMemo(
  () => [1, 2, 3].map(n => n * count),
  [count]   // only recompute when count changes
);

Now items keeps the same reference across renders — unless count changes. React.memo's Object.is comparison on items now succeeds, and the child is skipped when only query changed.

Fix 3 — useCallback on the handler

usecallback.jsx
const handleSearch = useCallback((q) => {
  setQuery(q);
}, []);   // stable — same reference forever (setQuery is stable)

Without this, onSearch is a new function every render, and React.memo on the child fails its comparison even when nothing the child cares about changed.

  1. Click the +1 button. count changes → useMemo's deps change → items gets a new reference → React.memo's Object.is(items) fails → the child renders. Correct and expected.
  2. Type into the search box. query changes, count doesn't. items keeps the same reference (thanks to useMemo). handleSearch also keeps its reference (thanks to useCallback with []). Both props pass Object.is → React.memo skips the child.
  3. Some unrelated state changes higher up the tree (say, theme). Parent re-renders, but items and handleSearch are still the same references → child skipped again. In a real app, this is what keeps unrelated parts of the tree quiet.
  4. Without useMemo, every parent render creates a new items array → child renders every time. Without useCallback, every parent render creates a new handleSearch → child renders every time.
  5. All three are needed together. That's why "just add memo" almost never helps on its own. If you're going to memoize the child, memoize the props it receives too — or skip memoization entirely and fix the state shape.
Step 1 / 5
⚠️
Memoization is not free. Every useMemo and useCallback adds a comparison and a cache slot. If the calculation is cheap (a map over 3 items, an arr.filter on 10 elements), memoizing it is slower than recomputing. Profile first. Memoize the genuinely expensive things: large arrays, expensive formatting, heavy derived data, props passed to React.memo children.

The most common memo mistakes

Quick check · 01
A child is wrapped in React.memo but keeps re-rendering on every parent render. What's the most likely cause?
React.memo compares props with Object.is. An inline object {`{ a: 1 }`} or inline arrow onClick={() => ...} creates a fresh reference every render — always "different". Memoize the prop with useMemo/useCallback, or lift the value out of the render.
Quick check · 02
When is useMemo actually worth it?
For cheap computations, the comparison overhead outweighs the savings. Profile, then memoize the hot spots. The stable-reference case is the "passed to React.memo child" scenario — memoizing is required for the child's memo to work.

Throttle & debounce

collapse events · search-as-you-type · scroll & resize handlers

Both reduce the number of times a function runs. They solve the same problem — events fire more often than the work should — with opposite timing.

DebounceThrottle
GuaranteeRuns only after wait ms of silenceRuns at most once every wait ms
If the user keeps typingNever runs until they stopRuns at regular intervals while typing
Great forSearch input, form validation, autosaveScroll handlers, resize handlers, mouse-move, rate-limited API calls
Feels like"Wait until you're done""Update on a schedule"

Raw implementation — debounce

debounce.js
function debounce(fn, wait = 300) {
  let timer;
  return function (...args) {
    clearTimeout(timer);
    timer = setTimeout(() => fn.apply(this, args), wait);
  };
}

Raw implementation — throttle

throttle.js
function throttle(fn, wait = 300) {
  let last = 0;
  return function (...args) {
    const now = Date.now();
    if (now - last >= wait) {
      last = now;
      fn.apply(this, args);
    }
  };
}

Raw debounce as a hook

useDebouncedValue.js
import { useState, useEffect } from 'react';

export function useDebouncedValue(value, wait = 300) {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const t = setTimeout(() => setDebounced(value), wait);
    return () => clearTimeout(t);   // cancel on next change or unmount
  }, [value, wait]);

  return debounced;
}

Raw throttle as a hook

useThrottledValue.js
import { useState, useEffect, useRef } from 'react';

export function useThrottledValue(value, wait = 300) {
  const [throttled, setThrottled] = useState(value);
  const last = useRef(0);

  useEffect(() => {
    const now = Date.now();
    if (now - last.current >= wait) {
      last.current = now;
      setThrottled(value);
    }
  }, [value, wait]);

  return throttled;
}

Using debounce for a search input

SearchBox.jsx (raw)
function SearchBox() {
  const [query, setQuery] = useState('');
  const [results, setResults] = useState([]);
  const [loading, setLoading] = useState(false);
  const debouncedQuery = useDebouncedValue(query, 400);

  useEffect(() => {
    if (!debouncedQuery) { setResults([]); return; }

    const controller = new AbortController();
    setLoading(true);

    fetch(`/api/search?q=${encodeURIComponent(debouncedQuery)}`, {
      signal: controller.signal,
    })
      .then(r => r.json())
      .then(setResults)
      .catch(err => { if (err.name !== 'AbortError') console.error(err); })
      .finally(() => setLoading(false));

    return () => controller.abort();   // cancel on next keystroke or unmount
  }, [debouncedQuery]);

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      {loading && <p>Searching…</p>}
      <ul>{results.map(r => <li key={r.id}>{r.name}</li>)}</ul>
    </>
  );
}
⚠️
Debounce alone is not enough for search. Debounce reduces the number of requests, but does not prevent two requests from being in flight — if the network is slow, an old response can land after a new one and overwrite fresher data with stale. Always pair debounce with AbortController (cancel the previous fetch) or an "ignore flag" pattern. This is a race condition, and it's the most common bug in a search box.

Same search, with TanStack Query

SearchBox.jsx (TQ)
import { useQuery } from '@tanstack/react-query';
import { useState } from 'react';

function SearchBox() {
  const [query, setQuery] = useState('');
  const debounced = useDebouncedValue(query, 400);

  const { data = [], isFetching } = useQuery({
    queryKey: ['search', debounced],
    queryFn: ({ signal }) =>
      fetch(`/api/search?q=${encodeURIComponent(debounced)}`, { signal })
        .then(r => r.json()),
    enabled: debounced.length > 0,
  });

  return (
    <>
      <input value={query} onChange={e => setQuery(e.target.value)} />
      {isFetching && <p>Searching…</p>}
      <ul>{data.map(r => <li key={r.id}>{r.name}</li>)}</ul>
    </>
  );
}

Everything else is handled for you: the signal argument cancels the previous request automatically when the query key changes; the results for each debounced query are cached, so re-searching a value is instant; and switching back to a previous search shows the cached results instantly.

Quick check · 03
You have a scroll handler that updates a "back to top" button's visibility. Debounce or throttle?
Debouncing the scroll handler means the button only appears after the user stops scrolling — for a UI affordance like "back to top", that's a worse experience. Throttle gives you one update per ~100ms while scrolling, which is smooth and cheap.
Quick check · 04
Debounce is applied to a search box. What additional problem still exists?
Debounce reduces frequency but doesn't order responses. Fix: AbortController (cancel the previous request), an ignore flag (check ignore before setting state), or a request id — TanStack Query's signal handles it for you.

Lazy loading

React.lazy · Suspense · route-level splits · component-level splits

Lazy loading means delaying loading a piece of code until it's actually needed. On a big app, the initial bundle is the biggest bottleneck to time-to-interactive. Lazy loading splits the bundle so the first screen only downloads what it needs.

Component-level lazy loading

Modal.jsx
import { lazy, Suspense, useState } from 'react';

const HeavyEditor = lazy(() => import('./HeavyEditor'));

export default function Page() {
  const [show, setShow] = useState(false);

  return (
    <>
      <button onClick={() => setShow(true)}>Edit</button>
      {show && (
        <Suspense fallback={<p>Loading editor…</p>}>
          <HeavyEditor />
        </Suspense>
      )}
    </>
  );
}

The import of HeavyEditor doesn't happen until the component first renders. Before then, its JS is a separate chunk, unloaded. The user pays for it only when they click "Edit".

Route-level split — the highest-impact version

routes.jsx
import { lazy, Suspense } from 'react';
import { BrowserRouter, Routes, Route } from 'react-router-dom';

const Home     = lazy(() => import('./pages/Home'));
const Products = lazy(() => import('./pages/Products'));
const Checkout = lazy(() => import('./pages/Checkout'));

export default function App() {
  return (
    <BrowserRouter>
      <Suspense fallback={<p>Loading…</p>}>
        <Routes>
          <Route path="/"         element={<Home />} />
          <Route path="/products" element={<Products />} />
          <Route path="/checkout" element={<Checkout />} />
        </Routes>
      </Suspense>
    </BrowserRouter>
  );
}
What lazy loading actually does

React.lazy(fn) tells React "when this component first needs to render, call fn() which returns a promise resolving to the module". React suspends rendering until the promise resolves, showing the nearest <Suspense> fallback. Bundlers (Vite, webpack) notice the dynamic import() and split the module into a separate chunk, loaded on demand.

The rules

  • Wrap the lazy component in a <Suspense> with a fallback, or React throws. The nearest Suspense above the lazy component is the one that shows the fallback.
  • Split at boundaries users perceive — routes, modals, tabs. Splitting one button's icon is over-engineering.
  • Preload on hover or intent. If you know the user will go to /checkout soon, call import('./pages/Checkout') on hover of the "Checkout" button. The chunk starts downloading early, so React.lazy gets an already-loaded module when the route renders.
  • Don't lazy load the first screen. Every Suspense boundary adds a flash. If a component is visible on initial load, keep it in the main bundle.
preload-on-hover
// Start the download as soon as the user shows intent
const preloadCheckout = () => import('./pages/Checkout');

<Link to="/checkout" onMouseEnter={preloadCheckout} onFocus={preloadCheckout}>
  Checkout
</Link>
⚠️
Don't lazy-load inside a synchronous component tree without Suspense. React throws "A component suspended while responding to synchronous input" if you don't have a Suspense ancestor. Every lazy component needs a boundary somewhere above it. On routes, put one at the router level — one fallback for the whole page is fine.
Quick check · 05
What does React.lazy(() => import('./X')) return?
React.lazy returns a component, not a promise. You render it like any component (<X />) and React handles the loading internally. The argument is a function that returns a promise of a module with a default export.

Pagination

raw hooks · page + total · keep-previous-page UX · then TanStack Query

Pagination fetches one page of data at a time. Two things it needs to be good:

  • Page boundary UI — page numbers, prev/next buttons, disable on ends.
  • Smooth transition — the previous page's data should stay visible while the next one loads, instead of flashing empty.

Raw implementation

usePaginatedUsers.js
import { useState, useEffect } from 'react';

export function usePaginatedUsers(page, limit = 10) {
  const [data, setData]       = useState({ users: [], total: 0 });
  const [loading, setLoading] = useState(true);
  const [error, setError]     = useState(null);

  useEffect(() => {
    const controller = new AbortController();
    setLoading(true);
    setError(null);

    fetch(`/api/users?page=${page}&limit=${limit}`, { signal: controller.signal })
      .then(r => {
        if (!r.ok) throw new Error('Failed');
        return r.json();
      })
      .then(setData)
      .catch(err => { if (err.name !== 'AbortError') setError(err); })
      .finally(() => setLoading(false));

    return () => controller.abort();
  }, [page, limit]);

  return { ...data, loading, error };
}
UsersPage.jsx (raw)
function UsersPage() {
  const [page, setPage] = useState(1);
  const { users, total, loading, error } = usePaginatedUsers(page, 10);

  if (error) return <p>Error: {error.message}</p>;
  if (loading && !users.length) return <p>Loading…</p>;

  const totalPages = Math.ceil(total / 10);

  return (
    <>
      <ul style={{ opacity: loading ? 0.5 : 1 }}>
        {users.map(u => <li key={u.id}>{u.name}</li>)}
      </ul>

      <button disabled={page === 1} onClick={() => setPage(p => p - 1)}>Prev</button>
      <span>Page {page} of {totalPages}</span>
      <button disabled={page >= totalPages} onClick={() => setPage(p => p + 1)}>Next</button>
    </>
  );
}

Notice loading && !users.length — the full spinner only shows on the very first load. On page changes, the previous users stay visible with reduced opacity while the next page loads. Without that, the list flashes empty on every page change, and the user sees a jarring spinner each time.

Same pagination, with TanStack Query

UsersPage.jsx (TQ)
import { useQuery, keepPreviousData } from '@tanstack/react-query';
import { useState } from 'react';

function UsersPage() {
  const [page, setPage] = useState(1);

  const { data, isLoading, isError, isFetching } = useQuery({
    queryKey: ['users', { page }],
    queryFn: ({ signal }) =>
      fetch(`/api/users?page=${page}&limit=10`, { signal })
        .then(r => r.json()),
    placeholderData: keepPreviousData,  // show previous page while next loads
  });

  if (isLoading) return <p>Loading…</p>;
  if (isError) return <p>Something went wrong.</p>;

  const totalPages = Math.ceil(data.total / 10);

  return (
    <>
      <ul style={{ opacity: isFetching ? 0.5 : 1 }}>
        {data.users.map(u => <li key={u.id}>{u.name}</li>)}
      </ul>

      <button disabled={page === 1} onClick={() => setPage(p => p - 1)}>Prev</button>
      <span>Page {page} of {totalPages}</span>
      <button disabled={page >= totalPages} onClick={() => setPage(p => p + 1)}>Next</button>
    </>
  );
}

Same UI. What you don't have to write:

  • useEffect, AbortController, and manual state — TanStack Query handles all three.
  • isLoading / isFetching / isError — free.
  • Cache — going back to page 2 is instant, no request.
  • keepPreviousData — the smooth "no flashing" UX with one option.
  • Automatic cancellation — via the signal argument when the query key changes.
Raw React
  • Manual loading / error / data state
  • Fetch inside useEffect
  • Manual abort on unmount / dep change
  • No cache — same page refetches
  • Flicker unless you add the loading && !data trick
TanStack Query
  • isLoading, isError, data from the hook
  • Just return a fetch — no effect
  • signal handles cancellation
  • Caches every [page] — page-back is free
  • placeholderData: keepPreviousData
Quick check · 06
Why is placeholderData: keepPreviousData important for a paginated table?
Without it, changing page flips the query state to "loading", and your component returns the spinner — wiping the table. With keepPreviousData, data is still the previous page, so the table stays rendered until the new data arrives. Same effect as loading && !data.length in the raw version, but one line.

Infinite scroll

raw implementation with IntersectionObserver · then useInfiniteQuery

Infinite scroll loads the next page automatically when the user scrolls near the bottom. The tricky parts are: (1) knowing when the user is near the bottom, and (2) appending new pages rather than replacing the current list.

Detecting "near the bottom" — IntersectionObserver

A sentinel element at the end of the list. When it enters the viewport, load the next page. This is dramatically cheaper than a scroll listener because it doesn't fire on every pixel.

useInfiniteScroll.js
import { useEffect, useRef } from 'react';

export function useInfiniteScroll(callback, enabled = true) {
  const sentinelRef = useRef(null);

  useEffect(() => {
    if (!enabled || !sentinelRef.current) return;

    const observer = new IntersectionObserver(
      entries => {
        if (entries[0].isIntersecting) callback();
      },
      { rootMargin: '200px' }   // start loading 200px before visible
    );

    observer.observe(sentinelRef.current);
    return () => observer.disconnect();
  }, [enabled, callback]);

  return sentinelRef;
}

The full raw implementation

PostsFeed.jsx (raw)
import { useState, useEffect, useCallback } from 'react';
import { useInfiniteScroll } from './useInfiniteScroll';

function PostsFeed() {
  const [pages, setPages]         = useState([]);   // array of pages
  const [nextPage, setNextPage]   = useState(1);
  const [hasMore, setHasMore]     = useState(true);
  const [loading, setLoading]     = useState(false);
  const [error, setError]         = useState(null);

  const loadMore = useCallback(async () => {
    if (loading || !hasMore) return;   // guard double calls
    setLoading(true);
    try {
      const res = await fetch(`/api/posts?page=${nextPage}&limit=20`);
      if (!res.ok) throw new Error('Failed');
      const data = await res.json();

      setPages(prev => [...prev, data.posts]);   // append the new page
      setNextPage(p => p + 1);
      setHasMore(data.hasMore);
    } catch (err) {
      setError(err);
    } finally {
      setLoading(false);
    }
  }, [loading, hasMore, nextPage]);

  // load first page on mount
  useEffect(() => { loadMore(); }, []);   // eslint-disable-line

  const sentinelRef = useInfiniteScroll(loadMore, hasMore && !loading);

  const allPosts = pages.flat();

  return (
    <div>
      <ul>
        {allPosts.map(p => <li key={p.id}>{p.title}</li>)}
      </ul>

      {/* Sentinel — the observer watches this */}
      <div ref={sentinelRef} />

      {loading && <p>Loading more…</p>}
      {error   && <p>Error: {error.message}</p>}
      {!hasMore && <p>You've reached the end.</p>}
    </div>
  );
}
⚠️
The guard is not optional. Without if (loading || !hasMore) return, the IntersectionObserver can fire multiple times before the first request resolves — the sentinel is still in view, and every observer callback triggers a new fetch. You end up with duplicated pages and duplicate React keys. The guard is what makes infinite scroll reliable.

Same feed, with useInfiniteQuery

PostsFeed.jsx (TQ)
import { useInfiniteQuery } from '@tanstack/react-query';
import { useEffect, useRef } from 'react';

function PostsFeed() {
  const {
    data, fetchNextPage, hasNextPage, isFetchingNextPage, isError,
  } = useInfiniteQuery({
    queryKey: ['posts'],
    queryFn: async ({ pageParam = 1, signal }) => {
      const res = await fetch(`/api/posts?page=${pageParam}&limit=20`, { signal });
      if (!res.ok) throw new Error('Failed');
      return res.json();
    },
    initialPageParam: 1,
    getNextPageParam: (lastPage, allPages) =>
      lastPage.hasMore ? allPages.length + 1 : undefined,
  });

  // IntersectionObserver on a sentinel
  const sentinelRef = useRef(null);
  useEffect(() => {
    const el = sentinelRef.current;
    if (!el || !hasNextPage) return;

    const observer = new IntersectionObserver(
      entries => {
        if (entries[0].isIntersecting && !isFetchingNextPage) {
          fetchNextPage();
        }
      },
      { rootMargin: '200px' }
    );

    observer.observe(el);
    return () => observer.disconnect();
  }, [hasNextPage, isFetchingNextPage, fetchNextPage]);

  if (isError) return <p>Error loading feed</p>;

  const allPosts = data?.pages.flatMap(p => p.posts) ?? [];

  return (
    <div>
      <ul>
        {allPosts.map(p => <li key={p.id}>{p.title}</li>)}
      </ul>
      <div ref={sentinelRef} />
      {isFetchingNextPage && <p>Loading more…</p>}
      {!hasNextPage && <p>You've reached the end.</p>}
    </div>
  );
}

The library handles: the pages array (you don't manage it), the next-page calculation (getNextPageParam), the has-next state (hasNextPage), the loading-next-page state (isFetchingNextPage), and deduplication when fetchNextPage is called twice.

💡
Cursor-based pagination is usually better than page numbers. For feeds where new items are being added constantly, ?page=2 can shift as new items arrive. Cursor pagination — ?after=lastSeenId — guarantees each page picks up exactly where the previous one ended. In useInfiniteQuery that's just getNextPageParam: (last) => last.nextCursor.
Quick check · 07
Why use IntersectionObserver instead of a scroll listener for infinite scroll?
A scroll listener fires on every scroll event — hundreds per second. You'd need to throttle it, and even then you're doing math on every tick. IntersectionObserver asks the browser to notify you only when the state changes, which is a completely different performance class.
Quick check · 08
You notice duplicate items after scrolling fast. What is the most likely cause?
IntersectionObserver can fire twice before the first request resolves. Without if (loading) return; (raw) or isFetchingNextPage guard (TQ), you append the same page twice. The duplicate keys are a symptom, not the cause.

Combining all four

a real search + filter + infinite feed

Real features don't use one pattern — they use all four at once. Here's a search bar with debounce, an infinite feed with TanStack Query, a memoized row component, and lazy-loaded images. This is the shape of most real "list + search" screens.

RealFeed.jsx
import { useState, useEffect, useRef, memo } from 'react';
import { useInfiniteQuery } from '@tanstack/react-query';
import { useDebouncedValue } from './useDebouncedValue';

// 1. Memoize the row — scrolling re-renders the list, rows should skip
const Row = React.memo(function({ post }) {
  return (
    <li>
      <img src={post.thumbnail} loading="lazy" alt="" />
      <h3>{post.title}</h3>
    </li>
  );
});

function RealFeed() {
  const [query, setQuery] = useState('');

  // 2. Debounce the search input
  const debounced = useDebouncedValue(query, 400);

  const {
    data, fetchNextPage, hasNextPage, isFetchingNextPage, isFetching,
  } = useInfiniteQuery({
    // 3. Query key includes the debounced search — cache per search term
    queryKey: ['feed', debounced],
    queryFn: ({ pageParam = 1, signal }) =>
      fetch(`/api/posts?q=${encodeURIComponent(debounced)}&page=${pageParam}`, { signal })
        .then(r => r.json()),
    initialPageParam: 1,
    getNextPageParam: (last, all) => last.hasMore ? all.length + 1 : undefined,
  });

  // 4. Infinite scroll sentinel
  const sentinel = useRef(null);
  useEffect(() => {
    const el = sentinel.current;
    if (!el || !hasNextPage || isFetchingNextPage) return;

    const io = new IntersectionObserver(
      ([e]) => { if (e.isIntersecting) fetchNextPage(); },
      { rootMargin: '200px' }
    );
    io.observe(el);
    return () => io.disconnect();
  }, [hasNextPage, isFetchingNextPage, fetchNextPage]);

  const posts = data?.pages.flatMap(p => p.posts) ?? [];

  return (
    <div>
      <input
        value={query}
        onChange={e => setQuery(e.target.value)}
        placeholder="Search posts…"
      />
      {isFetching && <small>Searching…</small>}

      <ul>{posts.map(p => <Row key={p.id} post={p} />)}</ul>
      <div ref={sentinel} />

      {isFetchingNextPage && <p>Loading more…</p>}
      {!hasNextPage && posts.length > 0 && <p>End of results.</p>}
    </div>
  );
}

Every pattern is doing one job:

  • Debounce — one request per ~400ms of typing, not per keystroke.
  • Infinite scroll — next page loads when the user is 200px from the end.
  • Memo — Row doesn't re-render for rows whose post object is unchanged.
  • Native lazy loading — <img loading="lazy"> defers offscreen image downloads (browser feature, no React code needed).
  • TanStack Query — caches each ['feed', query], so switching back to a prior search shows results instantly while refreshing in the background.

Interview questions

memoization · throttle/debounce · lazy loading · pagination · infinite scroll

Q1What's the difference between React.memo, useMemo, and useCallback?

React.memo wraps a component and skips rendering it if props are shallow-equal. useMemo caches the result of a computation between renders. useCallback caches a function reference. All three are memoization, but they cache different things — mixing them up is the source of most "memo isn't helping" bugs.

Q2When should you NOT use useMemo or useCallback?

When the computation is cheap. The comparison itself costs something — for a small array map or a filter over 5 items, recomputing is faster than the check. Also: don't wrap every function in useCallback; if the function isn't passed to a memoized child or used in a dependency array, memoizing it has zero benefit and adds noise.

Q3Why does React.memo sometimes not prevent re-renders?

If a prop is a new reference every render (an inline object {a: 1}, an inline array, or an inline function () => doThing()), Object.is comparison always fails, so memo can't help. Fix: memoize the prop with useMemo/useCallback, or move the value out of the render.

Q4Explain debounce vs throttle.

Debounce runs the function only after `wait` ms of silence — every new event resets the timer. Great for search inputs. Throttle runs at most once every `wait` ms, on a schedule. Great for scroll and resize handlers. Debounce is "wait until done"; throttle is "run on a cadence".

Q5How would you implement debounce in React?

Two options. (1) A useDebouncedValue hook that returns a delayed copy of the value: store it in state, update it in setTimeout inside useEffect, clear the timeout in cleanup. Then depend on the debounced value in a fetch effect. (2) A debounce(fn, wait) utility wrapped in useMemo (or a ref) so it isn't recreated every render. The hook version is idiomatic in React because it fits the render model.

Q6Is debounce enough to fix the search race condition?

No. Debounce reduces the number of requests but doesn't order their responses. Two requests can be in flight if the network is slow, and an old response can arrive after a new one — overwriting fresher data. Fix with AbortController (cancel the previous), an ignore flag (check ignore before setState), or a request id. TanStack Query's signal argument gives you cancellation for free.

Q7What does React.lazy do?

It wraps a dynamic import() so React can treat the module as a component. On first render, React calls the import, gets a promise, and suspends rendering until the module resolves. The nearest <Suspense> ancestor shows its fallback during the wait. The bundler splits the module into its own chunk, so it isn't in the initial bundle.

Q8Where should you place Suspense boundaries?

At boundaries the user perceives — around routes (one boundary at the router level), around modals and tabs that only load on demand. Don't put a boundary on every component (you'll see spinners flash in weird places) and don't lazy-load above-the-fold content (the user sees a spinner instead of content).

Q9What is route-level code splitting, and why is it the highest-impact split?

Lazy-loading each route's component so its JS is only downloaded when that route is visited. It's the highest-impact split because most apps have many routes the user never visits in a session — bundling them all forces every user to download code for pages they won't see. Splitting by route means the first screen loads only the first route's code.

Q10How would you implement pagination in React?

State: page and pageSize. Effect (or query hook) fetches /api/items?page=X&limit=Y on page change. Render a page-boundary UI with prev/next disabled at the ends. Important detail: show the full spinner only on first load (loading && !data.length) — otherwise the list flashes empty on every page change. TanStack Query handles this with placeholderData: keepPreviousData and caches each page.

Q11How would you implement infinite scroll?

Two things: a sentinel element at the end of the list, and an IntersectionObserver that fires a "load more" callback when the sentinel enters the viewport. The callback appends the new page to state. Guard with if (loading || !hasMore) return; to prevent duplicate fetches. In TanStack Query, use useInfiniteQuery — pages array, fetchNextPage, hasNextPage, and isFetchingNextPage are provided; you only write the observer.

Q12Why use IntersectionObserver instead of a scroll listener?

A scroll listener fires hundreds of times per second — you'd need to throttle it, and even then you're doing math on every tick. IntersectionObserver asks the browser to notify you only when the observed element enters/exits the viewport — one callback per state change. Massive performance win, and the code is simpler.

Q13How do you prevent duplicate items in infinite scroll?

Two things. (1) Guard the fetch: if (loading || !hasMore) return; — because IntersectionObserver can fire multiple times before the request resolves. (2) If your API can return overlapping items (e.g. new posts pushed while you paginate), de-dupe by id — [...new Map([...pages.flat()].map(p => [p.id, p])).values()], or use cursor pagination which guarantees each page picks up after the previous one.

Q14What's the difference between page-based and cursor-based pagination?

Page-based: ?page=2&limit=10, offset math on the server (LIMIT/OFFSET). Simple but suffers from shifting when rows are added/removed — a page-2 request can return duplicates or skips. Cursor-based: ?after=lastId, server returns rows after that id. Stable, but no "jump to page 5". Feeds and infinite scroll typically want cursor pagination; admin tables with "Page 3 of 20" want page-based.

Q15What does TanStack Query's useInfiniteQuery give you over manually tracking pages?

It stores the pages array, computes the next page param via getNextPageParam, exposes hasNextPage, isFetchingNextPage, and fetchNextPage — all without you writing the state machine. It also caches the whole paginated result across mounts, deduplicates concurrent fetches, and passes a signal to cancel the in-flight request. You only provide queryFn and getNextPageParam.

Q16You notice a React list re-renders on every keystroke in a search input. What's the diagnosis?

The search input's state lives in the same component that renders the list. Every keystroke updates state → re-renders the whole component → the list reconciles. Fixes: (1) put the search state in a child so the input's state doesn't re-render the list (or split into sibling components); (2) memoize the list component with React.memo and stable props; (3) debounce the value so state only changes after 300ms of typing. All three can be needed at once.
