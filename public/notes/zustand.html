Zustand — the small store with sharp teeth

The store library that fits in your head. How it works, why it's different from Context and Redux, how selectors keep re-renders under control, and everything else you need to ship it in production.

01

Why Zustand exists

the shape of the problem · where Redux and Context fall short

React's built-in tools for shared state are context and lifting state up. Both work, both have hard ceilings. Context re-renders every consumer on every change; prop drilling crumbles past three levels. Redux solves both, but asks you to learn actions, reducers, middleware, and DevTools setup before you ship a toggle. Zustand is the smallest useful answer: one hook, one store, selectors for precision, zero boilerplate.

The three big options, honestly compared

Context APIRedux ToolkitZustand
Setup costProvider + reducer + typed contextStore + slice + Provider + hookOne create() call
Re-render granularityEvery consumer re-renders on any changePer-selector, via useSelectorPer-selector, with a single hook
Provider requiredYesYesNo — stores are modules
Async built inNovia createAsyncThunkJust write async functions in the store
Outside ReactNoYesYes (useStore.getState())
Best whenSmall, mostly-read data (theme, auth user)Large team, strict conventions, DevTools-heavyFocused app state with minimal ceremony
The one sentence

Zustand is a single object in memory, wrapped in a hook that returns whatever slice of that object you ask for. It has no Provider, no actions, no reducer — just functions on an object that mutate it and notify subscribers.

Quick check · 01
What is the main reason people reach for Zustand instead of Context?
Context's value prop is "avoid prop drilling", but every consumer re-renders when the value changes. Zustand gives per-selector re-renders with a fraction of the boilerplate.
02

Installation & first store

create · useStore · the shape of the return value

terminal
npm install zustand

Create a store with create. It takes a function that returns your initial state plus whatever actions you want to expose. The return value is a React hook you call to read state, and the same object carries .getState(), .setState(), and .subscribe() for use outside React.

stores/counter.js
import { create } from 'zustand';

export const useCounterStore = create((set) => ({
  // state
  count: 0,
  step: 1,

  // actions — plain functions, called directly
  increment: () => set((s) => ({ count: s.count + s.step })),
  decrement: () => set((s) => ({ count: s.count - s.step })),
  reset:     () => set({ count: 0 }),
  setStep:   (n) => set({ step: n }),
}));

Using it in a component

Counter.jsx
import { useCounterStore } from '../stores/counter';

export default function Counter() {
  const count     = useCounterStore((s) => s.count);
  const increment = useCounterStore((s) => s.increment);
  const reset     = useCounterStore((s) => s.reset);

  return (
    <div>
      <p>{count}</p>
      <button onClick={increment}>+1</button>
      <button onClick={reset}>reset</button>
    </div>
  );
}
💡
No Provider. Zustand stores are just modules. Import them anywhere — including .ts files, services, or Redux DevTools. Each create call makes a completely isolated store; they do not talk to each other unless you wire them to.
Quick check · 02
What does create() return?
The return value is a hook — you call useStore(selector) inside components. It also carries the non-hook API for code that isn't a React component.
03

Selectors — precision re-rendering

what a selector does · shallow equality · unstable object traps

When you call useStore(selector), Zustand runs your selector against the current state and subscribes to changes. On every set(), it re-runs the selector and compares the new result to the previous one. If they're equal (Object.is by default), this component does not re-render. If they differ, it does.

  1. Two components subscribe to count and step, two subscribe to unrelated slices. Initially all render once — normal.
  2. An action runs set(s => ({ count: s.count + 1 })).
  3. Zustand re-runs every subscribed selector. Counter: result changed → re-renders. Toolbar: step unchanged → does not re-render. Footer and Header: unrelated slices → do not re-render.
  4. Only Counter re-rendered. That's the whole win — context would have re-rendered all four.
  5. Now an action runs set({ step: 5 }). This time only Toolbar re-renders.
  6. Two components, two independent updates. Zustand's comparison is Object.is on the selector's return value — so the return value's stability determines everything.
Step 1 / 6

The unstable-object trap

If your selector returns a new object every time, Object.is always reports "different" — even if the contents are identical. The component re-renders on every store update, even updates it doesn't care about.

unstable.ts
// ❌ Every update produces a NEW object — always re-renders
const { count, step } = useCounterStore((s) => ({ count: s.count, step: s.step }));

// ✅ Read each slice separately
const count = useCounterStore((s) => s.count);
const step  = useCounterStore((s) => s.step);

// ✅ Or keep the object but tell Zustand to compare shallowly
import { useShallow } from 'zustand/react/shallow';
const { count, step } = useCounterStore(
  useShallow((s) => ({ count: s.count, step: s.step }))
);
⚠️
The number one Zustand bug. A selector that returns a fresh object or array every call. It looks correct, but the component re-renders on every store change. Fix: read one field per selector, or wrap with useShallow.
💡
Selectors can compute. (s) => s.todos.filter(t => !t.done).length is fine — but the filter runs on every store update, and the array being created is a new object, so you'd still re-render on unrelated changes. Cache computed values outside the store, or derive in useMemo in the component.
Quick check · 03
A component does useStore((s) => ({ a: s.a, b: s.b })). It re-renders on every store update, even when only c changes. Why?
Zustand compares the selector's return value by reference. A fresh { a, b } literal is always a new reference, so the check always fails. Fix: split into two selectors, or use useShallow.
04

set and the store API

set partial · set function · get · replace · subscribe

The set function is how you update state. It accepts either a partial object (merged into state) or a function that receives the current state and returns a partial. The get function returns the current state — useful when an action needs to read state.

set-patterns.js
create((set, get) => ({
  count: 0,
  user: null,

  // partial object — merged into current state
  reset: () => set({ count: 0 }),

  // function form — read the current state
  increment: () => set((s) => ({ count: s.count + 1 })),

  // get() — read state outside the setter
  double: () => set({ count: get().count * 2 }),

  // replace: true — WIPE state instead of merging
  logout: () => set({ count: 0, user: null }, true),
}));
⚠️
The replace: true trap. With set(obj, true) the state becomes exactly the object you passed — no merge, no default fields. Every field you omit is gone, including actions. Use this only when you're intentionally resetting the whole store.

Reading and writing state outside React

outside-react.ts
// Get current state (a snapshot)
const current = useCounterStore.getState();

// Update without a React render
useCounterStore.setState({ count: 100 });

// Or the function form
useCounterStore.setState((s) => ({ count: s.count + 1 }));

// Subscribe to changes outside React (e.g., in an API client)
const unsub = useCounterStore.subscribe((state) => {
  console.log('count is now', state.count);
});
unsub();
Quick check · 04
What does set({ count: 5 }, true) do that set({ count: 5 }) doesn't?
replace: true replaces the whole state object with the partial you pass. Every field you didn't list becomes undefined. Use it for logout-style resets, not for normal updates.
05

Async actions

no thunk · no middleware · just async functions

In Redux, an async action needs createAsyncThunk and three reducers. In Zustand, you write an async function. That's it. The function updates state at each step — loading, then data or error — using the same set.

stores/users.js
import { create } from 'zustand';

export const useUsersStore = create((set, get) => ({
  users: [],
  loading: false,
  error: null,

  fetchUsers: async () => {
    set({ loading: true, error: null });
    try {
      const res = await fetch('/api/users');
      if (!res.ok) throw new Error('Failed');
      const users = await res.json();
      set({ users, loading: false });
    } catch (err) {
      set({ error: err.message, loading: false });
    }
  },

  addUser: async (user) => {
    const res = await fetch('/api/users', {
      method: 'POST',
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(user),
    });
    const created = await res.json();
    set((s) => ({ users: [...s.users, created] }));
  },
}));
💡
Race conditions are still your problem. If fetchUsers is called twice quickly, the second set may resolve before the first, leaving stale data in state. Store a request ID or an AbortController in the store and check it before writing. Zustand does not do this for you — same as Redux thunks.

Reading from the store inside an action

Use get() when an action needs a value from elsewhere in the store:

get-inside-action.js
create((set, get) => ({
  cart: [],
  addToCart: (item) => {
    const existing = get().cart.find((x) => x.id === item.id);
    if (existing) {
      set((s) => ({
        cart: s.cart.map((x) => x.id === item.id ? { ...x, qty: x.qty + 1 } : x),
      }));
    } else {
      set((s) => ({ cart: [...s.cart, { ...item, qty: 1 }] }));
    }
  },
}));
Quick check · 05
You want to call useUsersStore.getState().fetchUsers() from a non-React module. Does this work?
The store lives in module scope, not in React context. Anywhere you import it, you can read and call its actions — including from services, listeners, and other stores.
06

Middleware

persist · devtools · immer · combine them

Middleware wraps the create call to extend the store. They're optional — the base store works fine without any. Each one adds capabilities the base store intentionally leaves out.

persist — survive a reload

persist.js
import { create } from 'zustand';
import { persist } from 'zustand/middleware';

export const useCartStore = create(
  persist(
    (set) => ({
      items: [],
      addItem: (item) => set((s) => ({ items: [...s.items, item] })),
      clear: () => set({ items: [] }),
    }),
    {
      name: 'cart',                 // localStorage key
      partialize: (state) => ({ items: state.items }),  // omit actions
      version: 1,                 // for migrations
    }
  )
);
⚠️
Don't persist functions. By default persist serialises the whole state to localStorage — which fails on functions. Use partialize to keep only the data fields. This is the most common persist mistake.

devtools — the Redux DevTools you know and love

devtools.js
import { create } from 'zustand';
import { devtools } from 'zustand/middleware';

export const useCounterStore = create(
  devtools(
    (set) => ({
      count: 0,
      increment: () => set(
        (s) => ({ count: s.count + 1 }),
        false,
        'counter/increment'   // action name shown in DevTools
      ),
    }),
    { name: 'CounterStore' }      // tab name in DevTools
  )
);

immer — mutate without spreads

immer.js
import { create } from 'zustand';
import { immer } from 'zustand/middleware/immer';

export const useTodoStore = create(
  immer((set) => ({
    todos: [],
    add: (text) => set((s) => { s.todos.push({ text, done: false }); }),
    toggle: (i) => set((s) => { s.todos[i].done = !s.todos[i].done; }),
  }))
);

Combining middleware

Order matters: outermost wraps innermost. Common order is devtools(persist(immer(...))) — DevTools sees every update, persist serialises, immer handles mutation syntax:

combined.js
import { create } from 'zustand';
import { devtools, persist } from 'zustand/middleware';
import { immer } from 'zustand/middleware/immer';

export const useCartStore = create<CartState>()(
  devtools(
    persist(
      immer((set) => ({
        items: [],
        add: (item) => set((s) => { s.items.push(item); }, false, 'cart/add'),
      })),
      { name: 'cart', partialize: (s) => ({ items: s.items }) }
    ),
    { name: 'CartStore' }
  )
);
Quick check · 06
Your persisted store serialises to localStorage but action functions keep disappearing on reload. Why?
Functions aren't JSON-serialisable. When persist reads the store back, the actions are simply gone. partialize keeps only the serialisable fields — actions live in the code, not the storage.

The slices pattern

one store, many concerns · the Zustand answer to "reducers"

As a store grows, one big create becomes hard to read. The slices pattern splits the state shape into focused pieces, then combines them into one store. Same store at runtime, better organised source.

slices/cartSlice.js
export const createCartSlice = (set) => ({
  cart: { items: [] },
  addToCart: (item) => set((s) => ({ cart: { items: [...s.cart.items, item] } })),
});
slices/userSlice.js
export const createUserSlice = (set) => ({
  user: null,
  setUser: (u) => set({ user: u }),
  clearUser: () => set({ user: null }),
});
stores/useAppStore.js
import { create } from 'zustand';
import { createCartSlice } from './slices/cartSlice';
import { createUserSlice } from './slices/userSlice';

export const useAppStore = create((...a) => ({
  ...createCartSlice(...a),
  ...createUserSlice(...a),
}));
Why this is nice

The store is still a single flat object at runtime — state.cart.items, state.user, state.addToCart. But the source is split by concern, each slice is testable in isolation, and adding a new domain is one import + one spread. This is Zustand's equivalent of RTK slices without the ceremony.

Quick check · 07
In the slices pattern, is state.cart a nested object inside a per-slice store, or a property on one flat store?
Slices are a code-organisation tool, not a runtime boundary. At runtime there's one store; each slice contributes keys to it. The nested structure (cart.items) is your choice, not a requirement.

Zustand with TypeScript

the StateCreator type · combining middleware · typed selectors

Zustand is written in TypeScript, and the typing is clean once you know the pattern. Two things to remember: declare the state type on create<T>(), and use the curried form create<T>()(...) when you attach middleware.

typed-store.ts
import { create } from 'zustand';
import { devtools, persist } from 'zustand/middleware';

interface User {
  id: string;
  name: string;
}

interface AuthState {
  user: User | null;
  login: (user: User) => void;
  logout: () => void;
}

export const useAuthStore = create<AuthState>()(
  devtools(
    persist(
      (set) => ({
        user: null,
        login: (user) => set({ user }, false, 'auth/login'),
        logout: () => set({ user: null }, false, 'auth/logout'),
      }),
      { name: 'auth', partialize: (s) => ({ user: s.user }) }
    ),
    { name: 'AuthStore' }
  )
);

Typed selectors with an equality function

typed-selector.ts
import { useShallow } from 'zustand/react/shallow';

// Single field
const user = useAuthStore((s) => s.user);       // User | null

// Multiple fields, shallow equality
const { user, logout } = useAuthStore(
  useShallow((s) => ({ user: s.user, logout: s.logout }))
);
💡
Why create<T>()(...) with the extra ()? Middleware changes the store's type signature — devtools(persist(fn)) is not the same shape as fn. The curried form lets TypeScript apply the middleware's type transformations correctly. Without it, you'll get confusing type errors.
Quick check · 08
What does create<AuthState>()(...) do differently from create((set) => ...)?
TypeScript types are erased — nothing changes at runtime. The generics tell the compiler what the store looks like, and the curried form is required when middleware is involved.

Testing Zustand stores

reset between tests · no wrapper · plain function tests

Stores are plain modules. You don't need a React testing utility to test them — just import and call actions directly. The one thing you must do is reset state between tests so they don't leak into each other.

counter.test.js
import { useCounterStore } from './counter';

beforeEach(() => {
  // reset the store before each test
  useCounterStore.setState({ count: 0, step: 1 }, true);
});

test('increment adds step', () => {
  useCounterStore.getState().increment();
  expect(useCounterStore.getState().count).toBe(1);
});
⚠️
Reset properly. setState({count: 0}) merges — it leaves actions intact but doesn't reset step. Use setState(initial, true) to wipe everything, or store an initialState object and reset from it. Otherwise a test that changes step will affect the next test.
Quick check · 09
Why do you need to reset the store between tests?
Imported once, shared across tests. If test A increments count, test B sees the incremented value unless you reset. This is different from component-local state, which is fresh per test.

Pitfalls that bite in real projects

common mistakes · what to do instead

PitfallWhat happensFix

Persisting the whole storeActions disappear; localStorage bloatspartialize to only data fields

⚠️
Zustand is not a cache. Don't store fetched server data in Zustand unless you're building your own caching layer. TanStack Query or SWR exist exactly for that. Use Zustand for client state: UI, drafts, cart, preferences, session tokens. Two tools, two jobs.

Interview questions

what you'll actually be asked about Zustand

Q1What is Zustand, and how does it differ from Redux?

Zustand is a small state management library for React (and vanilla JS) built around a single store per module. Unlike Redux, there is no Provider, no reducer, no action type constants — you define state and actions in one object, and mutate state with a set function. Component subscription is per-selector by default, so you get the same re-render precision as Redux with a fraction of the code.

Q2Why doesn't Zustand require a Provider?

Because the store lives in module scope, not in React context. When you call create(), the returned hook and the internal store are already available to any module that imports them. Redux uses a Provider to inject the store into context; Zustand sidesteps the whole layer. The upside is less boilerplate and access outside React; the downside is that you can't have two different instances of the same store in one app tree without extra work (there's a createStore + useStore pattern for that case).

Q3How do selectors prevent unnecessary re-renders?

When you call useStore(selector), Zustand runs the selector against current state and stores the result. On every state update, it re-runs the selector and compares the new result to the previous one using Object.is. If they're equal, the component does not re-render. This means each component subscribes only to the specific slice it reads, ignoring unrelated state changes entirely.

Q4What's the pitfall with selecting multiple fields in an object?

The selector (s) => ({ a: s.a, b: s.b }) creates a new object literal every call. Zustand's default Object.is comparison always fails, so the component re-renders on every store update. Fix: split into one selector per field, or wrap with useShallow from zustand/react/shallow so Zustand compares the object shallowly instead of by reference.

Q5How would you implement an async action in Zustand?

Just write an async function on the store. No thunk, no middleware. The function calls set to flip loading, awaits the fetch, then calls set again with data or error. It's a plain JS function; the store has no opinion about how you handle async. Race conditions and cancellation are still your responsibility — an AbortController stored alongside the action, or checking a request ID before writing, is the standard fix.

Q6What does the persist middleware do, and what's the pitfall?

It serialises the store to storage (localStorage by default) and rehydrates on load. The pitfall is that JSON can't serialise functions — so if you persist the whole state, every action disappears after reload. The fix is partialize: a function returning only the data fields you want to persist. Also mind version and migrate for schema changes, and avoid persisting sensitive fields like tokens.

Q7What is the slices pattern and why use it?

Split the store's state and actions into separate factory functions — one per concern — then spread them into a single create. Each slice is a plain function that takes set and returns a partial state. At runtime there is still one store; the slices are purely an organisational tool. This keeps large stores readable and each slice testable in isolation — the same idea as RTK's createSlice, without the reducer ceremony.

Q8How do you use a Zustand store outside React?

Every store returned by create exposes getState(), setState(), and subscribe(). From a service module, event handler, or another store, you can call useStore.getState().someAction() or read a snapshot. This makes Zustand naturally usable in non-React code — a common ask when migrating an existing app.

Q9When would you use Zustand vs TanStack Query vs Context?

TanStack Query for server state — anything fetched from an API. Zustand for client state shared across distant components — cart, session, preferences, UI drafts. Context for injecting a value deep in the tree that rarely changes — a theme, a router, a small user object — where re-render cost is negligible. Big apps often use all three.

Q10How do you reset a Zustand store for testing?

Because the store is a module-level singleton, state leaks between tests. Call useStore.setState(initialState, true) in beforeEach — the second argument true replaces the whole state instead of merging. Store the initial state in a constant (or in your slice factories) so the reset stays in sync with your defaults.

Q11How does Zustand work internally?

Under the hood it's a closure — create holds a state variable, a set of listeners, and a setState that mutates the state and notifies every listener. The React hook is built with useSyncExternalStore, which is the React-provided way to subscribe to an external store. That's why there's no Provider: the hook returns the current snapshot and subscribes to changes directly. The entire library is a few hundred lines.
