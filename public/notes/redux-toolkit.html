01

Why Redux Toolkit exists

the boilerplate problem · what RTK fixes

Plain Redux works. But writing it by hand is exhausting: you write action type constants, action creators, switch-statement reducers, manual object spreads for every update, and a store setup that wires middleware and DevTools yourself. Redux Toolkit (RTK) is the official fix — the same Redux underneath, with the repetitive parts generated for you.

TaskHand-written ReduxRedux Toolkit
Store setupcreateStore + applyMiddleware + compose + DevTools enhancerOne configureStore() call [citation:1][citation:2]
Action typesHand-written string constantsGenerated from reducer names [citation:3]
Action creatorsHand-written functionsGenerated by createSlice [citation:3]
Immutable updates{ ...state, items: [...state.items, x] }state.items.push(x) — Immer handles the copy [citation:1]
Async logicHand-written thunk dispatching _PENDING / _SUCCESS / _FAILUREcreateAsyncThunk generates all three [citation:14]
Data fetching + cachingWrite it yourselfRTK Query — endpoints, hooks, cache management [citation:14]
The one sentence to remember

Redux Toolkit is still Redux: one store, dispatched action objects, reducers that update state. What changes is how much code you write to get there. [citation:1]

Quick check · 01
Which statement about Redux Toolkit is false?
RTK does not replace Redux — the store, actions, and reducers are still Redux [citation:1]. What changes is the ergonomics: configureStore handles setup, createSlice generates actions/types, and Immer turns mutation syntax into immutable updates.
02

Installation & store setup

npm packages · configureStore · Provider

What to install

terminal
npm install @reduxjs/toolkit react-redux

@reduxjs/toolkit includes the Redux core, Redux Thunk, and Reselect. react-redux gives you Provider, useSelector, and useDispatch. [citation:7]

Create the store

src/app/store.js
import { configureStore } from '@reduxjs/toolkit';
import usersReducer from '../features/users/usersSlice';
import authReducer  from '../features/auth/authSlice';

export const store = configureStore({
  reducer: {
    users: usersReducer,
    auth:  authReducer,
  },
});

configureStore does all of this automatically: combines your slice reducers, adds redux-thunk, adds dev-mode checks for accidental mutations, and wires up the Redux DevTools Extension. [citation:2]

Wrap the app with Provider

src/main.jsx
import React from 'react';
import ReactDOM from 'react-dom/client';
import { Provider } from 'react-redux';
import { store } from './app/store';
import App from './App';

ReactDOM.createRoot(document.getElementById('root')).render(
  <Provider store={store}>
    <App />
  </Provider>
);
💡
One store, one Provider. You wrap <App /> once at the root. Every component below it can now use useSelector and useDispatch without prop drilling.
Quick check · 02
What does configureStore add by default that hand-written createStore does not?
Those three defaults are why RTK exists [citation:1][citation:2]. You can override any of them with the middleware and enhancers options if you need to.
03

createSlice — reducers, actions, types, all at once

name · initialState · reducers · Immer · exports

createSlice takes a slice name, an initial state, and an object of reducer functions. It returns a reducer, and it automatically generates action creators and action type strings from the reducer names. [citation:3]

A complete slice

src/features/counter/counterSlice.js
import { createSlice } from '@reduxjs/toolkit';

const initialState = {
  value: 0,
  status: 'idle',
};

const counterSlice = createSlice({
  name: 'counter',
  initialState,
  reducers: {
    increment(state) {
      state.value += 1;             // looks like mutation — Immer makes it safe
    },
    decrement(state) {
      state.value -= 1;
    },
    incrementByAmount(state, action) {
      state.value += action.payload;   // action.payload is whatever you pass to dispatch
    },
  },
});

export const { increment, decrement, incrementByAmount } = counterSlice.actions;
export default counterSlice.reducer;
What just happened

You wrote three reducer functions. RTK gave you:

· Action creators: increment(), decrement(), incrementByAmount(5)
· Action types: 'counter/increment', 'counter/decrement', 'counter/incrementByAmount'
· A reducer ready to be added to the store.

Immer: why mutation syntax is safe

Inside a createSlice reducer, writing state.value += 1 looks like mutation — but Immer records your changes and produces a new immutable state object behind the scenes. No spreads, no accidental reference bugs. [citation:1]

⚠️
One rule: you can mutate state, but you must return nothing (or return a brand-new state). Mixing "mutate and return" confuses Immer. Just mutate, or just return a new value — pick one.

Using the slice in a component

Counter.jsx
import { useSelector, useDispatch } from 'react-redux';
import { increment, decrement, incrementByAmount } from './counterSlice';

export default function Counter() {
  const count = useSelector((state) => state.counter.value);
  const dispatch = useDispatch();

  return (
    <div>
      <p>{count}</p>
      <button onClick={() => dispatch(increment())}>+1</button>
      <button onClick={() => dispatch(decrement())}>-1</button>
      <button onClick={() => dispatch(incrementByAmount(5))}>+5</button>
    </div>
  );
}
Quick check · 03
Given createSlice({ name: 'todos', reducers: { addTodo(state, action) { ... } } }), what action type is generated?
The pattern is {sliceName}/{reducerName} [citation:3]. So name: 'todos' + addTodo produces 'todos/addTodo'. You never type this string yourself — the action creator carries it.
Quick check · 04
Why can you write state.items.push(newItem) inside a slice reducer without breaking Redux?
Immer is baked into createSlice [citation:1]. Your code mutates a draft; Immer diffs it and returns a new state. You get the ergonomics of mutation with the safety of immutability.

createAsyncThunk — API calls the right way

pending · fulfilled · rejected · extraReducers · unwrap

In a MERN app, most state comes from your Express API. createAsyncThunk takes an action type string and a function that returns a promise, and generates a thunk that dispatches three lifecycle actions: pending, fulfilled, and rejected. [citation:14][citation:11]

The three phases, visualised

  1. You call dispatch(fetchUsers()). The thunk runs your async function — here, a fetch to the Express API. Immediately, it dispatches the pending action. Your extraReducers sets loading = true.
  2. If the promise resolves, the thunk dispatches fulfilled with the resolved value as action.payload. You set loading = false and store the data. [citation:11]
  3. The fulfilled branch typically looks like: state.loading = false; state.items = action.payload; — one clean line, no manual success action.
  4. If the promise rejects, the thunk dispatches rejected. The error lives in action.error (auto-serialised), or in action.payload if you used rejectWithValue. You set loading = false and store the message.
  5. All three are handled in extraReducers via the builder callback — because these action types are not generated by your slice's own reducers. [citation:3]
Step 1 / 5

A complete users slice with an API call

features/users/usersSlice.js
import { createSlice, createAsyncThunk } from '@reduxjs/toolkit';

// 1. Define the async thunk
export const fetchUsers = createAsyncThunk(
  'users/fetchUsers',                       // action type prefix
  async (_, { rejectWithValue }) => {          // payload creator
    try {
      const res = await fetch('/api/users');
      if (!res.ok) throw new Error('Failed to fetch');
      return await res.json();                 // becomes action.payload
    } catch (err) {
      return rejectWithValue(err.message);   // becomes action.payload in rejected
    }
  }
);

// 2. Slice
const usersSlice = createSlice({
  name: 'users',
  initialState: {
    items: [],
    loading: false,
    error: null,
  },
  reducers: {},                              // no sync reducers here
  extraReducers: (builder) => {
    builder
      .addCase(fetchUsers.pending, (state) => {
        state.loading = true;
        state.error = null;
      })
      .addCase(fetchUsers.fulfilled, (state, action) => {
        state.loading = false;
        state.items = action.payload;
      })
      .addCase(fetchUsers.rejected, (state, action) => {
        state.loading = false;
        state.error = action.payload;
      });
  },
});

export default usersSlice.reducer;

Using it in a component

UsersList.jsx
import { useEffect } from 'react';
import { useSelector, useDispatch } from 'react-redux';
import { fetchUsers } from './usersSlice';

export default function UsersList() {
  const dispatch = useDispatch();
  const { items, loading, error } = useSelector((state) => state.users);

  useEffect(() => {
    dispatch(fetchUsers());
  }, [dispatch]);

  if (loading) return <p>Loading…</p>;
  if (error)   return <p>Error: {error}</p>;

  return <ul>{items.map((u) => <li key={u._id}>{u.name}</li>)}</ul>;
}

rejectWithValue vs a thrown error

ApproachWhat action.payload holds on rejectionWhen to use
throw new Error('...')undefined — error is in action.error.messageQuick prototypes; you only need the message
return rejectWithValue(msg)Exactly msg (or any shape you pass)Production — you control the error shape, and it stays serialisable [citation:11]

Waiting for a thunk in a component

Sometimes you need to do something after the thunk finishes — redirect, close a modal, show a toast. Dispatch returns a promise; .unwrap() gives you the raw payload or throws the rejection. [citation:11]

awaiting a thunk
const handleSubmit = async () => {
  try {
    const result = await dispatch(fetchUsers()).unwrap();
    console.log('Got users:', result);
    navigate('/dashboard');
  } catch (err) {
    console.error('Failed:', err);  // err is whatever you passed to rejectWithValue
  }
};
Quick check · 05
Where do you handle the pending / fulfilled / rejected actions of a thunk?
reducers is for actions the slice generates. Thunk lifecycle actions come from elsewhere, so they go in extraReducers [citation:3]. That is the entire reason extraReducers exists.
Quick check · 06
What does dispatch(fetchUsers()).unwrap() do when the thunk rejects?
unwrap() resolves with the fulfilled payload, or throws the rejection value [citation:11]. Without unwrap, the dispatched promise always resolves with the action object — it never rejects, to avoid unhandled promise warnings.

RTK Query — stop hand-writing data fetching

createApi · auto-generated hooks · caching · invalidation

If createAsyncThunk feels like a lot of ceremony for "GET a list", that is because it is. RTK Query is the built-in data-fetching layer: you define endpoints once, and it generates a reducer, middleware, and React hooks that handle loading, caching, refetching, and invalidation. [citation:14]

One API file, all your endpoints

src/services/api.js
import { createApi, fetchBaseQuery } from '@reduxjs/toolkit/query/react';

export const api = createApi({
  reducerPath: 'api',
  baseQuery: fetchBaseQuery({ baseUrl: '/api' }),
  tagTypes: ['Users', 'Posts'],
  endpoints: (builder) => ({
    getUsers: builder.query({
      query: () => '/users',
      providesTags: ['Users'],
    }),
    addUser: builder.mutation({
      query: (body) => ({ url: '/users', method: 'POST', body }),
      invalidatesTags: ['Users'],
    }),
  }),
});

export const { useGetUsersQuery, useAddUserMutation } = api;

Add it to the store

src/app/store.js
import { configureStore } from '@reduxjs/toolkit';
import { api } from '../services/api';

export const store = configureStore({
  reducer: {
    [api.reducerPath]: api.reducer,        // RTK Query's reducer
  },
  middleware: (gDM) => gDM().concat(api.middleware),  // cache + lifecycle
});

Use the hook — no thunk, no useEffect

UsersList.jsx
import { useGetUsersQuery } from '../services/api';

export default function UsersList() {
  const { data, isLoading, isError } = useGetUsersQuery();

  if (isLoading) return <p>Loading…</p>;
  if (isError)   return <p>Something went wrong.</p>;

  return <ul>{data.map((u) => <li key={u._id}>{u.name}</li>)}</ul>;
}
What RTK Query did for you

It fetched on mount, tracked loading, cached the result, de-duplicated a second component that asked for the same data, and will refetch automatically when addUser fires — because the mutation invalidates the 'Users' tag. [citation:14]

Quick check · 07
Two components both call useGetUsersQuery() at the same time. What happens?
RTK Query de-duplicates in-flight requests for the same endpoint + arguments. This is one of its core advantages over hand-written thunks, where two components would each fire their own request. [citation:6]

How it fits a MERN app

frontend state · backend boundary · auth example

In a MERN stack, MongoDB + Express own the data. React + Redux Toolkit own the client-side mirror of that data, plus UI state. The boundary is HTTP.

StateLives inManaged by
User list from GET /api/usersServer → Redux cacheRTK Query endpoint
Logged-in user + tokenRedux + localStorageauthSlice with a thunk for login
Modal open/closedComponent stateuseState — no Redux needed
Form draft before submitComponent stateuseState — no Redux needed
Cart itemsReduxcartSlice (sync reducers)
Don't put everything in Redux

Redux is for state that multiple distant components need or that must survive navigation. Modal toggles, form inputs, and hover state belong in component state. Putting them in Redux is the #1 reason people say "Redux is overkill".

Auth: a thunk that talks to Express

features/auth/authSlice.js
import { createSlice, createAsyncThunk } from '@reduxjs/toolkit';

export const login = createAsyncThunk(
  'auth/login',
  async ({ email, password }, { rejectWithValue }) => {
    try {
      const res = await fetch('/api/auth/login', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify({ email, password }),
      });
      if (!res.ok) {
        const err = await res.json();
        throw new Error(err.message || 'Login failed');
      }
      return await res.json();           // { user, token }
    } catch (err) {
      return rejectWithValue(err.message);
    }
  }
);

const authSlice = createSlice({
  name: 'auth',
  initialState: {
    user: null,
    token: localStorage.getItem('token'),
    loading: false,
    error: null,
  },
  reducers: {
    logout(state) {
      state.user = null;
      state.token = null;
      localStorage.removeItem('token');
    },
  },
  extraReducers: (builder) => {
    builder
      .addCase(login.pending, (state) => {
        state.loading = true;
        state.error = null;
      })
      .addCase(login.fulfilled, (state, action) => {
        state.loading = false;
        state.user = action.payload.user;
        state.token = action.payload.token;
        localStorage.setItem('token', action.payload.token);
      })
      .addCase(login.rejected, (state, action) => {
        state.loading = false;
        state.error = action.payload;
      });
  },
});

export const { logout } = authSlice.actions;
export default authSlice.reducer;
Quick check · 08
A component only shows/hides a dropdown. Should that state live in Redux?
Redux adds indirection. If only one component cares about the value, and it resets on unmount, useState is simpler and faster. Use Redux for the "single source of truth" state that distant components read. [citation:8]

Pitfalls that bite in real projects

common mistakes · what to do instead

PitfallWhat happensFix
Mutating state outside a reducerReact doesn't re-render; DevTools shows no actionAlways dispatch an action; never write state.x = in a component
Returning state and mutating it in ImmerImmer throws: "An immer producer returned a new value and modified its draft"Mutate or return — never both
Forgetting extraReducers for thunksAsync data never reaches state; loading stays falseAdd all three cases: pending, fulfilled, rejected
Putting local UI state in ReduxBoilerplate for no benefit; every keystroke dispatchesUse useState unless multiple distant components need it
Forgetting api.middleware in storeRTK Query hooks never fire; no caching, no lifecyclemiddleware: (gDM) => gDM().concat(api.middleware)
Duplicating server data in Redux and RTK QueryTwo sources of truth drift apartPick one: RTK Query for server data, plain slices for client-only state
Large objects in Redux DevToolsDevTools slows to a crawlNormalise data; use createEntityAdapter or RTK Query's cache
⚠️
The "two sources of truth" trap in MERN. If you fetch /api/users with a thunk into usersSlice.items, and also fetch it with RTK Query's useGetUsersQuery, you now have two copies. One component reads the first, another the second, and a mutation updates only one. Pick RTK Query for server data, or thunks — not both for the same endpoint.

Interview questions

what you'll actually be asked about RTK

Q1What is Redux Toolkit, and why is it preferred over plain Redux?

RTK is the official, opinionated toolset for Redux. It removes boilerplate: configureStore sets up the store with thunk and DevTools, createSlice generates action creators and types from reducer names, and Immer lets you write "mutating" reducer code that produces immutable state. It is still Redux — same store, actions, reducers — just with less code and fewer footguns. [citation:1][citation:14]

Q2What does configureStore do under the hood?

It combines your slice reducers with combineReducers, adds redux-thunk middleware, adds development-mode checks for accidental mutations and non-serialisable values, and enables the Redux DevTools Extension — all with one call. You can override each default with the middleware and enhancers options. [citation:2]

Q3How does createSlice reduce boilerplate?

You give it name, initialState, and an object of reducer functions. It returns the reducer and generates action creators and action type strings ('sliceName/reducerName'). Reducers can be written with mutation syntax because Immer is built in. [citation:3]

Q4Explain createAsyncThunk and the three lifecycle actions.

It takes an action-type prefix and a payload creator (async function). When dispatched, it dispatches pending immediately, then fulfilled with the resolved value as payload, or rejected with the error. You handle all three in extraReducers. Use rejectWithValue to control the rejection payload shape. [citation:11][citation:14]

Q5What is the difference between reducers and extraReducers in createSlice?

reducers defines actions that the slice generates — sync handlers with auto-created action creators. extraReducers handles action types defined elsewhere: actions from other slices, or thunk lifecycle actions. Reducers in extraReducers do not generate new action creators. [citation:3]

Q6When should you use createAsyncThunk vs RTK Query?

createAsyncThunk for complex async flows — chaining dispatches, reading state mid-flow, non-HTTP async. RTK Query for standard API endpoints: it handles caching, de-duplication, loading states, and tag-based invalidation with far less code. For a typical MERN CRUD app, RTK Query covers most of what you'd otherwise write with thunks. [citation:14]

Q7Why can you mutate state in a createSlice reducer?

Because Immer wraps the reducer. You're mutating a draft, not the real state. Immer records the changes and produces a new immutable state object. The result is safe and idiomatic — but you must not both mutate and return a new value. [citation:1]

Q8How does RTK Query handle caching and refetching?

Each endpoint result is cached under a key. Components subscribe via generated hooks. You assign providesTags to queries and invalidatesTags to mutations; when a mutation invalidates a tag, every query providing that tag refetches automatically. In-flight requests are de-duplicated. [citation:6][citation:14]

Q9What does dispatch(fetchUsers()).unwrap() do?

The dispatched thunk returns a promise that always resolves with the action object. .unwrap() extracts the fulfilled payload, or throws the rejection value — so you can try/catch it in the component. [citation:11]

Q10Is Redux Toolkit overkill for a small MERN app?

Often, yes. If your app is a handful of pages and state lives mostly in components, useState and useContext may be enough. Redux earns its place when you have reasonable amounts of data changing over time, need a single source of truth, or find prop drilling unmanageable. [citation:8]
