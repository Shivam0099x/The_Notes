What PostgreSQL is

relational model · tables · ACID · why it wins

PostgreSQL is an open-source relational database. Data lives in tables — a fixed set of typed columns, and rows of values. Relationships are expressed through foreign keys. Every operation is ACID: atomic, consistent, isolated, durable. It has decades of production use, is used by companies you've heard of (Instagram, Apple, Twitch, Reddit), and is the default "serious" database for most teams that aren't on a managed proprietary service.

The mental model

A Postgres database is a set of tables with enforced shapes. Rows are typed, keys are enforced, relationships are declared. You don't "query documents" — you write declarative SQL that describes the result you want, and the planner decides how to compute it.

Why teams pick Postgres

  • Correctness. ACID transactions, foreign keys, constraints — the database refuses to store garbage.
  • Powerful SQL. Window functions, CTEs, JSONB, full-text search, partitioning, lateral joins, custom types — all built in.
  • Extensibility. Extensions like pg_trgm (fuzzy text), PostGIS (geo), pgvector (vector search), TimescaleDB (time series).
  • Standards-compliant. If you learn SQL in Postgres, you know SQL almost everywhere.
  • Mature replication, backups, and monitoring. Production-grade for decades.
Quick check · 01
What does ACID stand for?
A transaction either fully commits or fully rolls back (atomicity), leaves data valid (consistency), doesn't see partial work of others (isolation), and survives a crash after commit (durability).

Creating tables — DDL

types · constraints · primary key · foreign key · default

schema.sql
CREATE TABLE users (
  id          SERIAL PRIMARY KEY,
  email       TEXT UNIQUE NOT NULL,
  name        TEXT NOT NULL,
  age         INT CHECK (age >= 0),
  active      BOOLEAN NOT NULL DEFAULT TRUE,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

CREATE TABLE posts (
  id          BIGSERIAL PRIMARY KEY,
  title       TEXT NOT NULL,
  body        TEXT,
  author_id   INT NOT NULL,
  created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  FOREIGN KEY (author_id) REFERENCES users(id) ON DELETE CASCADE
);

Constraints — the database enforces them, always

  • NOT NULL — column can't be null.
  • UNIQUE — no duplicates (nulls are allowed by default; use UNIQUE NULLS NOT DISTINCT in PG15+ to tighten).
  • PRIMARY KEY — UNIQUE + NOT NULL, and the row's identity.
  • FOREIGN KEY — the value must exist in the referenced column. ON DELETE CASCADE, SET NULL, RESTRICT control what happens when the parent is deleted.
  • CHECK — arbitrary boolean expression. CHECK (age >= 0), CHECK (end_date > start_date).
  • DEFAULT — used when you omit the column. DEFAULT NOW(), DEFAULT 'pending'.
⚠️
Never use FLOAT or REAL for money. NUMERIC(10,2) or store paise/cents as integers. Binary floating point can't represent 0.10 exactly — you will get 0.09999999999999999 and your invoices will be off by paise. This is one of the most common production bugs in e-commerce.
Quick check · 02
What type would you use to store a price like ₹99.99?
FLOAT represents decimals in binary, which can't represent 0.1 exactly. NUMERIC stores exact decimals and is the correct type for money.
04

Insert, update, delete, select

the four basic writes · RETURNING · UPSERT

dml.sql
-- INSERT one row
INSERT INTO users (email, name, age)
VALUES ('aarav@x.com', 'Aarav', 22);

-- INSERT many
INSERT INTO users (email, name, age) VALUES
  ('priya@x.com', 'Priya', 20),
  ('karan@x.com', 'Karan', 31);

-- INSERT … RETURNING gives you back the inserted row (including generated id)
INSERT INTO users (email, name) VALUES ('neha@x.com', 'Neha')
RETURNING id, created_at;

-- UPDATE
UPDATE users SET age = age + 1 WHERE city = 'Indore';

-- UPDATE … RETURNING
UPDATE users SET active = FALSE
WHERE created_at < NOW() - INTERVAL '1 year'
RETURNING id;

-- DELETE
DELETE FROM users WHERE active = FALSE;

-- UPSERT — INSERT, or UPDATE if the unique key conflicts
INSERT INTO users (email, name)
VALUES ('aarav@x.com', 'Aarav S')
ON CONFLICT (email)
DO UPDATE SET name = EXCLUDED.name;

-- UPSERT but ignore if exists (do nothing)
INSERT INTO users (email, name) VALUES ('x@y.com', 'X')
ON CONFLICT (email) DO NOTHING;
💡
RETURNING saves a round-trip. Instead of INSERT then SELECT to get the auto-generated id, add RETURNING id and Postgres returns the row that was just written. In Express with pg, this is how you avoid the classic race condition of "insert then query for the last id".

Safe UPDATE/DELETE — always scope with WHERE

A stray UPDATE users SET active = false with no WHERE deactivates every user. In a REPL, the most common defensive pattern is:

  1. Run the SELECT with the same WHERE and check the rows.
  2. Wrap the UPDATE/DELETE in a transaction — BEGIN, run it, then ROLLBACK to test, or COMMIT to keep it.
  3. Or use RETURNING * so you see exactly what was affected.
Quick check · 03
You just INSERTed a row and want the auto-generated id back in one statement. What do you add?
MAX(id) is racy — another insert could land between your write and the read. RETURNING gives you your row atomically.

SELECT — the heart of SQL

WHERE · ORDER BY · LIMIT · DISTINCT · operators · NULL

The SELECT statement runs in a defined order — even though you write it in a different order. Internalize this once and half of SQL becomes obvious.

  1. FROM / JOIN runs first. Postgres builds the working set of rows from one or more tables (plus any joins). Nothing else happens until the source is defined.
  2. WHERE filters individual rows. Every row that fails the condition is discarded before grouping. Aggregates can't be referenced in WHERE — see step 4.
  3. GROUP BY collapses rows that share the grouped columns into a single row per group. Aggregate functions like COUNT(), SUM() then operate on each group.
  4. HAVING filters groups, not rows. HAVING COUNT(*) > 5 works; WHERE COUNT(*) > 5 does not. This is the single most common beginner mistake in aggregate queries.
  5. SELECT computes the output columns, evaluates functions, and applies AS aliases. Aliases are visible here — which is why you can ORDER BY an alias but not reference it in WHERE.
  6. ORDER BY sorts the result. Alias names from SELECT are available; NULLs sort last by default on ascending order (use NULLS FIRST to override).
  7. LIMIT / OFFSET finally returns a slice of the sorted result. LIMIT 10 OFFSET 20 gives rows 21–30 — the query still computes rows 1–30 internally, which is why deep offsets are slow.
Step 1 / 7
select.sql
SELECT id, name, age FROM users;

SELECT * FROM users WHERE age > 18 AND active = TRUE;

SELECT * FROM users ORDER BY age DESC, name ASC;

SELECT DISTINCT city FROM users;

SELECT * FROM users LIMIT 10 OFFSET 20;

-- expression + alias
SELECT name, age * 12 AS age_in_months FROM users;

-- NULL handling: use IS NULL / IS NOT NULL, not = NULL
SELECT * FROM users WHERE age IS NULL;
SELECT * FROM users WHERE COALESCE(age, 0) > 18;   -- treat NULL as 0

-- BETWEEN, IN, LIKE, ILIKE (case-insensitive)
SELECT * FROM users WHERE age BETWEEN 18 AND 30;
SELECT * FROM users WHERE city IN ('Indore', 'Bhopal');
SELECT * FROM users WHERE name LIKE 'A%';      -- case-sensitive
SELECT * FROM users WHERE name ILIKE 'a%';     -- case-insensitive
⚠️
NULL is not 0, '', or false. NULL means "unknown". Any comparison with NULL returns NULL (which is treated as "not true" by WHERE), so age = NULL is never true. Use IS NULL, IS NOT NULL, and COALESCE(field, fallback). Even NULL = NULL returns NULL — this trips up almost every beginner.
Quick check · 04
Why does SELECT * FROM users WHERE age = NULL return no rows?
The comparison itself doesn't error — it returns NULL, and WHERE NULL excludes the row. Use age IS NULL instead.

Joins

INNER · LEFT · RIGHT · FULL · CROSS · self-join

Joins combine rows from two tables based on a condition. The default is INNER JOIN — only rows that match on both sides survive.

The four join types, drawn with rows← → keys also work

  1. Two tables: users with ids 1–4, posts with author_id values that reference users. Post 13 references 99, which doesn't exist. User 4 has no posts.
  2. INNER JOIN — keeps only rows where a match exists on both sides. Users 1 and 2 have posts; user 3 has a post; user 4 has none, and post 13 has no author. Result: users 1, 2, 3 joined with their posts (3 rows).
  3. LEFT JOIN — keeps all rows from the left table, fills with NULL on the right when there's no match. User 4 appears with NULL post columns. Post 13 is still excluded. Result: 4 rows.
  4. RIGHT JOIN — mirror of LEFT. Post 13 appears with NULL user columns. User 4 is excluded. Result: 4 rows.
  5. FULL OUTER JOIN — keeps both sides, NULLs where either doesn't have a match. User 4 and post 13 both appear with nulls. Result: 5 rows.
  6. CROSS JOIN — every row of the left with every row of the right. 4 users × 4 posts = 16 rows, no condition. Rarely what you want, occasionally exactly what you want (generating combinations, calendar × product pairs).
Step 1 / 6
joins.sql
-- INNER JOIN — only matching rows
SELECT u.name, p.title
FROM users u
JOIN posts p ON p.author_id = u.id;

-- LEFT JOIN — all users, plus their posts if any
SELECT u.name, p.title
FROM users u
LEFT JOIN posts p ON p.author_id = u.id;

-- Users with NO posts: LEFT JOIN + IS NULL
SELECT u.name
FROM users u
LEFT JOIN posts p ON p.author_id = u.id
WHERE p.id IS NULL;

-- Self-join: employees and their managers
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;

Join gotchas you'll be asked about

  • Conditional filter in WHERE on the right table breaks LEFT JOIN. LEFT JOIN posts p ON ... WHERE p.published = true removes users without posts. Move the condition to the ON clause: LEFT JOIN posts p ON p.author_id = u.id AND p.published = true.
  • Multiple joins multiply. A user with 3 posts and 2 comments gives 6 rows if you join both. Aggregate per-join or use subqueries.
  • Always alias tables and qualify columns. u.id, not id, when more than one table might have it. Ambiguous column errors are the second-most-common SQL bug after the NULL comparison.
Quick check · 05
You want every user, along with a count of their posts (0 for users with none). Which join?
INNER JOIN would drop users without posts. LEFT JOIN keeps them. But COUNT(*) counts the null-extended row as 1 — use COUNT(p.id) which ignores nulls, giving 0.

Aggregation — GROUP BY & HAVING

COUNT · SUM · AVG · MIN · MAX · GROUP BY · HAVING · FILTER

agg.sql
-- total users
SELECT COUNT(*) FROM users;

-- users per city
SELECT city, COUNT(*) AS total
FROM users
GROUP BY city;

-- only cities with more than 5 users (filter on the group, not the rows)
SELECT city, COUNT(*) AS total
FROM users
GROUP BY city
HAVING COUNT(*) > 5;

-- AVG ignoring nulls (Postgres does this by default)
SELECT AVG(age), MIN(age), MAX(age) FROM users;

-- FILTER clause — one pass, multiple counts
SELECT
  COUNT(*) FILTER (WHERE active)     AS active_users,
  COUNT(*) FILTER (WHERE NOT active) AS inactive_users
FROM users;

-- round before aggregating if you don't want FLOAT AVG to lose precision
SELECT ROUND(AVG(age), 2) FROM users;
FunctionReturns
COUNT(*)Number of rows (including nulls)
COUNT(col)Number of non-null values in col
COUNT(DISTINCT col)Number of distinct non-null values
SUM(col)Sum (null if all null)
AVG(col)Average of non-nulls — returns NUMERIC for NUMERIC, FLOAT for INT/FLOAT
MIN(col) / MAX(col)Smallest / largest value
STRING_AGG(col, ',')Concatenate values from all rows
ARRAY_AGG(col)Collect all values into an array
💡
SELECT non-aggregated-column requires it to be in GROUP BY. If you select name alongside COUNT(*) without grouping by name, Postgres rejects the query — because there's no single name per group. MySQL (in old modes) allowed it and picked a random row; Postgres is strict, and that's a feature.
Quick check · 06
Why use HAVING COUNT(*) > 5 instead of WHERE COUNT(*) > 5?
WHERE filters rows individually, before grouping — so COUNT(*) is meaningless there. HAVING filters the groups produced by GROUP BY.
08

Subqueries

scalar · IN · EXISTS · correlated · LATERAL

subqueries.sql
-- Scalar subquery: one value
SELECT name FROM users
WHERE age = (SELECT MAX(age) FROM users);

-- IN subquery: value appears in the sub-result
SELECT name FROM users
WHERE id IN (SELECT author_id FROM posts);

-- EXISTS: the subquery returns any row at all (fast with index)
SELECT u.name FROM users u
WHERE EXISTS (
  SELECT 1 FROM posts p WHERE p.author_id = u.id
);

-- Correlated subquery: inner query references outer (usually slow; prefer JOIN)
SELECT u.name, (
  SELECT COUNT(*) FROM posts p WHERE p.author_id = u.id
) AS post_count
FROM users u;

-- LATERAL: subquery can reference columns from earlier FROM items (like a for-each)
SELECT u.name, latest.title
FROM users u
LEFT JOIN LATERAL (
  SELECT title FROM posts p
  WHERE p.author_id = u.id
  ORDER BY created_at DESC LIMIT 1
) latest ON TRUE;
IN vs EXISTS vs JOIN

IN is fine for small sub-results but can be slow if the inner list is huge. EXISTS stops as soon as one match is found — the best choice for "does any row exist" checks. JOIN is best when you need columns from both tables. For a "count of related rows" per parent, LEFT JOIN + GROUP BY usually beats a correlated subquery because the query planner can do a single hash join instead of running the subquery per row.

Quick check · 07
"Get users who have at least one post." Which is generally fastest?
EXISTS stops at the first matching row, and with an index on posts(author_id) it can short-circuit cheaply. IN materialises the entire sub-result.

CTEs — WITH

readable queries · recursive CTEs · materialization

A Common Table Expression (WITH name AS (...)) is a named subquery you can reference later in the query. It exists to make complex queries readable and to reuse intermediate results.

cte.sql
-- Readable pipeline: filter → aggregate → filter again
WITH active_users AS (
  SELECT * FROM users WHERE active = TRUE
),
post_counts AS (
  SELECT author_id, COUNT(*) AS n
  FROM posts
  GROUP BY author_id
)
SELECT u.name, COALESCE(pc.n, 0) AS posts
FROM active_users u
LEFT JOIN post_counts pc ON pc.author_id = u.id;

Recursive CTE — walking hierarchies

A recursive CTE has a base case, UNION ALL, and a recursive step that references the CTE itself. It's how you traverse org charts, comment trees, category hierarchies — anything self-referential.

recursive.sql
-- Find a manager and everyone who reports to them (transitively)
WITH RECURSIVE reports AS (
  -- base: the starting employee
  SELECT id, name, manager_id
  FROM employees
  WHERE id = 1

  UNION ALL

  -- recursive step: children of everyone found so far
  SELECT e.id, e.name, e.manager_id
  FROM employees e
  JOIN reports r ON e.manager_id = r.id
)
SELECT * FROM reports;
💡
CTEs are not automatically "faster". In Postgres 12+, non-recursive CTEs are inlined by default — they behave like subqueries. If you want to force materialization (compute once, reuse), use WITH name AS MATERIALIZED (...). This matters when the CTE does expensive work and is referenced many times.
Quick check · 08
You need to walk an org chart from a CEO down through all reports. What SQL feature?
A recursive CTE handles arbitrary depth. Self-joins only work if you know the max depth in advance — and even then the query is ugly.

Window functions

OVER · PARTITION BY · ROW_NUMBER · RANK · LAG · LEAD · running totals

A window function computes a value across a set of related rows without collapsing them into one row per group the way GROUP BY does. This is the single biggest step from "intermediate SQL" to "advanced SQL" — most interview questions that look hard use window functions.

window.sql
-- Rank users by age within each city — one row per user, plus their rank
SELECT
  name,
  city,
  age,
  RANK() OVER (PARTITION BY city ORDER BY age DESC) AS rank_in_city
FROM users;

-- Running total of order amounts by day
SELECT
  day,
  amount,
  SUM(amount) OVER (ORDER BY day) AS running_total
FROM orders;

-- Previous row's value (LAG) — great for deltas and trends
SELECT
  day,
  amount,
  amount - LAG(amount) OVER (ORDER BY day) AS daily_change
FROM orders;

The comparison set

FunctionWhat it does
ROW_NUMBER()1, 2, 3, ... — no ties, always unique
RANK()1, 2, 2, 4 — ties share rank, then jump
DENSE_RANK()1, 2, 2, 3 — ties share rank, no jump
LAG(col, n)Value from n rows before
LEAD(col, n)Value from n rows after
FIRST_VALUE() / LAST_VALUE()First / last value in the window
NTILE(n)Split into n roughly equal buckets
SUM/AVG/COUNT/MIN/MAX OVER ()Aggregate without collapsing rows
The classic "top N per group" query

Get the 2 highest-paid employees per department. Window functions make it trivial:

SELECT * FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn FROM employees) t WHERE rn <= 2;

This pattern is the thing that separates basic SQL from advanced — you'll be asked it, or a variation, in almost every data-heavy interview.

Quick check · 09
What's the difference between GROUP BY and PARTITION BY in a window function?
After GROUP BY city, you have one row per city. After PARTITION BY city in a window function, you still have every row — with an extra column giving the aggregate or rank relative to the city.

Transactions & isolation

BEGIN · COMMIT · ROLLBACK · isolation levels · locking

transaction.sql
BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;

-- if everything was fine
COMMIT;

-- if something failed
ROLLBACK;

The four isolation levels

LevelPreventsAllows
READ UNCOMMITTED—Dirty reads, non-repeatable reads, phantom reads
READ COMMITTED (default)Dirty readsNon-repeatable reads, phantom reads
REPEATABLE READDirty + non-repeatablePhantom reads

setting isolation per transaction
BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ... statements ...

What each problem means

Dirty read — reading another transaction's uncommitted change (which might roll back).

Non-repeatable read — you read the same row twice and get different values because someone committed in between.

Phantom read — you run the same query twice and get different rows because someone inserted/deleted between them.

Postgres implements REPEATABLE READ as a snapshot — no phantom reads even though the SQL standard allows them. In practice, its REPEATABLE READ behaves like most databases' SERIALIZABLE.

💡
Postgres uses MVCC. Readers never block writers, and writers never block readers. Each transaction sees a consistent snapshot of the data. The trade-off: dead rows accumulate and VACUUM reclaims them. Under heavy write load, autovacuum is not a footgun — disabling it is.
Quick check · 10
What is Postgres's default isolation level?
SERIALIZABLE would be safest but slowest; it's opt-in per transaction. Default is READ COMMITTED. For operations where two reads in one transaction must be consistent, raise the level explicitly.

Indexes — the whole toolbox

B-tree · composite · partial · expression · GIN · GiST · BRIN · covering

An index is a sorted data structure that lets Postgres find rows without scanning the whole table. The B-tree is the default and the one you'll create 90% of the time. But Postgres has specialised indexes for specialised data.

index.sql
-- standard B-tree
CREATE INDEX idx_users_email ON users (email);

-- composite — column order matters (use left-to-right like a phone book)
CREATE INDEX idx_users_city_age ON users (city, age);

-- unique index
CREATE UNIQUE INDEX idx_users_email_unique ON users (email);

-- partial index — only index rows that matter
CREATE INDEX idx_users_active ON users (city) WHERE active = TRUE;

-- expression index — index the result of an expression
CREATE INDEX idx_users_lower_email ON users (LOWER(email));

-- covering index — includes extra columns so the query can be satisfied from the index alone
CREATE INDEX idx_users_email_name ON users (email) INCLUDE (name);

Specialised index types

IndexForExample
B-treeEquality, range, sort, prefix (default)WHERE age > 18, ORDER BY created_at
GINArrays, JSONB, full-text search, trigramWHERE tags @> ARRAY['node']
GiSTGeometric, ranges, nearest-neighbour (with PostGIS)WHERE location <-> point
BRINVery large tables with naturally ordered data (timestamps)WHERE created_at >= '2024-01-01' on billions of rows
hashEquality only — smaller than B-tree, no orderingWHERE uuid = ...
Composite index order

An index on (city, age) helps queries filtering by city, or by city AND age. It does not help a query filtering only by age — that's the left-prefix rule, same as MongoDB's compound indexes. Order the columns by equality first, then range, then sort, matching your hottest queries.

⚠️
Every index costs on writes. Each INSERT, UPDATE, and DELETE must update every index on the table. A write-heavy table with 15 indexes is slow to write and expensive on storage. Use indexes where they earn their keep; check pg_stat_user_indexes for indexes with zero idx_scan and consider dropping them.
Quick check · 11
You have a query WHERE city = 'Indore' AND age > 25. Which composite index is best?
With (city, age), Postgres can seek to the Indore block and range-scan age inside it. With (age, city), the age values are scattered across cities — much less efficient, and useless for queries filtering only on city.

Views, materialized views & triggers

saved queries · refresh · row-level triggers

Views

views.sql
-- a view is a saved query — it re-runs every time you select from it
CREATE VIEW active_users AS
  SELECT id, name, email FROM users WHERE active = TRUE;

SELECT * FROM active_users;

-- materialized view — data is physically stored; you must REFRESH it
CREATE MATERIALIZED VIEW user_post_counts AS
  SELECT u.id, u.name, COUNT(p.id) AS post_count
  FROM users u
  LEFT JOIN posts p ON p.author_id = u.id
  GROUP BY u.id, u.name;

REFRESH MATERIALIZED VIEW user_post_counts;    -- re-compute

Triggers

A trigger is a function that Postgres runs automatically in response to INSERT, UPDATE, or DELETE on a table.

trigger.sql
-- auto-update a column on every UPDATE
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_users_updated_at
BEFORE UPDATE ON users
FOR EACH ROW
EXECUTE FUNCTION set_updated_at();
Quick check · 12
When is a materialized view's data recalculated?
That's the whole trade-off — the data is fast because it's stored, but it's only as fresh as the last refresh. Use a regular view when freshness matters more than speed.

JSONB — semi-structured data in a relational world

-> vs ->> · containment · GIN indexing

Postgres lets you store JSON directly in a column with full query capability. Use it when part of your schema is genuinely dynamic (feature flags, plugin settings, event payloads) — not as an excuse to skip schema design.

jsonb.sql
CREATE TABLE products (
  id      SERIAL PRIMARY KEY,
  name    TEXT NOT NULL,
  attrs   JSONB
);

INSERT INTO products (name, attrs) VALUES
  ('Shirt', '{"color":"red","size":"M","price":599}'),
  ('Phone', '{"brand":"Nike","ram":8,"price":29999}');

-- ->> returns TEXT, -> returns JSONB
SELECT name, attrs ->> 'color' AS color FROM products;

-- filter
SELECT * FROM products WHERE attrs ->> 'brand' = 'Nike';

-- containment — matches if attrs contains all the given keys/values
SELECT * FROM products WHERE attrs @> '{"color":"red"}';

-- numeric cast inside a JSON path
SELECT * FROM products WHERE (attrs ->> 'price')::INT > 1000;

-- GIN index makes containment fast
CREATE INDEX idx_products_attrs ON products USING GIN (attrs);
⚠️
Don't use jsonb as a schema escape hatch. If a field is queried, filtered, or sorted consistently, it should be a real column with a real type and a real index. JSONB is for genuinely flexible data — feature flags, plugin configs, event payloads. Columns you constantly extract with ->> want to be real columns.

EXPLAIN — read the planner's mind

EXPLAIN ANALYZE · seq scan vs index scan · rows · cost · buffers

Every performance question about Postgres starts here. EXPLAIN ANALYZE runs the query and shows the plan with real timing and row counts.

explain.sql
EXPLAIN ANALYZE
SELECT * FROM users WHERE email = 'aarav@x.com';

-- typical output:

--   Index Cond: (email = 'aarav@x.com')
-- Planning Time: 0.050 ms
-- Execution Time: 0.040 ms
NodeWhat it means
Seq ScanReads every row. Fine for small tables, bad for large. If you see this on a large table for a selective query, add an index.
Index ScanUses an index to find rows, then fetches each row from the table. Fast for selective filters.
Index Only ScanAll required data is in the index — no table fetch. Fastest for covered queries.
Bitmap Heap ScanIndex found many candidate pages; fetch them in physical order. Good when many rows match.
Hash JoinBuilds a hash of the smaller side, probes with the larger. Fast for equality joins on large tables.
Nested LoopFor each outer row, look up matches in the inner. Fast when the outer side is small.
Sort / HashAggregateSorts or groups. Watch for high cost here — often fixed by an index that pre-sorts.
The three numbers to read first

rows — estimated vs actual. If wildly off, stats are stale; run ANALYZE table_name.
Execution Time — total. Anything over ~100ms on a user-facing query is worth attention.
Buffers — EXPLAIN (ANALYZE, BUFFERS) shows shared vs disk reads. High "read" vs "hit" means the data isn't cached.

Quick check · 13
You see Seq Scan on a 10-million-row table for WHERE email = '...'. What is likely wrong?
Two likely causes: no index, or stale statistics. First add the index; if the plan doesn't change, run ANALYZE users and check the row estimates.

Replication, backup & operations

streaming replication · pg_basebackup · pg_dump · pooling

Streaming replication

Postgres supports streaming replication: a primary continuously sends its write-ahead log (WAL) to one or more replicas. Replicas apply WAL to stay in sync. A replica can be hot standby (readable) — you can route read-heavy workloads to it. Failover is usually managed by an external tool (Patroni, repmgr, or a managed service) — Postgres itself does not auto-failover.

backup & restore
# logical backup of a database
pg_dump -Fc -d shop > shop.dump

# restore
pg_restore -d shop_new shop.dump

# physical backup of a whole cluster (for replicas, disaster recovery)
pg_basebackup -D /backup/data -h primary -U replicator -X stream

Connection pooling matters

Every Postgres connection is a real OS process (~5–10 MB). Hundreds of clients each opening a connection will exhaust the server. Use a pooler:

  • pgBouncer (external) — transaction-level pooling, the industry standard.
  • Node-level — the pg package's Pool, or the pool built into your ORM.
  • Managed — most managed Postgres services (Neon, Supabase, RDS Proxy) provide a pooler endpoint.
Quick check · 14
Why use a connection pooler like pgBouncer in front of Postgres?
Poolers don't rewrite queries. They manage the lifecycle of connections — reuse, queue, and enforce a max — so 500 app workers can share 20 real DB connections.

Postgres in Node / Express

pg · parameterized queries · pooling · transaction helper

db.js
import pg from 'pg';

export const pool = new pg.Pool({
  connectionString: process.env.DATABASE_URL,
  max: 20,               // never exceed the DB's max_connections
  idleTimeoutMillis: 30_000,
});

// helper for transactions
export async function withTransaction(fn) {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK');
    throw err;
  } finally {
    client.release();
  }
}
routes/users.js
import express from 'express';
import { pool } from '../db.js';

const router = express.Router();

router.get('/', async (req, res) => {
  const { rows } = await pool.query(
    'SELECT id, name, email FROM users ORDER BY id'
  );
  res.json(rows);
});

router.get('/:id', async (req, res) => {
  // $1 is a parameter — NEVER string-concatenate user input
  const { rows } = await pool.query(
    'SELECT id, name, email FROM users WHERE id = $1',
    [req.params.id]
  );
  if (rows.length === 0) return res.status(404).json({ message: 'Not found' });
  res.json(rows[0]);
});
⚠️
Never concatenate user input into SQL strings. "SELECT * FROM users WHERE name = '" + name + "'" is SQL injection. Always use parameterized queries ($1, $2, …, with the values as an array). The driver quotes and escapes them safely — no exceptions.
Quick check · 15
Why does pool.query('SELECT * FROM users WHERE id = $1', [id]) protect against SQL injection?
Parameterised queries keep the query text and the data separate. Even if the value is '; DROP TABLE users; --, it's treated as one string value in a column comparison — not as SQL.

Interview questions

the ones you'll actually be asked

Q1What is the difference between a primary key, a unique key, and a foreign key?

A primary key uniquely identifies rows in a table (unique + not null; one per table). A unique key also prevents duplicates but allows nulls and you can have many per table. A foreign key declares that a column's value must exist in another table's primary/unique key — enforcing referential integrity.

Q2INNER JOIN vs LEFT JOIN — and what's the difference between WHERE p.published = true and ON ... AND p.published = true?

INNER JOIN keeps only rows where both sides match. LEFT JOIN keeps all left rows, filling the right with nulls when there's no match.
Putting a filter on the right table in WHERE turns a LEFT JOIN into an INNER JOIN — rows where the right side is null fail the filter and disappear. Putting the same filter in the ON clause keeps those left rows with nulls (the right table simply doesn't match). The difference decides whether parents without children appear in your result.

Q3GROUP BY vs PARTITION BY?

GROUP BY collapses rows — you get one row per group. PARTITION BY (used inside OVER () for window functions) computes an aggregate or rank across the partition while keeping every original row. Use GROUP BY when you want summaries; use PARTITION BY when you want each row annotated with the aggregate it belongs to (running totals, ranks, per-group deltas).

Q4What's a CTE, and when would you use one instead of a subquery?

A CTE (WITH name AS (...)) is a named subquery that makes complex queries readable and lets you reference the same intermediate result multiple times. Use one when a query has multiple stages (filter → aggregate → rejoin) or when you need recursion. Since PG12, non-recursive CTEs are inlined like subqueries; use MATERIALIZED if you want to force computation once.

Q5How does EXISTS differ from IN, and which is faster?

IN compares each outer value against a materialised list of inner values — inefficient when the inner list is large. EXISTS runs a correlated check per outer row and stops at the first match; with an index on the inner column it short-circuits quickly. For "does any matching row exist" checks, EXISTS is usually faster. For small, fixed lists (e.g. IN ('a','b','c')), IN is fine.

Q6Explain ACID and Postgres's default isolation level.

Atomicity — a transaction is all-or-nothing. Consistency — constraints are maintained. Isolation — concurrent transactions don't see each other's uncommitted work. Durability — committed data survives crashes. Postgres's default is READ COMMITTED — each statement sees a snapshot at its start, so you can't get dirty reads, but the same row can change between two statements in a transaction. Raise to REPEATABLE READ or SERIALIZABLE for stronger guarantees.

Q7What is MVCC, and how does it enable non-blocking reads?

Multi-Version Concurrency Control. When a row is updated, Postgres writes a new version and marks the old one as expired. Each transaction sees the version that was current when its snapshot was taken. So a reader never waits for a writer, and a writer never waits for a reader. Expired versions are reclaimed by VACUUM (usually autovacuum) — this is why long-running transactions cause bloat.

Q8How would you find the top 3 highest-paid employees per department?

Use a window function: SELECT * FROM (SELECT *, ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn FROM employees) t WHERE rn <= 3; — ROW_NUMBER gives each row a rank within its department; the outer WHERE keeps the top three per group. Use RANK() instead if you want ties to be included.

Q9What is a covering index, and when does it help?

An index that contains every column a query needs — either as indexed columns or via INCLUDE. When Postgres can satisfy the query entirely from the index, it does an Index Only Scan and never touches the heap. Dramatic win for read-heavy queries on big tables. The cost is a larger index that must be updated on every write.

Q10When would you choose a composite index vs two single-column indexes?

When your query filters (or filters + sorts) on both columns together, a composite index on (a, b) allows an efficient combined seek and pre-sorts by b within a. Two separate indexes on a and b force Postgres to do a bitmap intersection, which is usually slower. Rules: composite order matters (equality first, range after); a composite index also covers queries on its leading column, so (a, b) makes (a) redundant — but not (b).

Q11What are partial and expression indexes?

A partial index only indexes rows matching a filter (WHERE active = TRUE) — smaller, faster to write, ideal for skewed data. An expression index indexes the result of an expression (LOWER(email), (data->>'status')) — useful when queries filter on a computed value. Combine both: CREATE INDEX ... ON users (LOWER(email)) WHERE active.

Q12How do you read EXPLAIN ANALYZE?

Look at: (1) node types — a Seq Scan on a large table is usually the problem; (2) rows — estimated vs actual, if wildly off run ANALYZE; (3) buffers with EXPLAIN (ANALYZE, BUFFERS) to see cache hits vs disk; (4) Execution Time; (5) loops — a nested loop with loops=N means the inner plan ran N times; that's where slowdowns hide.

Q13What is VACUUM and why does Postgres need it?

Because MVCC keeps old row versions around for transactions with older snapshots, dead tuples accumulate. VACUUM reclaims that space (marks it reusable), and VACUUM FULL actually rewrites the table (locks it, so avoid during traffic). autovacuum handles this in the background; disabling it causes bloat, then slower queries, then outages. It also updates the visibility map, which is what makes Index Only Scans possible.

Q14How do you do pagination efficiently?

LIMIT/OFFSET is easy but scales badly — offsetting 100,000 rows still computes rows 1–100,000 first. Use keyset pagination: fetch rows after a known last-seen value, WHERE created_at < $lastSeen ORDER BY created_at DESC LIMIT 20. With an index on (created_at), each page is a single index seek. The trade-off: you can't jump to page 500 directly — fine for infinite-scroll UIs, not for page-number UIs.

Q15How would you debug a slow query?

1) Find slow queries via pg_stat_statements (mean/total time) or the log_min_duration_statement setting. 2) EXPLAIN (ANALYZE, BUFFERS) to see the plan and where time is spent. 3) Check for Seq Scans on large tables, missing or unused indexes, and rows estimates that are far off. 4) Look for correlated subqueries or N+1 patterns. 5) Consider rewriting joins, adding covering indexes, using CTEs to separate stages, or materializing aggregates. 6) Verify the fix by re-running EXPLAIN and comparing actual times.

Q16What's the difference between pg_dump and pg_basebackup?

pg_dump produces a logical backup (SQL statements or a custom format) of one database — portable across versions, easy to restore into a new cluster. pg_basebackup takes a physical, byte-for-byte copy of the data directory — used to bootstrap replicas and for full-cluster disaster recovery. Combine physical backups with WAL archiving for point-in-time recovery.

Q17What is a materialized view, and when would you use one?

A view whose result is stored physically. You must REFRESH MATERIALIZED VIEW (or set up CONCURRENTLY with a unique index) to update it. Use it for expensive aggregations that don't need to be real-time — dashboards, leaderboards, daily reports. For live data, use a regular view.

Q18How does JSONB differ from JSON, and when would you use it?

JSON stores the text verbatim; JSONB parses and stores in a binary format, so it's indexable (with GIN), supports containment (@>), and is faster to query. Use JSONB for genuinely dynamic data (feature flags, plugin config, event payloads). If you find yourself ->>-ing the same field in every query, promote it to a real column.

Q19How does Postgres prevent SQL injection?

It doesn't — the application has to. Postgres itself is just a database; the injection happens in string interpolation of SQL. The driver (pg, Prisma, Knex, etc.) provides parameterized queries ($1, $2) that send the query text and values separately, so the values can never be parsed as SQL. Never concatenate user input. Use an ORM or query builder, or use parameterized queries directly.

Q20Postgres vs MongoDB — when would you choose each?

Postgres when the data is relational, the schema is stable, you need strong consistency, complex joins, ACID transactions across entities, or SQL's expressive power (window functions, CTEs, aggregations). MongoDB when the data is hierarchical, the schema is genuinely flexible, you're storing documents that map directly to your API shape, or you need horizontal write scale via sharding. Many modern teams use both: Postgres as the source of truth, MongoDB for specific document-shaped needs (or Postgres + JSONB and skip Mongo entirely).
