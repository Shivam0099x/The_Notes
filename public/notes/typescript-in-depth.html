01

What TypeScript is

a superset · compiled, not interpreted · erased

  • TypeScript = JavaScript + a static type system. Every valid JS file is already valid TS.
  • You write .ts (or .tsx for JSX), the TypeScript compiler (tsc) checks it, then produces plain .js.
  • The compiler strips out types — the browser never sees them. Types are a compile-time tool, not a runtime one.
  • TypeScript is developed by Microsoft, first released in 2012, and is now the default for serious JS projects and the entire React/Next/Node ecosystem.
  • Everything runs in the JS runtime (V8, Node, Deno, Bun). TS itself is not a runtime.
The one sentence

TypeScript is JavaScript with types — you get the compiler to check your code before it runs, and the browser gets plain JavaScript after it's done.

02

Why TypeScript

the problems it actually solves

  • Catch bugs at compile time. user.nmae (typo) → error before you ship. user.name.toUpperCase() when name is null → error before you ship.
  • Autocomplete and refactoring. The editor knows the shape of every object, so it can suggest methods, rename safely, and jump to definitions across a monorepo.
  • Self-documenting code. A typed function signature tells you what goes in and what comes out — without reading its body.
  • Confident refactoring. Rename a function parameter; the compiler finds every caller that breaks. Without types you'd find out at runtime.
  • Team safety. When you change an API contract, TS rejects every consumer that hasn't been updated.
  • Runtime-safe data. Pair with Zod and you can validate external input, then trust the resulting type.
⚠️
TypeScript does not fix runtime data. If the API returns the wrong shape, TS can't know — it trusts you. That's why runtime validation (Zod, io-ts) exists at the boundary. TS prevents you from making type mistakes; it doesn't prevent the world from sending garbage.

How the compiler works

  1. Parse — turn .ts into an AST (abstract syntax tree).
  2. Type-check — walk the AST, resolve types, and report errors. This is where tsc spends its time.
  3. Emit — strip types, transform some modern syntax, and write .js output.
💡
In real projects, Vite/webpack/Next handle the build. They use esbuild or swc to transpile TS without type-checking (fast), and run tsc --noEmit in CI for the actual type check (thorough). Best of both: fast dev loop, complete type safety at build time.
⚠️
Turn on strict on day one. Enabling it later on an existing codebase is a wall of possibly undefined errors. strict enables strictNullChecks, noImplicitAny, and several other checks that make TS behave the way most people expect.

Basic types

string · number · boolean · bigint · symbol · undefined · null · void · any · unknown · never · enums · arrays · tuples

basics.ts
let name: string     = 'Aarav';
let age: number      = 22;
let active: boolean  = true;
let big: bigint      = 123n;
let sym: symbol      = Symbol('id');
let u: undefined   = undefined;
let n: null        = null;

// void — used as a function return type when there's nothing to return
function log(msg: string): void {
  console.log(msg);
}

// any — disables the type checker
let anything: any = 'text';
anything.toUpperCase();    // no check
anything.nonExistent();    // no check — will crash at runtime

// unknown — the safe version of any
let unknownValue: unknown = 'text';
if (typeof unknownValue === 'string') {
  unknownValue.toUpperCase();   // now allowed — narrowed
}

// never — this value can never exist
function fail(msg: string): never {
  throw new Error(msg);
}

// arrays
let nums: number[]              = [1, 2, 3];
let names: Array<string>        = ['Aarav'];

// tuples — fixed length, fixed types per position
let point: [number, number] = [10, 20];

// enums
enum Role { Admin = 'ADMIN', User = 'USER' }
let r: Role = Role.Admin;

// literal union — often better than enums
type Status = 'pending' | 'active' | 'deleted';
TypeWhat it means
any"Trust me" — disables checks on this value
unknown"Could be anything, narrow before use" — the safe any
never"This value can never happen" — used for exhaustive checks, functions that throw
voidReturn type of a function that returns nothing
undefinedThe absence of a value (variable never assigned, function returned nothing)
nullThe intentional absence of a value
bigintArbitrary-precision integers — 123n
symbolUnique identifier — Symbol('id')
⚠️
any vs unknown. Prefer unknown for external data (fetch responses, JSON.parse, catch clauses). any turns off the checker everywhere it flows; unknown forces you to narrow it. In a real codebase, any should be rare — the linter rule @typescript-eslint/no-explicit-any exists for a reason.
Quick check · 01
What type should catch (err) have in strict mode?
In JS, throw can throw anything — a string, a number, an object. unknown forces you to check err instanceof Error before accessing .message. In TS 4.4+, catch clauses default to unknown in strict mode.

Type inference & type assertions

what TS figures out · as · satisfies

  • Inference — TS guesses the type from the value. let x = 10 → number. const y = 'hi' → 'hi' (literal). const arr = [1, 2, 3] → number[].
  • Best practice: annotate function parameters and exported return types. Let TS infer local variables.
  • Assertion (as) — tell TS "trust me, this is what the type is" without changing the runtime value.
  • satisfies (TS 4.9+) — checks the value against a type without changing its inferred type.
inference.ts
let a = 'hello';         // inferred: string
const b = 'hello';       // inferred: 'hello' (literal)
let c = [1, 2, 3];     // inferred: number[]
let d = { name: 'A' };    // inferred: { name: string }

// Type assertion
const input = document.getElementById('email') as HTMLInputElement;
input.value;   // now has .value

// satisfies — check the shape WITHOUT widening the type
type Config = { port: number; host: string };

const config = {
  port: 3000,
  host: 'localhost',
} satisfies Config;
// type of config.port is STILL 3000, not number — but it was validated
⚠️
Assertions are the last resort. x as SomeType silences the checker. If the value wasn't actually SomeType, the bug is still there — just hidden. Use assertions for cases where you truly know more than the compiler (DOM, external libs), not as a way to make errors go away. Prefer satisfies when you want to check without changing the type.

Union types

A | B · optional interaction with nullable

unions.ts
// a value that could be any one of these types
let id: string | number;
id = 'abc';    // ok
id = 42;       // ok
// id = true;  ❌ not allowed

// union with null — extremely common
function greet(name: string | null) {
  if (name === null) return 'Hello, guest';
  return `Hello, ${name}`;    // TS knows name is string here
}

// union of literals
type Status = 'pending' | 'active' | 'deleted';

// union of objects
type Shape = { kind: 'circle'; r: number } | { kind: 'square'; side: number };
⚠️
You can only use operations that are valid on every member of the union. string | number has .toUpperCase() on strings and .toFixed() on numbers — neither works on both, so neither is allowed until you narrow. That's the point: a union is a promise that you'll check before doing anything type-specific.
08

Type narrowing

typeof · instanceof · in · discriminated unions · exhaustiveness

  • typeof — narrows primitives. typeof x === 'string' → string.
  • instanceof — narrows class instances.
  • in — narrows by checking a property exists.
  • Equality — x === 'error' narrows a union of literals.
  • Truthiness — if (x) removes null, undefined, '', 0, false.
  • Discriminated unions — objects with a shared literal field. Checking it narrows the whole shape.
narrowing.ts
// typeof
function fmt(x: string | number) {
  if (typeof x === 'string') return x.toUpperCase();   // x: string
  return x.toFixed(2);                              // x: number
}

// instanceof
function fmtDate(x: Date | string) {
  if (x instanceof Date) return x.toISOString();
  return x.toUpperCase();
}

// discriminated union — the killer pattern
type Result =
  | { status: 'loading' }
  | { status: 'success'; data: string }
  | { status: 'error'; message: string };

function render(r: Result) {
  switch (r.status) {
    case 'loading': return '…';
    case 'success': return r.data;      // r has .data here
    case 'error':   return r.message;   // r has .message here
  }
}

// exhaustiveness — the compiler flags missing cases
function assertNever(x: never): never {
  throw new Error(`Unhandled: ${x}`);
}
💡
The assertNever trick. Adding a new member to a union should break every switch that forgets it. Put assertNever(x) in the default branch and the compiler enforces exhaustiveness for free.

Interfaces & type aliases

when to use which · intersection types

interfaces.ts
// interface — object shape
interface User {
  id: number;
  name: string;
  email?: string;         // optional
}

// interface can extend
interface Admin extends User {
  permissions: string[];
}

// type alias — any type, not just objects
type Status = 'pending' | 'active' | 'deleted';
type Id     = string | number;
type Mapper = (x: number) => string;

// intersection — combine types with &
type Admin2 = User & { permissions: string[] };
interfacetype
Object shapeYesYes
Union / intersectionNoYes
Primitives, tuples, mapped typesNoYes
Declaration mergingYes (same name, multiple declarations)No
Extendextends& intersection
Implements (by a class)YesYes
Rule of thumb

Use interface for object-shaped contracts you might extend or augment (public APIs, service shapes, model schemas). Use type for everything else — unions, intersections, function types, tuples, mapped types. Both work day to day; the difference shows up in declaration merging and library extension.

⚠️
Intersection is not "or". A & B means the value must satisfy both A and B — combining their properties. If A has name: string and B has name: number, A & B requires a value where name is both — impossible. For "one or the other", use a union |.

Optional fields

? · undefined vs null · readonly

optional.ts
interface User {
  id: number;
  name: string;
  email?: string;         // optional — may be undefined or missing
  readonly createdAt: Date; // cannot be reassigned after creation
}

const u: User = { id: 1, name: 'Aarav', createdAt: new Date() };

// Optional fields need checking before use
u.email.toUpperCase();             ❌ possibly undefined
u.email?.toUpperCase();            ✓ optional chaining
u.email?.toUpperCase() ?? 'none'; ✓ fallback

// readonly is a compile-time guarantee, not runtime immutability
u.createdAt = new Date();       ❌ compile error
// but (u as any).createdAt = ...
//     would still work at runtime
⚠️
? means undefined, not null. An optional field is T | undefined. If the API may return null, write email?: string | null. Don't conflate them — email?.toUpperCase() handles undefined but would still throw on null.

Functions

declarations · arrows · optional/default/rest · function types · interfaces for functions · callbacks

functions.ts
// function declaration
function add(a: number, b: number): number {
  return a + b;
}

// arrow function — expression
const double = (n: number): number => n * 2;

// arrow function — statement block
const greet = (name: string): string => {
  const msg = `Hi ${name}`;
  return msg;
};

// optional, default, rest parameters
function describe(
  name: string,
  title?: string,             // optional
  age: number = 0,             // default
  ...tags: string[]           // rest
): string {
  return `${title ?? ''} ${name}, ${age}, ${tags.join(',')}`.trim();
}

// function type
type Adder = (a: number, b: number) => number;
const sum: Adder = (a, b) => a + b;

// interface for an object with methods
interface Calculator {
  add(a: number, b: number): number;
  subtract(a: number, b: number): number;
}

const calc: Calculator = {
  add: (a, b) => a + b,
  subtract: (a, b) => a - b,
};

// callback types
function process(items: number[], cb: (n: number) => void) {
  items.forEach(cb);
}
💡
Return types are optional but recommended on exported functions. TS infers the return type from the body, but if you later change the body, the inferred return type changes silently. Annotating the return type makes the intent explicit and catches accidental changes.

Classes & access modifiers

fields · constructor · public/private/protected/readonly · parameter properties · static

  • public (default) — accessible anywhere.
  • private — only inside the class. Compile-time only.
  • protected — inside the class and its subclasses.
  • readonly — can be assigned at declaration or in constructor, never after.
  • Parameter properties — TS shorthand: constructor(public name: string) creates a field and assigns it automatically.
  • #field — real JS privacy, enforced at runtime.
class.ts
class Account {
  static count = 0;              // shared across instances
  readonly id: string;             // set once, then locked
  private balance = 0;            // compile-time private
  #pin: string;                    // runtime-private

  constructor(public owner: string, pin: string) {
    this.id = crypto.randomUUID();
    this.#pin = pin;
    Account.count++;
  }

  deposit(amount: number) {
    if (amount <= 0) throw new Error('Must be positive');
    this.balance += amount;
  }

  getBalance(): number {
    return this.balance;
  }

  static createEmpty(): Account {
    return new Account('guest', '0000');
  }
}

const acc = new Account('Aarav', '1234');
acc.deposit(100);
console.log(acc.owner);                 // from parameter property
// acc.balance;   ❌ private
// acc.#pin;      ❌ syntax error
console.log(Account.count);            // static access
⚠️
private is compile-time only. At runtime the field still exists on the object and can be reached with (obj as any).balance or reflection. Use #balance for genuine runtime privacy — the engine itself enforces it.

Generics

type parameters · constraints · defaults · generic classes and interfaces

  • Generics let you write code that works for any type while preserving the relationship between input and output.
  • function identity<T>(x: T): T — the returned value has the same type as the argument, whatever that was.
  • Constraints (T extends { length: number }) force T to have a certain shape.
  • Defaults (T = string) provide a fallback when the type isn't given.
generics.ts
// basic generic
function first<T>(arr: T[]): T | undefined {
  return arr[0];
}

// multiple type parameters
function pair<A, B>(a: A, b: B): [A, B] {
  return [a, b];
}

// constraint
function longest<T extends { length: number }>(a: T, b: T): T {
  return a.length >= b.length ? a : b;
}

// default type parameter
interface ApiResponse<T = unknown> {
  data: T;
  ok: boolean;
}

// generic class
class Repo<T extends { id: string }> {
  private items: Map<string, T> = new Map();

  save(item: T) { this.items.set(item.id, item); }
  find(id: string): T | undefined { return this.items.get(id); }
}
⚠️
Don't over-genericize. If a function only ever works for strings, don't make it <T>. Generics add complexity; they earn it only when the type relationship actually matters. function map<T, U>(arr: T[], fn: (x: T) => U): U[] earns it — the output element type depends on the callback.

Literal types

exact values as types · as const

literals.ts
let direction: 'up' | 'down' | 'left' | 'right';
direction = 'up';        // ok
// direction = 'forward';  ❌

// as const — freeze the literal types
const config = {
  method: 'POST',
  retries: 3,
} as const;
// type of config.method is now 'POST', not string

// classic: a roles array as a const tuple
const ROLES = ['admin', 'user', 'guest'] as const;
type Role = typeof ROLES[number];    // 'admin' | 'user' | 'guest'
💡
Literal types are how you build real domain types. A Status, a Role, an HTTPMethod — all better expressed as literal unions than as loose strings. They give you autocomplete, exhaustive switch checks, and compile-time rejection of invalid values.

Type guards

custom guards · user-defined is predicates · asserts

  • A type guard is a function whose return type is a type predicate: x is T.
  • When it returns true, TS narrows the argument's type inside the calling scope.
  • asserts x is T — an assertion function. It either throws or narrows.
guards.ts
interface Cat { meow(): void; whiskers: number }
interface Dog { bark(): void; breed: string }

// type predicate
function isCat(x: Cat | Dog): x is Cat {
  return 'meow' in x;
}

function handle(pet: Cat | Dog) {
  if (isCat(pet)) pet.meow();       // pet: Cat
  else pet.bark();                    // pet: Dog
}

// assertion function — narrows or throws
function assertIsString(x: unknown): asserts x is string {
  if (typeof x !== 'string') throw new Error('Not a string');
}

function upper(x: unknown) {
  assertIsString(x);
  return x.toUpperCase();             // x is now string
}
⚠️
A type guard is only as good as its logic. If your predicate says x is User but only checks x != null, TS will narrow — but at runtime x might not be a User. Guards must actually verify the shape. This is why runtime validation (Zod) pairs so well: it can produce a real guard that also validates.

The keyof operator

keys as types · indexed access · safe accessors

keyof.ts
interface User { id: number; name: string; email: string }

type UserKey = keyof User;             // 'id' | 'name' | 'email'

// safe property accessor
function get<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const u: User = { id: 1, name: 'Aarav', email: 'a@x.com' };
const n = get(u, 'name');              // inferred: string
// get(u, 'age');    ❌ 'age' is not a key of User

// keyof + typeof — get keys from a runtime object's type
const config = { host: 'localhost', port: 3000 };
type ConfigKey = keyof typeof config;   // 'host' | 'port'

// mapped type — transform every key
type Nullable<T> = { [K in keyof T]: T[K] | null };
💡
keyof + generics is the pattern behind every safe library. Type-safe object pickers, sort-by-field helpers, form libraries — they all use K extends keyof T so that invalid field names are caught at compile time.

Index signatures

dynamic keys · combining fixed and dynamic fields

index-signatures.ts
// an object whose keys you don't know at compile time
interface Scoreboard {
  [player: string]: number;
}

const scores: Scoreboard = {
  aarav: 10,
  priya: 20,
  neha:  30,
};

// Records do the same thing but cleaner
type Scoreboard2 = Record<string, number>;

// Fixed keys + dynamic keys — index signature must accept the fixed ones too
interface WithMeta {
  id: string;
  [key: string]: string;   // id must be a string, other keys are string→string
}

// Constrain key names with a pattern (TS 4.4+)
interface Strict {
  [k: `data-${string}`]: string;
}
⚠️
Index signatures silently allow any key. scores['nonexistent'] is typed as number even though the key isn't there. Enable noUncheckedIndexedAccess in tsconfig to force number | undefined — the correct behaviour for anything not statically known.

Modules & namespaces

ESM · import type · why namespaces are legacy

modules.ts
// named exports
export function add(a: number, b: number) { return a + b; }
export const PI = 3.14159;

// default export
export default class Calculator { /* ... */ }

// imports
import { add, PI } from './math';
import Calculator from './calculator';

// import type — erased at compile time, no runtime cost
import type { User } from './types';

// re-export
export * from './utils';
export { add as sum } from './math';

// namespace — old way, avoid in new code
namespace Math {
  export const PI = 3.14159;
  export function add(a: number, b: number) { return a + b; }
}
Math.PI;
⚠️
Namespaces are legacy. They predate ES modules. Modern code uses ES import/export exclusively. Namespaces only appear in older code and in d.ts declaration files for legacy global libraries.

Decorators

class · method · property · parameter · legacy vs standard

  • A decorator is a function that wraps a class, method, property, or parameter to modify its behaviour.
  • Common in Angular, NestJS, TypeORM. Less common in React/Express codebases.
  • Two systems exist: legacy (experimental stage-2) and standard (stage-3, TS 5+). They're incompatible. Modern projects should use standard decorators.
decorators.ts
// legacy decorator example (experimentalDecorators: true)
function log(target: any, key: string, desc: PropertyDescriptor) {
  const original = desc.value;
  desc.value = function (...args: any[]) {
    console.log(`calling ${key}`, args);
    return original.apply(this, args);
  };
  return desc;
}

class Service {
  @log
  fetchUsers(limit: number) { /* ... */ }
}
💡
You don't need decorators for React. They're for framework-heavy backends (NestJS, Angular) and ORMs (TypeORM, MikroORM). In a typical Express or React codebase, you'll go years without writing one. Learn them, but don't force them into places they don't help.

Async programming

Promise types · async/await · error typing · parallel vs sequential

async.ts
// async functions always return Promise<T>
async function fetchUser(id: number): Promise<User> {
  const res = await fetch(`/api/users/${id}`);
  if (!res.ok) throw new Error('Failed');
  return res.json();
}

// catch clauses are unknown by default — narrow before use
try {
  await fetchUser(1);
} catch (err) {
  if (err instanceof Error) {
    console.error(err.message);
  }
}

// parallel vs sequential
const [a, b] = await Promise.all([fetchUser(1), fetchUser(2)]);  // parallel
const c = await fetchUser(1);
const d = await fetchUser(2);                    // sequential

// Promise.allSettled for "I don't care about failures"
const results = await Promise.allSettled([
  fetchUser(1),
  fetchUser(2),
]);
// results: ({ status: 'fulfilled'; value: User } | { status: 'rejected'; reason: any })[]
⚠️
Floating promises. Calling an async function without awaiting or catching it produces a "floating promise" — errors get swallowed silently. Enable @typescript-eslint/no-floating-promises; it catches this pattern across your codebase.

Non-null assertion

the ! operator · when it's OK · why it's dangerous

non-null.ts
const input = document.getElementById('email');   // HTMLElement | null

// Assertions
const input1 = document.getElementById('email')!;  // HTMLElement — TS trusts you
input1.value;                                      // runtime crash if element is missing

// Safer — narrow with a guard
const input2 = document.getElementById('email');
if (!input2) throw new Error('Input not found');
input2.value;                                      // HTMLElement, no runtime risk
⚠️
The ! operator lies to the compiler. When you write x!, TS removes null and undefined from the type — but does nothing at runtime. If x was actually null, you get a crash with a stack trace pointing to a line that "couldn't" have been null. Use ! only when you have an invariant you can't express otherwise. Prefer optional chaining, guards, or defaulting.

Interview questions

the type-system ones you'll be asked

Q1What's the difference between interface and type?

interface describes object shapes and can be merged (declaration merging). type can describe unions, intersections, tuples, primitives, and mapped types. Use interface for object contracts you might extend; type for everything else.

Q2Difference between any and unknown?

Both accept any value. any disables type checking on the value everywhere it flows — you can call methods and access properties without checks. unknown is the safe version: you can assign anything to it, but must narrow before use. Prefer unknown for external data.

Q3What does never mean, and when do you use it?

It's the type of "no value". A function returning never never returns (throws or infinite loop). It's used for exhaustive checks (assertNever in a default branch) — adding a new union member makes the compiler flag any switch that forgets it.

Q4What is a discriminated union?

A union where every member has a shared literal field (the discriminant). Checking that field narrows the union to one member, so you get that member's fields in the branch. It's the cleanest way to model state, API results, and actions in TypeScript.

Q5When would you use a type guard?

When the runtime type isn't obvious from `typeof`/`instanceof` alone — e.g. distinguishing two object shapes. A predicate function isCat(x: Cat | Dog): x is Cat lets TS narrow inside if (isCat(pet)). Assertion functions (asserts x is T) narrow after a throw-check.

Q6What does keyof do?

It turns an object type into a union of its keys. keyof User = 'id' | 'name' | 'email'. Combined with generics (K extends keyof T), it makes type-safe property accessors, pickers, and sorters — invalid field names are caught at compile time.

Q7Difference between readonly and const?

const is for variables — can't be reassigned. readonly is for properties — can't be reassigned after construction. A const object can have mutable properties; a readonly property can exist on a mutable object. Both are compile-time only.

Q8Difference between private and #private?

private is a TS-only modifier — the field still exists at runtime and can be accessed via as any. #field is JavaScript's real private field — enforced by the engine, inaccessible from outside no matter what. Use # when you need genuine runtime privacy.

Q9What is a generic constraint?

A way to say "T can be any type, but it must have this shape". <T extends { length: number }> lets the function body safely read x.length. Without a constraint, T could be a number, and the access would fail to type-check.

Q10Explain Omit vs Pick.

Pick<T, K> keeps only the keys in K. Omit<T, K> removes the keys in K. Pick<User, 'id' | 'name'> and Omit<User, 'password'> produce similar shapes but different intents — Pick is "keep only these", Omit is "drop these".

Q11What is the difference between type A = B & C and type A = B | C?

& is intersection — the value must satisfy both, combining their properties. | is union — the value must satisfy one of them. A & B can be impossible if they contradict; A | B means the value could be A or B, and you need narrowing before type-specific use.

Q12When is as appropriate?

When you know the type more precisely than the compiler — typically at the boundary with external code (DOM, third-party libs, JSON.parse that you've validated). as silences the checker; use it only when you're genuinely sure. For "check but don't widen", use satisfies.

Q13What is strict mode?

A group of tsconfig checks enabled together, including strictNullChecks, noImplicitAny, strictFunctionTypes, and strictPropertyInitialization. Without strictNullChecks in particular, null and undefined are assignable to every type — which is where a huge class of runtime crashes lives.

Q14What's the difference between structural and nominal typing?

TypeScript is structural — a value's type is determined by its shape, not its name. If an object has the right fields, it's accepted, even if it wasn't declared as that interface. Java and C# are nominal — you must explicitly implement or extend the right types. Structural typing is why you can pass plain objects where a class instance is expected, and why libraries can accept "anything with a .length".

Q15Why doesn't TypeScript protect me from bad API responses?

Because types are erased at runtime. res.json() returns any — TS trusts whatever you assert about it. If the API sends { email: 42 }, TS has no way to know. That's why runtime validation with Zod or io-ts is standard: validate the shape at the boundary, then use the inferred type as trusted.

OOP in depth

the four pillars · classes, inheritance, encapsulation, abstraction, polymorphism, static

OOP is about bundling state (data) with behaviour (methods) into objects, and letting objects interact through well-defined interfaces. TypeScript supports all four pillars natively.

PillarMeaningIn TS
EncapsulationHide internal state, expose a controlled interfaceprivate, protected, #field, getters/setters
InheritanceReuse state and behaviour from a base typeextends, super, override
AbstractionModel only what matters, hide the restinterface, abstract class
PolymorphismSame call, different behaviour per typeMethod overriding, interface-based dispatch

Encapsulation

encapsulation.ts
class BankAccount {
  private balance = 0;

  deposit(amount: number) {
    if (amount <= 0) throw new Error('Must be positive');
    this.balance += amount;
  }

  get currentBalance(): number {
    return this.balance;
  }
}

Inheritance

inheritance.ts
class Animal {
  constructor(public name: string) {}
  speak(): string { return '…'; }
}

class Dog extends Animal {
  constructor(name: string, public breed: string) {
    super(name);      // must call before using `this`
  }

  override speak(): string {
    return 'Woof';
  }
}

Abstraction — interfaces and abstract classes

abstraction.ts
// Interface — pure contract
interface Shape {
  area(): number;
}

// Abstract class — partial implementation + contract
abstract class BaseShape {
  constructor(public name: string) {}
  abstract area(): number;      // must be implemented by subclass
  describe(): string {           // shared implementation
    return `${this.name}: ${this.area()}`;
  }
}

class Circle extends BaseShape {
  constructor(private r: number) { super('circle'); }
  area(): number { return Math.PI * this.r ** 2; }
}

// const s = new BaseShape('x');   ❌ abstract cannot be instantiated

Polymorphism

polymorphism.ts
class Notification { send() { console.log('base'); } }
class Email extends Notification { override send() { console.log('email'); } }
class SMS   extends Notification { override send() { console.log('sms'); } }

const channels: Notification[] = [new Email(), new SMS()];
channels.forEach(c => c.send());   // each calls its own implementation

Static

static members belong to the class, not instances. They're used for factory methods, shared constants, and counters.

static.ts
class User {
  static count = 0;

  constructor(public name: string) {
    User.count++;
  }

  static createGuest(): User {
    return new User('guest');
  }
}

User.count;             // 0
const u = User.createGuest();
User.count;             // 1
⚠️
Prefer composition over inheritance. Inheritance is the tightest coupling in OOP — a change to the base class ripples through every subclass silently. Inherit only for real is-a relationships, and keep hierarchies shallow. "Has-a" (composition) is almost always the safer design.

Miscellaneous topics

things that matter in real code that don't fit elsewhere

satisfies

Checks a value against a type without widening its inferred type. Unlike as, it's safe (fails if the shape doesn't match). Unlike annotation, it preserves literal types.

satisfies.ts
type Route = { path: string; auth: boolean };

const routes = {
  home:   { path: '/',      auth: false },
  admin:  { path: '/admin', auth: true },
} satisfies Record<string, Route>;

// routes.admin.auth is still `true`, not `boolean` — literal type preserved

Type-level operators

  • typeof — get the type of a value: type X = typeof someVar.
  • Indexed access — T['key'] for the type at key.
  • Mapped types — { [K in keyof T]: T[K] } transforms every property.
  • Conditional types — T extends U ? X : Y.
  • Template literal types — \`user-${string}\`.
  • Infer — T extends (infer U)[] ? U : never to extract a type from within a type.

Enum vs literal union

Prefer literal unions. Enums emit runtime code (extra bundle size), have confusing reverse-mapping for numeric members, and don't serialise as cleanly. Literal unions (type Status = 'a' | 'b') are erased, work everywhere, and integrate better with external systems.

Unknown vs never in function parameters

  • function f(x: unknown) — accepts anything, caller can pass any value, function must narrow before use.
  • function f(x: never) — impossible to call (no value satisfies never). Used for exhaustiveness checks.
