01

What a DBMS is

data vs information vs database · why not files · what the DBMS guarantees

A database is an organised collection of data. A DBMS (Database Management System) is the software that stores, retrieves, and protects that data. You don't talk to the files directly — you talk to the DBMS, and it decides how to store, index, and retrieve them.

Why not just use files?

Every application could write to a JSON file or a CSV. For small, single-user, simple data, it works. It collapses the moment you have multiple users, concurrent writes, or relationships between entities.

Problem with filesWhat the DBMS solves
Two processes write to the same file → corrupted dataConcurrency control — locks, MVCC, transaction isolation
App crashes mid-write → half-written fileAtomicity + recovery via write-ahead logging
Finding "all users over 25 in Pune" means scanning the fileIndexes — data structures that find rows without scanning
Nothing stops a field from being a number in one row and a string in anotherSchema + constraints — types, NOT NULL, foreign keys
No access control — anyone with file access can read anythingAuthentication + authorization — users, roles, grants
Backups and restores are manual, error-proneBackup + point-in-time recovery
The one sentence

A DBMS is the layer between your application and the storage. It guarantees atomicity (writes succeed or don't happen), consistency (constraints hold), isolation (concurrent operations don't corrupt each other), and durability (committed data survives a crash), while providing the query and index machinery to make data findable.

What the DBMS layer does

  • Storage management — how bytes go on disk, how pages are laid out, how memory is cached.
  • Query processing — parse the request, plan the fastest execution path, execute it.
  • Transaction management — group operations into atomic units, coordinate concurrent access.
  • Recovery — after a crash, bring the database back to a consistent state.
  • Access control — who can read, write, alter what.
Quick check · 01
Why is a JSON file NOT a substitute for a database in a multi-user app?
A file gives you no way to coordinate two writers, no way to undo a half-finished write, and no guarantee the file is consistent when your app reads it. Those guarantees are exactly what a DBMS provides.

Architecture of a DBMS

the layered stack · query pipeline · buffer manager · file manager

Every relational DBMS has the same high-level layers, even if the implementations differ. Data flows top to bottom on writes and bottom to top on reads.

  1. The application sends a query. From here on, the DBMS is in charge — the app doesn't touch files directly.
  2. The parser checks syntax, the rewriter normalises it (expands views, flattens subqueries), and the catalog validates that the tables and columns exist and the user has permission.
  3. The optimizer generates multiple possible execution plans and estimates the cost of each — how many pages to read, how many rows to touch, whether to use an index. It picks the cheapest. This is why two queries that "mean the same thing" can run at wildly different speeds.
  4. The execution engine runs the chosen plan: it requests rows from the storage manager, applies filters, joins, aggregates, and returns results.
  5. The buffer manager is the RAM cache. It holds recently used pages in memory, tracks which pages are dirty (modified but not yet written), and decides when to evict a page. All this matters because disk is thousands of times slower than memory.
  6. The storage manager reads and writes pages (4–16 KB blocks) from disk. It maintains B+ tree indexes, writes the write-ahead log, and handles recovery after a crash.
Step 1 / 6
💡
The optimizer is the reason query rewriting matters. Two queries that are logically equivalent — SELECT * FROM a, b WHERE a.id = b.a_id and SELECT * FROM a JOIN b ON a.id = b.a_id — can produce very different plans. The optimizer is smart, but not omniscient; understanding what plan it picks is how you make queries fast. (The SQL specifics of that are in the SQL note; here we only care that the layer exists.)
Quick check · 02
Which layer decides whether a query uses an index or a full scan?
The optimizer uses statistics (table size, index selectivity, page counts) to choose between plans. The buffer manager only caches pages — it doesn't decide which pages to request.

Data models

relational · document · key-value · graph · columnar · choosing a model

A data model is the way a database conceptually organises data. Each model optimises for a different shape of data and access pattern. Understanding them makes you choose the right tool instead of fitting the wrong one.

ModelData shapeStrengthsWeaknesses
RelationalTables of rows, related by keysJoins, ACID, mature tooling, strong consistencySchema migrations, less flexible shape
DocumentHierarchical JSON-like documentsFlexible shape, one read returns a connected structureWeak joins, schema drift, hard to enforce constraints
Key-valueSimple key → value mapExtreme speed, trivially scalableNo querying by value, no structure
GraphNodes and edges with propertiesTraversal, relationships are first-classNiche tooling, complex to scale writes
ColumnarColumn-oriented storageAnalytical queries, compressionNot good for row-level reads/writes
Time-seriesTimestamped samplesEfficient range queries by time, built-in aggregationOverkill for non-temporal data
The model follows the access pattern

Relational when data is highly connected and queries join across entities. Document when one entity is a self-contained object (a product with variants, a user with preferences). Key-value when the access pattern is literally "get by key" (sessions, caches, feature flags). Graph when the question is "who is connected to whom" (social, fraud detection, recommendations). Columnar when you scan millions of rows to aggregate a few columns (analytics).

Quick check · 03
An analytics dashboard scans 500 million rows to compute averages per region. Which model fits best?
Analytical queries scan few columns across many rows. A row-store reads entire rows even when you only need two columns. Columnar storage reads only the columns requested, and compresses them better.

The ER model

entities · attributes · relationships · cardinality · weak entities

The Entity-Relationship model is the design language for relational databases. You describe the world as entities (things), attributes (properties of things), and relationships (how things connect). Then you translate the model into tables.

Rectangles/ellipses = entities · ovals = attributes (underlined key) · diamond = relationship · dashed = identifying relationship for a weak entity

Entities and attributes

  • Entity — a real-world thing with independent existence. A User, an Order, a Product.
  • Strong entity — has its own identity. It doesn't depend on another entity to exist.
  • Weak entity — cannot exist without its parent. A LineItem only makes sense as part of an Order. Its identity depends on the parent.
  • Attributes — properties. A User has email, name, age. A LineItem has quantity, unit_price.
  • Key attribute — a property whose value uniquely identifies the entity. user_id for User.
  • Composite attribute — an attribute composed of sub-attributes (address = street + city + pin).
  • Multivalued attribute — an attribute that can hold multiple values (a user can have multiple phone numbers).

Relationships and cardinality

Cardinality describes how many entities on one side can be associated with entities on the other. It drives the table structure.

CardinalityMeaningHow to model it
1:1One user has one profileForeign key on either side, or merge the tables
1:NOne user has many ordersForeign key on the "many" side (orders.user_id)
N:MMany students take many coursesJoin table with foreign keys to both sides

Participation constraints

  • Total participation — every entity must participate. Every Order must have a User. Enforced with a NOT NULL foreign key.
  • Partial participation — participation is optional. A User may have zero orders.
  • Weak entity — always total participation on the identifying relationship (a LineItem always belongs to an Order).
From ER to tables — the translation

Each strong entity becomes a table. Its key becomes the primary key. A 1:N relationship becomes a foreign key on the "many" side. An N:M relationship becomes a join table. A weak entity becomes a table with a composite primary key: parent key + partial key of the weak entity. This translation is mechanical, but every step matters — get the cardinality wrong and your schema will have anomalies downstream.

Quick check · 04
An Order has many LineItems, but a LineItem cannot exist without its Order. What kind of entity is LineItem?
Having its own attributes doesn't make it strong. A weak entity cannot exist without its identifying parent. LineItem's identity is (order_id, line_number) — without the order, the item has no identity.

Keys & constraints

superkey · candidate · primary · foreign · unique · the hierarchy

Keys are the mechanism that connects tables and enforces identity. The names are hierarchical and often confused.

KeyDefinitionExample
SuperkeyAny set of columns that uniquely identifies a row(email), (email, name), (aadhaar)
Candidate keyA minimal superkey — no extra columns(email), (aadhaar) — both uniquely identify but neither needs the other
Primary keyThe chosen candidate key — the official identifierWe pick id as the primary key
Alternate keyA candidate key that wasn't chosen as primaryemail is alternate if id is primary
Composite keyA candidate key made of multiple columns(order_id, line_number) for a LineItem
Foreign keyA column that references the primary key of another tableorders.user_id → users.id
Unique keyA constraint that no two rows share this value — but nulls are usually allowedusers.email is often unique
Superkey ⊇ Candidate key ⊇ Primary key

Every candidate key is a superkey, but not every superkey is a candidate key. Every primary key is a candidate key, but not every candidate key is chosen as primary. If a set of columns doesn't uniquely identify a row, it isn't a superkey at all.

Constraint types

  • Primary key — unique + not null. One per table.
  • Foreign key — value must exist in the referenced primary key (or be null if allowed). Enforces referential integrity.
  • Unique — no duplicates, but (usually) allows nulls.
  • Not null — the column must have a value.
  • Check — arbitrary condition (age >= 0).
  • Default — value used when none is provided.
⚠️
Foreign keys are the DBMS's integrity guarantee. Without one, you can reference a user that doesn't exist and the DBMS won't stop you. With one, insert fails if the reference is broken, and ON DELETE CASCADE defines what happens when the parent is deleted. Applications enforcing this "by convention" get it wrong eventually.
Quick check · 05
A table has columns (id, email, name). Both id and email uniquely identify a row. Which of these is not a candidate key?
A candidate key must be minimal — you can't remove any column and still uniquely identify a row. id alone does the job, so (id, email) has a redundant column. It's a superkey, but not a candidate key.

Normalization

anomalies · 1NF · 2NF · 3NF · BCNF · when to denormalize

Normalization is the process of restructuring a schema so that every fact is stored in exactly one place. It's not about "making tables smaller" — it's about eliminating update anomalies that arise when data is duplicated.

The three anomalies, with an example

Suppose one table stores both students and their courses: (student_id, student_name, student_email, course_id, course_name, instructor).

AnomalyWhat happens
InsertYou can't add a new course without also having a student enrolled in it — every course row needs a student.
UpdateIf a course's instructor changes, you have to update every row where that course appears. Miss one → inconsistent data.
DeleteIf the last enrolled student is removed, the course information disappears too — you lost the course.

The normal forms

  1. 1NF — atomic values only. No column may hold a comma-separated list, no repeating groups. A phones column holding "123, 456" violates 1NF. Move the phones into their own table with a foreign key back to the user.
  2. 2NF — no partial dependency. Every non-key column must depend on the whole primary key, not just part of it. If student_name depends only on student_id (not on course_id), and your key is (student_id, course_id), that's a 2NF violation. Split it out.
  3. 3NF — no transitive dependency. A non-key column must not depend on another non-key column. If instructor depends on course_id and course_id is a non-key column, then instructor is transitively dependent — split it out.
  4. BCNF — every determinant is a candidate key. This catches edge cases that 3NF misses, especially with composite keys where two different candidate keys overlap. In practice most well-designed schemas hit BCNF without extra work.
  5. Denormalization is a valid choice. Every join costs a page read. Warehouses, dashboards, and read-heavy systems often intentionally store duplicate data to avoid joins. The rule is: normalize until it hurts, denormalize until it works — and know exactly which anomalies you're trading away.
Step 1 / 5
💡
Normalization is about correctness, not performance. A normalized schema is usually slower to read (because joins) but safer to write (no duplication, no drift). Denormalize on purpose, for a measured performance reason — never as a first step.
Quick check · 06
A table has columns (student_id, course_id, student_name) with primary key (student_id, course_id). student_name depends only on student_id. Which normal form does this violate?
This is the classic partial-dependency violation. student_name only needs student_id, so it belongs in a separate students table, not in the junction table.

Transactions

the unit of work · begin/commit/rollback · what a transaction protects

A transaction is a sequence of operations that the DBMS treats as one indivisible unit. Either all operations succeed and become visible, or none of them do. There's no middle state.

The classic example

Transfer ₹100 from account A to account B:

1. Debit A by ₹100.
2. Credit B by ₹100.

If the process crashes between 1 and 2, without a transaction you've destroyed ₹100. With a transaction, the DBMS rolls back the debit and A is untouched. The transaction guarantees the pair is atomic.

The transaction lifecycle

  1. Begin — the transaction starts, and the DBMS records the state it needs to roll back to.
  2. Operations — reads and writes happen. Writes may not be flushed to disk yet (they're in the buffer).
  3. Commit — the DBMS flushes the write-ahead log so the changes survive a crash. Data becomes visible to other transactions.
  4. Rollback — the DBMS undoes the changes using the log or undo records. The database returns to its state before the transaction began.
⚠️
Commit ≠ flushed to the actual data file. A committed transaction is flushed to the write-ahead log, which is enough for durability — after a crash, the log is replayed. The data pages are written lazily. This is a critical design: the log is written sequentially (fast); data files are updated in the background (slow, random access).

ACID

atomicity · consistency · isolation · durability · how each is enforced

ACID is the set of guarantees a transactional database makes. Each letter names a property, and each property has a mechanism inside the DBMS that provides it.

PropertyMeaningHow the DBMS enforces it
AtomicityAll or nothingWrite-ahead log + undo log. On rollback, undo the operations
ConsistencyConstraints hold before and afterConstraints (PK, FK, CHECK), triggers, application logic
IsolationConcurrent transactions don't interfereLocks, MVCC, isolation levels
DurabilityCommitted = permanentFlush the WAL to disk before acknowledging commit
Consistency is the odd one out

Atomicity, isolation, and durability are provided entirely by the DBMS. Consistency is partly your responsibility — the DBMS enforces the declared constraints (NOT NULL, foreign keys, unique), but it can't know that "order total must equal sum of line items" unless you tell it. That rule has to be enforced by the application, a trigger, or a check constraint. When people say "ACID ensures consistency," they mean consistency within the rules you declared.

Quick check · 07
A transaction commits. The server crashes five seconds later before the data pages are written to disk. What happens after restart?
This is exactly what durability means. Commit flushes the log, not the pages. On restart, the DBMS replays the WAL to reconstruct committed changes. The pages can lag behind; the log cannot.

Concurrency control

schedules · anomalies · locking · 2PL · MVCC

Multiple transactions run at once. Without controls, their interleavings produce results no single transaction would produce alone. Concurrency control restricts interleavings so that only "safe" ones are allowed.

The three read anomalies

AnomalyWhat happens
Dirty readT1 writes a value, T2 reads it, T1 rolls back. T2 has now used data that never existed.
Non-repeatable readT1 reads a row, T2 updates the same row and commits, T1 reads it again and gets a different value. Same row, different answer within one transaction.
Phantom readT1 runs a query returning 5 rows. T2 inserts a new matching row and commits. T1 runs the same query and gets 6 rows. The "phantom" row appeared.

Locking — the two-phase approach

The classic solution is Two-Phase Locking (2PL): a transaction acquires locks as it reads and writes, and cannot release any lock until all locks it will ever acquire have been acquired. This guarantees serializability — the result is equivalent to running the transactions one after another.

  1. T1 wants to update row A. It acquires an exclusive lock on A. Nothing else can read or write A while T1 holds it.
  2. This is the growing phase. T1 is accumulating locks. It cannot release A yet — releasing would let another transaction see its in-progress work.
  3. T1 also wants to update row B. It tries to acquire a lock on B, but T2 already holds one. T1 waits. It does not release A while waiting — that would violate the growing phase.
  4. Eventually T2 releases B. T1 acquires B. Now T1 has all the locks it needs. It begins its shrinking phase — releasing locks in the order it finished with them.
  5. T1 releases A. Now T1's work is fully done and other transactions can see it. Releasing A before B would be fine too — the point is that no new lock is acquired after the first release.
  6. T1 commits and releases all locks. Because no transaction could acquire a lock that another held, and the growing phase prevented "I released A and now I want to acquire B", every transaction that committed did so in a state equivalent to a serial order. This is serializability.
Step 1 / 6

Deadlocks

Two-phase locking has a classic problem: deadlock. T1 holds A and waits for B; T2 holds B and waits for A. Neither can proceed. The DBMS detects this (usually with a wait-for graph) and picks one transaction to abort.

MVCC — the modern alternative

Locks block readers and writers against each other. Modern databases (Postgres, MySQL with InnoDB, Oracle) use MVCC — Multi-Version Concurrency Control. Instead of locking, they keep multiple versions of a row. Each transaction sees the version that was current when it started its snapshot. Readers never block writers, writers never block readers.

What MVCC trades

MVCC gives you non-blocking reads, which is a huge win for read-heavy workloads. The cost is storage: old versions accumulate until VACUUM (Postgres) or a similar mechanism reclaims them. Under heavy write load with long-running transactions, the version count can grow large. MVCC also doesn't prevent every anomaly — serializable behaviour still needs additional checks.

Quick check · 08
Two-phase locking (2PL) has a fundamental drawback. What is it?
2PL guarantees serializability but creates deadlocks. The DBMS detects and aborts one transaction. Modern databases use MVCC to avoid blocking entirely, which reduces (but doesn't eliminate) deadlock scenarios.

Isolation levels

the four levels · what each prevents · the cost of each

Isolation levels let you trade consistency for performance. A higher level prevents more anomalies but allows less concurrency (or requires more versioning).

LevelDirty readNon-repeatable readPhantom readConcurrency

READ COMMITTED (default)PreventedAllowedAllowedHigh

💡
*Postgres footnote. The SQL standard says REPEATABLE READ permits phantom reads. Postgres implements REPEATABLE READ as a true snapshot, so it also prevents phantoms — behaving like the standard's SERIALIZABLE in that respect. This is a real interview gotcha: know the standard table AND know that Postgres's REPEATABLE READ is stronger.
Quick check · 09
You read a row, another transaction commits an update, and you read the same row again and get a different value. Which anomaly is this, and what isolation level prevents it?
A dirty read is reading an uncommitted change. Here the change is committed — the issue is that the value changed between two reads in the same transaction. That's a non-repeatable read.

Indexing — the concept

why indexes exist · B+ trees · hash indexes · when they hurt

An index is a sorted data structure that lets the DBMS find rows without scanning the whole table. Without an index, finding one row in a million means reading a million pages. With one, it means reading a handful.

The B+ tree — why databases choose it

The B+ tree is the default index in almost every relational database. It's a balanced tree where each node is a disk page and holds hundreds of keys. The tree stays 3–4 levels deep even for billions of rows.

  1. The root page holds a small number of separator keys. A lookup starts here. Because every query starts at the root, this page is virtually always in the buffer pool — effectively free.
  2. Looking for 68. The root says [50 | 100]. 68 > 50 and 68 < 100, so it descends to the middle child. Each comparison eliminates an entire subtree.
  3. The next-level node [20 | 40] says 68 > 40 → go right. Follow that child pointer.
  4. The third-level node [60 | 70 | 80] says 60 ≤ 68 < 70 → go to its leaf. This is the last internal node the lookup needs.
  5. The leaf page holds the actual key-value pairs (the indexed value and a pointer to the row). The lookup finds 68 and returns the row pointer. Total page reads: 3–4. For a table of billions of rows. This is the power of a B+ tree.
Step 1 / 5

Why not a hash table for every index?

Hash tables are O(1) for equality but useless for ranges. "Find all users aged 18–30" on a hash index means hashing every possible age and unioning — practically a full scan. B+ trees support ranges, sorts, and prefix lookups because their keys are ordered.

The cost of indexes

  • Writes. Every insert, update, or delete must update every index on the table. Six indexes = six extra B+ tree writes per row insert.
  • Storage. An index can be 20–40% of the data size. A text or array index can be larger than the collection.
  • Maintenance. Long-running writes may page-split or fragment the index, degrading lookup performance over time.
⚠️
More indexes is not better. An index nobody queries is pure cost — write amplification and disk. A collection with 15 indexes on 3 columns is a maintenance nightmare. Add indexes based on the queries that actually run, remove indexes that don't show up in query statistics.
Quick check · 10
Why does a hash index not help a range query WHERE age BETWEEN 18 AND 30?
A hash index is great for WHERE age = 22. For a range, the values are scattered across the hash space. A B+ tree keeps them sorted and adjacent, so a range is one leaf-chain walk.

Storage engines

pages · heap vs clustered · row vs column · B-tree vs LSM

Pages — the unit of disk I/O

Disks don't give you "one byte" at a time; they give you a page — typically 4 KB, 8 KB, or 16 KB. Every DBMS read or write touches a full page, whether you need one byte from it or all of it. This is why data layout matters: if related rows are on the same page, one read returns them all.

Storage layoutHow it storesBest for
Heap (row-store)Rows written in insertion order, with an index pointing to their locationOLTP: point reads, single-row inserts/updates
Clustered (index-organized)Rows stored in primary-key order in the table itselfRange scans by primary key, cover the whole row from one B+ tree
ColumnarValues of one column stored togetherOLAP: aggregate over few columns, huge scans
LSM treeWrites go to memory first, flushed as sorted files, periodically mergedWrite-heavy workloads (Cassandra, RocksDB, LevelDB)

B-tree vs LSM tree

The B-tree is the workhorse of OLTP databases because it gives consistent read latency — one lookup is always O(log n) page reads. LSM trees flip the trade-off: they make writes extremely fast by appending to memory and merging files later, at the cost of slower reads (multiple files may need to be searched) and periodic compaction pauses.

The read vs write trade-off

B-tree: reads are consistently fast, writes are slower (in-place page modification). LSM tree: writes are very fast (append-only), reads are slower (multiple files, bloom filters help). Row-store: entire row per disk read, good for OLTP. Column-store: only the queried columns, good for analytics. Every storage engine is a trade-off.

Quick check · 11
A system ingests 100,000 events per second but rarely reads them individually. Which storage engine pattern fits best?
The workload is write-dominated. B-tree indexes get hot on every insert and page-split constantly. LSM trees absorb this write rate by writing to memory and flushing sorted files, which is why time-series and event-log systems use them.

Crash recovery & WAL

the write-ahead log · redo vs undo · checkpoints

Databases crash. Power fails, processes are killed, disks fail. The DBMS must recover to a consistent state where every committed transaction is present and every uncommitted transaction is absent.

The write-ahead log (WAL)

The core rule: before a data page is modified on disk, an entry describing the change must be written to the log and flushed. The log is append-only (sequential writes, fast); data pages are random writes (slow). This ordering is what makes recovery possible.

  1. A transaction updates a row in memory. Before the row is touched on disk, the DBMS writes a log record: "row 42, old value X, new value Y".
  2. The log record is flushed to disk. From this moment on, the change can survive a crash — because the log has it, even if the data page doesn't. This is the write-ahead part: log first, page second.
  3. When the transaction commits, a commit record is appended to the log. The commit is durable the moment the commit record hits disk. The data page can lag behind — that's fine.
  4. The data page is still in the buffer pool, unmodified on disk. Under normal operation, it will be written lazily by the buffer manager — often much later.
  5. The server crashes. Memory is lost. The buffer pool is gone. The data page never reached disk.
  6. On restart, the DBMS replays the log. Every committed transaction is redone (redo). Every transaction without a commit record is undone (undo) using the "old value" stored in its log records. The database ends up consistent, with exactly the committed transactions applied.
Step 1 / 6

Checkpoints

Replaying the whole log on every restart would be slow. A checkpoint periodically flushes all dirty pages to disk and records in the log "everything up to this point is safely on disk." Recovery can then skip everything before the last checkpoint.

Quick check · 12
Why must the log record be flushed before the data page is modified on disk?
That's the whole point of "write-ahead". If the page is written and the log isn't, and then a crash happens, the disk contains a change no one knows about and no rollback can undo it. Log first, always.

Distributed databases

replication · sharding · two-phase commit · eventual vs strong consistency

When one machine can't hold the data or handle the load, you distribute it. Two fundamental strategies — and they can be combined.

StrategyWhat it doesWhy use itCost
ReplicationSame data on multiple nodesAvailability (failover), read scalingWrites must be propagated; replicas may lag
Sharding (partitioning)Different data on different nodes, split by a shard keyWrite scaling, storage scalingCross-shard queries are slow/expensive; resharding is hard

Two-phase commit (2PC)

When a transaction must modify data on multiple nodes, 2PC coordinates them. The coordinator asks every participant to prepare (prepare to commit, but don't yet). If any participant can't, everyone is told to roll back. If all say yes, the coordinator asks everyone to commit. This guarantees all-or-nothing across nodes, but adds two round trips of latency and creates a blocking risk if the coordinator dies mid-transaction.

⚠️
Distributed transactions are slow. This is why many modern systems prefer eventual consistency and sagas — a sequence of local transactions with compensating actions — over 2PC. It's a trade: you accept brief inconsistency in exchange for throughput and availability.

CAP & consistency models

the theorem · what "choose 2" actually means · PACELC

The CAP theorem says a distributed database can guarantee at most two of three properties when a network partition occurs:

PropertyMeaning
Consistency (C)Every read sees the most recent write — a linearisable single view
Availability (A)Every request gets a response (not an error)
Partition tolerance (P)The system keeps working despite messages being dropped between nodes
What "choose 2" actually means

Partitions happen — networks fail. So P isn't really optional. The real choice is what to do when a partition occurs: refuse writes to preserve consistency (CP), or accept writes and risk divergence to preserve availability (AP). No system is "CA" — that's only possible if there is no network partition, which a distributed system cannot guarantee. So in practice, distributed databases are CP or AP.

PACELC — the more useful extension

CAP only describes behaviour during a partition. What about the 99% of the time when the network is fine? PACELC answers: during a Partition, choose A or C; Else (no partition), choose Latency or Consistency. Even with a healthy network, strong consistency requires coordinating across nodes, which adds latency.

Consistency models

ModelGuarantee
Strong (linearizable)Every read returns the most recent committed write
SequentialAll nodes see writes in the same order
CausalWrites that depend on each other are seen in order; unrelated writes may be reordered
EventualIf writes stop, all replicas will eventually converge
Quick check · 13
Why is "CA" not a realistic option for a distributed database?
CA would only be possible if the system never has a network partition. Distributed systems always do. So the real choice is: when a partition happens, are you CP or AP?

SQL vs NoSQL — the honest comparison

what each does well · when to pick which · the false binary

SQL (relational)NoSQL

ACIDFull ACID by defaultVaries — many NoSQL databases are "BASE" (eventually consistent)

The false binary

The "SQL vs NoSQL" debate is often a false choice. Real systems mix: PostgreSQL for transactional data, Redis for caching and rate limiting, Elasticsearch for search, a document store for catalogs, a time-series database for metrics. The right question isn't "SQL or NoSQL" but "for this data, with this access pattern, which model fits?"

Quick check · 14
A banking system with strict multi-account transfer requirements should use which database?
Transfers need multi-row atomic updates with strong consistency. That's the definition of what relational databases with ACID exist for. Choosing speed over correctness here would lose money.

Interview questions

what you'll actually be asked about DBMS theory

Q1What is a DBMS, and why not just use files?

A DBMS is the software layer between applications and stored data. Files alone can't handle concurrent access without corruption, don't provide atomicity or recovery after a crash, have no query/index machinery, and can't enforce constraints or access control. The DBMS provides all of these — ACID transactions, indexes, schemas, recovery, and security — as a single trusted layer.

Q2Explain the three-tier architecture of a DBMS.

Three levels of abstraction: internal (physical — how bytes are stored, page layout, indexes), conceptual (logical — the tables, columns, relationships, constraints), and external (view — what each user or application sees). The separation lets you change the storage format without breaking applications, and give different users different views without duplicating data.

Q3What's the difference between a candidate key, primary key, and foreign key?

A candidate key is a minimal set of columns that uniquely identifies a row. A primary key is the candidate key chosen as the official identifier (unique + not null, one per table). A foreign key is a column that references another table's primary (or unique) key, enforcing referential integrity. Candidate keys are choices; primary is the chosen one; foreign key is the connection.

Q4What is normalization, and why does it matter?

Restructuring a schema so each fact is stored in exactly one place, eliminating update, insert, and delete anomalies. 1NF requires atomic values, 2NF eliminates partial dependencies, 3NF eliminates transitive dependencies, BCNF is stricter still. It matters because duplicated data drifts out of sync — normalizing makes the database the single source of truth.

Q5Explain ACID.

Atomicity: all-or-nothing — enforced by the WAL and undo logs. Consistency: constraints hold — enforced by declared constraints and application logic. Isolation: concurrent transactions don't corrupt each other — enforced by locking or MVCC. Durability: committed = permanent — enforced by flushing the log before acknowledging commit.

Q6What's the difference between a dirty read, non-repeatable read, and phantom read?

Dirty read: reading uncommitted data. Non-repeatable read: the same row returns different values in one transaction because another transaction committed an update between the two reads. Phantom read: a query returns a different set of rows because another transaction inserted or deleted matching rows between two executions of the same query. Each is progressively harder to prevent, which is why isolation levels exist.

Q7What is two-phase locking, and what problem does it have?

A protocol where a transaction acquires locks in a growing phase and only releases them in a shrinking phase — no new lock can be acquired after the first release. This guarantees serializability. Its problem is deadlock: two transactions can each hold a lock the other needs, blocking forever. The DBMS detects this with a wait-for graph and aborts one transaction to break the cycle.

Q8What is MVCC, and what does it trade?

Multi-Version Concurrency Control — each transaction sees a snapshot of the data as of its start time, using versioned rows. Readers never block writers, writers never block readers. The trade-off is storage: old versions accumulate until a vacuum process reclaims them, and long-running transactions slow that reclamation.

Q9Why does a B+ tree beat a binary search tree for disk indexes?

A BST has one key per node, so its height is log₂n — around 24 levels for a crore of keys, meaning ~24 disk reads. A B+ tree packs hundreds of keys per node (one page), so its height is logfn — 3–4 levels for the same dataset. Fewer disk reads, and its sorted leaves make range scans efficient too.

Q10Why is a hash index unsuitable for range queries?

Hashes destroy ordering. A hash index maps a value to a bucket, which is perfect for equality. But nearby values (18, 19, 20) land in completely unrelated buckets. A range query would have to hash every possible value in the range — practically a full scan. B+ trees keep values sorted, so a range is one contiguous leaf walk.

Q11What is the write-ahead log (WAL), and why does it exist?

A sequential log of every change, flushed to disk before the corresponding data pages are modified. It's what makes durability and recovery possible: after a crash, committed changes are redone from the log, uncommitted ones are undone. Sequential writes are much faster than random page writes, which is why the DBMS commits to the log and lets data pages lag.

Q12Explain the CAP theorem and why "CA" isn't a real option.

CAP says a distributed system can guarantee at most two of Consistency, Availability, and Partition tolerance. But partitions happen — networks drop. So P isn't a choice. The real choice is: when a partition occurs, refuse writes to stay consistent (CP), or accept writes to stay available (AP). PACELC extends this: even without a partition, coordinating for consistency costs latency.

Q13What's the difference between replication and sharding?

Replication: the same data on multiple nodes — used for availability (failover) and read scaling. Writes still go through one primary. Sharding: different data on different nodes, split by a shard key — used for write and storage scaling. Cross-shard queries are expensive and resharding is hard. At scale you use both: each shard is itself a replica set.

Q14When would you choose a NoSQL database over a relational one?

When the schema is genuinely dynamic (product catalogs with wildly different attributes, user-generated event payloads), when writes dominate and you need horizontal scale from day one, when the access pattern fits a specific model (key-value for sessions/cache, documents for hierarchical entities, graphs for relationship-heavy data, time-series for metrics). Not as a default "because it's newer" — the missing joins, transactional guarantees, and constraints add up fast.

Q15What is a checkpoint, and why does it matter for recovery?

A periodic operation that flushes all dirty pages to disk and records in the log that everything up to that point is safely persisted. Recovery only needs to replay the log from the last checkpoint forward — without checkpoints, every restart would replay the entire log from the beginning, which could take hours.
