What MongoDB is (and isn't)

document store · NoSQL · ACID · where it fits

MongoDB is a document database. Instead of tables and rows, it stores documents — self-contained JSON-like objects — grouped into collections. A document can nest other objects and arrays, so one read returns a full, connected structure rather than requiring joins across tables.

Relational (MySQL / Postgres)MongoDB
DatabaseDatabase
TableCollection
RowDocument
ColumnField
IndexIndex
Foreign keyReference (ObjectId) or embedded document
JOIN$lookup in aggregation, or two queries in code
Schema enforced by DBSchema optional; can be enforced with validators or Mongoose

What MongoDB does well

  • Flexible schema. Add a field without migrations — every document can differ.
  • Hierarchical data in one document. Orders with line items, blog posts with comments, users with preferences.
  • Horizontal scale. Native sharding across a cluster.
  • Fast development loop. JSON in, JSON out. Same shape as your API and UI.
  • ACID transactions since 4.0 (multi-document, replica sets required).

What MongoDB does not do well

  • Complex relational joins at scale. If your data is deeply relational, use Postgres.
  • Strict schema at the database level by default. You can enforce it — but it's opt-in.
  • Atomic multi-document operations without transactions. Single-document operations are atomic; multi-document aren't, unless you use a transaction.
  • Ad-hoc analytical queries. Its aggregation pipeline is strong but not a warehouse.
The mental model

A MongoDB document is one JSON object. It has a primary key _id (auto-generated ObjectId if you don't set one), it lives in a collection, collections live in a database, and each server (or shard) can hold many databases. There is no cross-collection foreign-key enforcement.

Quick check · 01
A MongoDB document is closest to which SQL concept?
A document is one row's worth of data, but it can contain nested objects and arrays — which in SQL would be spread across multiple related tables.
02

The document model & BSON types

BSON · ObjectId · nested objects · arrays · type ordering

MongoDB stores documents in BSON (Binary JSON) — a binary encoding that supports types JSON does not: dates, binary data, ObjectId, Decimal128 for money, 64-bit integers, regex, and so on.

a document
{
  _id: ObjectId("6712a8c9e1f4b2d3a4e5f6a7"),
  name: "Aarav Sharma",
  email: "aarav@x.com",
  age: 22,
  active: true,
  createdAt: ISODate("2024-10-18T09:15:00Z"),

  address: {                         // nested object
    city: "Indore",
    pin: "452001",
  },

  tags: ["student", "backend"],           // array of strings

  orders: [                           // array of objects
    { orderId: "ORD-1", amount: 299 },
    { orderId: "ORD-2", amount: 199 },
  ],
}

ObjectId — the default primary key

Every document has an _id. If you don't supply one, MongoDB generates an ObjectId — a 12-byte value composed of a timestamp, a machine identifier, a process id, and a counter. That means ObjectIds are roughly sortable by creation time, and unique without coordination.

Why ObjectIds are not UUIDs

ObjectIds are 12 bytes, sortable by time, and generated client-side or server-side without conflict. UUIDs are larger and typically random — fine for privacy, but they lose the time-ordering you get for free with ObjectIds, which affects how efficiently inserts distribute across a sharded cluster.

BSON type ordering

When sorting or comparing across different types, MongoDB uses a fixed type order:

RankType
1MinKey
2Null
3Numbers (int, long, double, decimal)
4String / Symbol
5Object
6Array
7BinData
8ObjectId
9Boolean
10Date
11Timestamp
12MaxKey

That's why a field mixing numbers and strings will sort all numbers first. It's also why find({ age: '22' }) doesn't match documents where age is the number 22.

Quick check · 02
You have a field with mixed types: some documents have score: 42 (number), some have score: "42" (string). When you sort, which comes first?
MongoDB sorts by BSON type first, then by value within the type. Numbers always come before strings regardless of value.
03

CRUD — the four things you do

insert · find · update · delete · result shapes

Create

mongosh
// one document
db.users.insertOne({ name: 'Aarav', age: 22 });

// many at once
db.users.insertMany([
  { name: 'Priya', age: 20 },
  { name: 'Karan', age: 31 },
]);

// insertOne returns { acknowledged: true, insertedId: ObjectId(...) }
// insertMany returns { acknowledged: true, insertedIds: { 0: ObjectId, 1: ObjectId } }

Read

mongosh
db.users.find({ age: { $gte: 20 } });         // cursor
db.users.findOne({ name: 'Aarav' });          // single doc or null
db.users.find().countDocuments();              // count (accurate)
db.users.find().limit(5).skip(10);           // pagination
db.users.find().sort({ age: -1 });            // descending

// projection — only these fields come back
db.users.find({}, { name: 1, age: 1, _id: 0 });
💡
find() returns a cursor, not an array. The shell auto-iterates it, but in drivers you often call .toArray() — which loads everything into memory. For large result sets, iterate in batches. The default batch is 101 documents then 16 MB per batch.

Update

mongosh
// one document, field update (use $set!)
db.users.updateOne(
  { name: 'Aarav' },
  { $set: { age: 23 } }
);

// many documents
db.users.updateMany(
  { active: false },
  { $set: { archived: true } }
);

// add to an array
db.posts.updateOne(
  { _id: someId },
  { $push: { tags: 'mongodb' } }
);

// remove from an array
db.posts.updateOne(
  { _id: someId },
  { $pull: { tags: 'mongodb' } }
);
⚠️
Always use operators. updateOne(filter, { age: 30 }) replaces the entire document with { age: 30 } — every other field is lost. You almost always want $set, $unset, $inc, $push, or $pull.

The update operators you'll actually use

OperatorEffect
$setSet a field to a value (creates it if missing)
$unsetRemove a field
$inc / $mulIncrement / multiply a number
$push / $pullAdd to / remove from an array
$addToSetAdd to an array only if not already present
$popRemove the first or last array element
$renameRename a field
$min / $maxSet only if lower / higher than current
$currentDateSet to current date

Delete

mongosh
db.users.deleteOne({ _id: someId });
db.users.deleteMany({ active: false });
db.users.deleteMany({});              // deletes ALL docs — keep it empty unless you mean it

Result shapes (read them, don't ignore them)

OperationResult
insertOne{ acknowledged, insertedId }
insertMany{ acknowledged, insertedIds }
updateOne / updateMany{ acknowledged, matchedCount, modifiedCount, upsertedId }
deleteOne / deleteMany{ acknowledged, deletedCount }
Quick check · 03
What does db.users.updateOne({ name: 'Aarav' }, { age: 30 }) actually do?
Without an update operator, MongoDB treats the object as a full replacement. Use { $set: { age: 30 } } to change just the field.
04

Query operators

comparison · logical · element · array · evaluation

Comparison

comparison.js
{ age: { $eq: 22 } }        // same as { age: 22 }
{ age: { $ne: 22 } }        // not equal
{ age: { $gt: 18 } }         // greater than
{ age: { $gte: 18, $lt: 30 } }  // range
{ age: { $in: [18, 22, 30] } }   // any of these
{ age: { $nin: [18, 22] } }      // none of these

Logical

logical.js
// implicit AND: fields listed together
{ age: 22, city: 'Indore' }

// explicit AND (for same-field conditions you can't express otherwise)
{ $and: [{ age: { $gt: 18 } }, { age: { $lt: 30 } }] }

// OR
{ $or: [{ city: 'Indore' }, { city: 'Bhopal' }] }

// NOT
{ age: { $not: { $gt: 30 } } }

// NOR
{ $nor: [{ active: true }, { verified: true }] }

Element and existence

element.js
// has this field (even if null)
{ phone: { $exists: true } }

// matches null OR missing — dangerous!
{ phone: null }

// type check
{ age: { $type: 'number' } }
⚠️
{ field: null } matches missing fields too. If you want "the field exists and is null", write { field: { $type: 'null' } }. If you want "the field is missing", use { field: { $exists: false } }.

Arrays

arrays.js
// array CONTAINS this value
{ tags: 'node' }

// array contains ALL of these
{ tags: { $all: ['node', 'js'] } }

// array has exactly 3 elements
{ tags: { $size: 3 } }

// match by index
{ 'tags.0': 'node' }

// array of embedded documents — $elemMatch when multiple fields must match SAME element
{ items: { $elemMatch: { sku: 'A1', qty: { $gt: 2 } } } }
The $elemMatch trap

{ items: { $elemMatch: { sku: 'A1', qty: { $gt: 2 } } } } matches documents where one item has both properties.
{ 'items.sku': 'A1', 'items.qty': { $gt: 2 } } matches documents where some item has sku A1 and some item (maybe different) has qty > 2. Big difference in arrays of objects.

Evaluation

eval.js
// regex — anchored is faster with an index
{ name: { $regex: '^A' } }
{ name: /^A/ }                        // same thing

// JSON Schema validator embedded in a query
{ $jsonSchema: { required: ['name'] } }

// modulo
{ qty: { $mod: [2, 0] } }              // even qty
Quick check · 04
What does { phone: null } match?
null is special in MongoDB — it matches both null and missing. For strict matching use { $type: 'null' } or { $exists: false }.

Schema design & data modelling

embed vs reference · the 16 MB limit · 1:1, 1:N, N:N

In SQL, you normalise to eliminate duplication, then join to reconstruct. In MongoDB, the question is what does one read need? — and the answer usually drives you to embed what is always read together, and reference what is independent.

Embed vs reference — the decision table

FactorEmbedReference
Access patternChild is almost always read with the parentChild is often queried independently
CardinalityBounded (a few items, an address, a profile)Unbounded (millions of orders, posts, logs)
UpdatesChild rarely changes; duplicated data is acceptableChild changes often and is shared
SizeFits comfortably in one documentWould push the document near 16 MB
OwnershipChild belongs to exactly one parentMany parents can reference the same child
⚠️
16 MB is the hard cap per document. If your embedded array could grow unbounded — comments on a viral post, line items on a large order, logs per user — reference it in a separate collection. Unbounded arrays are the most common cause of "my writes stopped working" errors in MongoDB.

1:1 relationships

1:1 embedded
// Embedded: the profile is only ever read with the user
{
  _id: ObjectId(...),
  name: 'Aarav',
  profile: {
    bio: 'Backend dev',
    avatarUrl: '...',
  },
}

1:N relationships

1:N — embed when N is small and always read together
// A user's addresses — bounded, always read with the user
{
  _id: ObjectId(...),
  name: 'Aarav',
  addresses: [
    { line1: '12 MG Road', city: 'Indore', pin: '452001' },
    { line1: '45 Ring Rd', city: 'Bhopal', pin: '462001' },
  ],
}
1:N — reference when N is unbounded
// Posts by a user — could be thousands; separate collection
// users
{ _id: ObjectId('u1'), name: 'Aarav' }

// posts (each references its author)
{ _id: ObjectId(...), title: '...', authorId: ObjectId('u1'), createdAt: ISODate(...) }

N:N relationships

N:N
// Students ↔ Courses — two-sided references
// students
{ _id: ObjectId('s1'), name: 'Priya', courseIds: [ObjectId('c1'), ObjectId('c2')] }

// courses
{ _id: ObjectId('c1'), name: 'DBMS', studentIds: [ObjectId('s1')] }

Two ways to reference

PatternChild storesParent storesUse when
Child referenceparentIdnothing extraThe unbounded side (posts of a user, comments of a post)
Parent referencenothing[childIds]The bounded side (course list of a student)
Quick check · 05
A user has a shopping cart that could hold hundreds of items over time. Should the cart be embedded in the user document or its own collection?
An ever-growing array will eventually break writes. Either keep only the current cart embedded (small, bounded) and archive completed carts separately, or put carts in their own collection with a userId.

Data validation

schema validators · Mongoose · when to enforce what

MongoDB is schema-flexible by default — but you can enforce structure. Two places to do it:

  • Database-level with $jsonSchema validators — enforced regardless of which app or driver writes.
  • Application-level with Mongoose — enforced only in the Node process that uses your model.

Database validator

mongosh
db.createCollection('users', {
  validator: {
    $jsonSchema: {
      bsonType: 'object',
      required: ['name', 'email', 'age'],
      properties: {
        name:  { bsonType: 'string', minLength: 1 },
        email: { bsonType: 'string', pattern: '^.+@.+$' },
        age:   { bsonType: 'int', minimum: 0, maximum: 150 },
      },
    },
  },
  validationAction: 'error',       // 'warn' logs instead
  validationLevel: 'strict',     // 'moderate' skips existing invalid docs
});

Mongoose schema

models/User.js
import mongoose from 'mongoose';

const userSchema = new mongoose.Schema({
  name: {
    type: String,
    required: true,
    trim: true,
    minlength: 1,
    maxlength: 80,
  },
  email: {
    type: String,
    required: true,
    unique: true,
    lowercase: true,
    match: /^.+@.+$/,
  },
  age: {
    type: Number,
    min: 0,
    max: 150,
  },
}, { timestamps: true });

export default mongoose.model('User', userSchema);
Database vs app validators

Mongoose validators run in Node before the insert. They're great for fast feedback and custom logic (e.g. cross-field checks). Database validators run inside MongoDB — they protect against bulk imports, other services, and direct shell writes. For anything you can't afford to see corrupted, use both.

Quick check · 06
You add a required: true validator in Mongoose but someone imports data directly with the mongosh shell. Does the validator catch it?
Mongoose is a driver-side layer. It validates before sending to the DB. Direct shell writes skip it entirely. Use $jsonSchema validators if you want a hard guarantee.

populate vs $lookup

application-level join · database-level join · trade-offs

MongoDB has no foreign-key joins. Two ways to "join" reference-based data:

populate — the Mongoose way

populate.js
// schema — authorId references users collection
const postSchema = new mongoose.Schema({
  title: String,
  author: { type: mongoose.Schema.Types.ObjectId, ref: 'User' },
});

// query — two round trips under the hood (find posts, then find users)
const posts = await Post.find().populate('author', 'name email');
// posts[i].author is now { _id, name, email }

$lookup — the aggregation way

lookup.js
await Post.aggregate([
  {
    $lookup: {
      from: 'users',
      localField: 'author',
      foreignField: '_id',
      as: 'authorDoc',
    },
  },
  { $unwind: '$authorDoc' },
  { $project: { title: 1, 'authorDoc.name': 1 } },
]);
populate$lookup
Runs inApplication (Node)MongoDB server
Round tripsAt least 2 (one per populated path)1
Access to filtering/aggregationLimited — can filter on populated fields, but post-hocFull pipeline, project, unwind, sort, group
Works without MongooseNoYes — it's part of MongoDB
Best forSimple "get the referenced doc" casesComplex joins, shaping, filtered aggregation
Quick check · 07
You need posts with their author's name only, filtered by the author's city. Which approach is the better fit?
Filtering on fields of the joined collection is much cleaner with $lookup + $match, because the join happens server-side before the filter. With populate, you'd fetch posts first and filter in JS — inefficient and often incorrect.

Transactions

ACID · sessions · when you actually need them

Every single-document operation in MongoDB is atomic. But when you need to update multiple documents or collections and all-or-nothing matters, you use a transaction — since MongoDB 4.0 in replica sets, and 4.2 in sharded clusters.

transaction.js
import mongoose from 'mongoose';

async function transfer(fromId, toId, amount) {
  const session = await mongoose.startSession();
  session.startTransaction();

  try {
    await Account.updateOne(
      { _id: fromId },
      { $inc: { balance: -amount } },
      { session }
    );
    await Account.updateOne(
      { _id: toId },
      { $inc: { balance: amount } },
      { session }
    );
    await session.commitTransaction();
  } catch (err) {
    await session.abortTransaction();
    throw err;
  } finally {
    await session.endSession();
  }
}
⚠️
Transactions need a replica set. A standalone mongod (like a default local install) cannot do multi-document transactions. Atlas gives you a replica set by default; for local dev, run mongod --replSet rs0 and initiate the set once.
Don't reach for transactions first

Multi-document transactions are slower and lock more. If your design embeds what should be updated together, single-document atomicity does the job. Reach for a transaction when two collections genuinely must change together — order creation + inventory decrement + user points, for example.

Quick check · 08
Is a single-document updateOne atomic in MongoDB?
Single-document writes are atomic in MongoDB — a document is written or it isn't. You only need transactions when a logical operation spans multiple documents or collections.

Replication

replica sets · primary · secondaries · failover · read preferences

A production MongoDB deployment is a replica set: one primary and two or more secondaries. All writes go to the primary and are replicated to the secondaries. If the primary dies, an election picks a new one — automatically, in seconds.

  1. A client connects to the replica set. It doesn't have to know which node is primary — the driver discovers the topology and routes writes to the current primary.
  2. The primary applies the write to its local data and records the change in its oplog (operations log) — an ordered, capped log of every write.
  3. Each secondary continuously tails the primary's oplog and applies the same operations in order. This is how replication stays consistent.
  4. Depending on the write concern, the primary returns "write acknowledged" after applying locally (w: 1) or after N secondaries have applied it (w: majority, the default). w: majority is what you want in production.
  5. All three nodes now hold the same data. If the primary crashes, the remaining nodes elect a new primary from among the secondaries with the most up-to-date oplog.
  6. The old primary comes back, discovers a new primary already exists, and rejoins as a secondary — it catches up from the new primary's oplog. This is failover, and it's what replication is really for: availability.

Quick check · 09
What is the primary benefit of a replica set?
Replication is for availability and durability, not write scaling — all writes still go through the single primary. Write scaling is what sharding (the next section) solves.

Sharding

shard key · chunks · mongos · hot spots

Sharding is MongoDB's answer to horizontal scaling. Data is split across multiple replica sets (called shards) based on a shard key. Applications talk to mongos routers, which send queries to the shard(s) that have the data.

enable sharding
// choose a hashed shard key on a monotonically increasing field
sh.shardCollection('app.users', { _id: 'hashed' });

// or a compound shard key that has high cardinality
sh.shardCollection('app.orders', { userId: 'hashed', createdAt: 1 });

What makes a good shard key

PropertyWhy
High cardinalityMany distinct values → data spreads evenly
Even write distributionNo single shard takes most writes
Query alignmentCommon queries include the shard key, so they hit one shard instead of all
Non-monotonicMonotonic keys (_id, timestamps) pile inserts onto the last shard
The monotonic-key trap

If your shard key is _id and ObjectIds are time-sortable, every new insert has a higher _id than the last — so every new document goes to the last chunk, landing on one shard. That's a hot shard. Fix: use a hashed shard key, or make the shard key compound with a high-cardinality field ({ tenantId: 'hashed', _id: 1 }).

Quick check · 10
Why might you choose a hashed shard key instead of the natural _id?
A hashed shard key destroys the ordering but creates even distribution — exactly what you want for write throughput. Range queries on the shard key become less efficient, so hash only the fields you don't need to range-query.

Change streams

real-time listeners · resumability · MERN real-time APIs

A change stream is a tailable cursor over the oplog (via the $changeStream aggregation stage) that emits events for insert, update, replace, delete, and other operations. It is the official way to build real-time features on top of MongoDB — better than polling.

watch.js
// watch the whole collection
const stream = User.watch();

// filter to just insert events
const stream = User.watch([
  { $match: { operationType: 'insert' } }
]);

stream.on('change', (change) => {
  console.log(change.operationType);  // 'insert' | 'update' | 'delete' ...
  console.log(change.fullDocument);  // the new document (for inserts)
});

// resumable: store the resume token, restart from it after a crash
const token = change._id;
const resumed = User.watch([], { resumeAfter: token });
💡
Change streams require a replica set — because they read from the oplog. If you're running a standalone mongod locally, either start it as a single-node replica set or use Atlas for development when you're building real-time features.
Change streams + Express + WebSockets

The typical MERN real-time architecture: MongoDB → change stream watcher in your Express server → forward each event to connected Socket.IO clients. The database is the source of truth; the change stream turns it into a push stream; the WebSocket layer distributes it to browsers.

Binary data & GridFS

when to store files in the database · GridFS chunks

The 16 MB document limit rules out storing most real files inline. MongoDB's answer for large binary data is GridFS: it splits the file into chunks (default 255 KB) stored as documents in a fs.chunks collection, with metadata in fs.files.

gridfs.js
import { GridFSBucket } from 'mongodb';
import mongoose from 'mongoose';

const bucket = new GridFSBucket(mongoose.connection.db);

// upload — pipe a stream from multer or fs
const uploadStream = bucket.openUploadStream('resume.pdf');
req.pipe(uploadStream);

// download
bucket.openDownloadStreamByName('resume.pdf').pipe(res);
⚠️
GridFS is not always the right answer. For most file storage (images, videos, PDFs), an object store like S3 or Cloudinary is a better fit — cheaper, faster, CDN-backed, and not competing with your database for I/O. Use GridFS when you need files to be transactional with your data, when you can't use an external store, or when you need change streams on the metadata.

terminal

How it fits a MERN app

Mongoose models · Express routes · API shape

LayerResponsibility
MongoDBPersists documents; enforces database validators, indexes, TTL

A typical MERN slice

routes/users.js
import express from 'express';
import User from '../models/User';

const router = express.Router();

router.get('/', async (req, res) => {
  const users = await User.find().select('-password');
  res.json(users);
});

router.post('/', async (req, res) => {
  try {
    const user = await User.create(req.body);   // schema validates
    res.status(201).json(user);
  } catch (err) {
    res.status(400).json({ message: err.message });
  }
});

export default router;
The idiomatic split

React never talks to MongoDB directly. Express is the boundary. Validate inputs on Express (express-validator or zod), let Mongoose enforce schema shape, and let the database enforce anything that must survive direct writes. Indexes exist at the database level; the API exposes endpoints the client queries.

Quick check · 11
Where would you enforce "email must be a valid email address"?
Client-side validation is for UX, not security. Any of your API routes can be called from a non-browser tool. Defence in depth: Express catches most cases, Mongoose catches the rest, and the database validator catches whatever bypasses both.

Interview questions

what you'll actually be asked

Q1What is MongoDB, and when would you pick it over a relational database?

MongoDB is a document-oriented NoSQL database. Pick it when the data is hierarchical or has an evolving schema (catalogues, user profiles with nested preferences, content with mixed shapes), when you need to scale writes horizontally, or when the JSON shape of the data matches what your API and UI already use. Stick with relational databases when the data is deeply relational, joins are common at scale, or the schema is stable and enforced strictly.

Q2What is the difference between a MongoDB document and a SQL row?

A document is a BSON (binary JSON) object that can contain nested objects, arrays, dates, and other rich types. A SQL row is a flat set of columns with fixed types, defined by the table. To model hierarchy in SQL you use additional tables and joins; in MongoDB you often embed it.

Q3Embedded documents vs referenced documents — when do you use which?

Embed when the child is always read with the parent, the number of children is bounded (a few addresses, a small list of tags), and the child isn't shared. Reference when the child is queried independently, the number of children is unbounded (posts, orders, logs), or the child is shared between multiple parents. The 16 MB document size limit is the hard ceiling that forces a reference when an embedded array could grow.

Q4How would you model a 1:N relationship?

Two valid patterns. Child reference: put a parentId field on the child documents (the unbounded side) — best when N is large, because the child collection can be indexed and paginated. Parent reference: put an array of child _ids on the parent — best when N is small and bounded, and you always read the children with the parent.

Q5Are MongoDB transactions ACID?

Yes, since MongoDB 4.0 on replica sets (and 4.2 on sharded clusters), multi-document transactions are ACID. Single-document operations were always atomic. The caveat: transactions require a replica set (a standalone mongod doesn't support them), and they're slower than non-transactional writes, so reach for them only when two or more documents must change together.

Q6What's the difference between replication and sharding?

Replication = the same data on multiple servers, for high availability and durability. If the primary dies, a secondary takes over. It doesn't help write throughput because writes go through one primary.
Sharding = different data on different servers, for horizontal scale. Data is partitioned by a shard key across multiple shards, so writes and storage spread. You need both at scale: each shard is itself a replica set.

Q7What is a change stream?

A cursor that emits events (insert, update, delete, replace) as documents change in a collection, database, or deployment. It's built on the replica set's oplog and requires a replica set. Use it for real-time features (push updates to WebSocket clients, sync with other services, trigger workflows). Change streams are resumable — save the _id of the last change and restart with resumeAfter.

Q8How do you ensure data validation in MongoDB?

Two layers. At the database level, a $jsonSchema validator on a collection (via createCollection or collMod) enforces shape regardless of which application writes. At the application level, Mongoose schema options (required, min, max, match, custom validators) provide fast feedback and richer logic before the write is sent. Use both for anything that must survive bulk imports, other services, or shell access.

Q9What's the difference between populate and $lookup?

populate is a Mongoose-level feature — it does extra queries in Node to replace reference IDs with full documents. Easy to use, but multiple round trips and no aggregation. $lookup is a MongoDB aggregation stage — the join happens server-side, in one round trip, and gives you full pipeline access (filter, sort, project the joined data). Use populate for simple "fetch the referenced doc", $lookup when you need to filter on the joined collection's fields or shape the result.

Q10How would you design a shard key?

A good shard key has high cardinality (many distinct values), even write distribution (no single shard takes most writes), and query alignment (your common queries include the shard key so they hit one shard instead of all). Avoid monotonic keys like _id or pure timestamps, which concentrate writes on the last chunk. Common choices: { tenantId: 'hashed' }, { userId: 'hashed' }, or a compound { tenantId: 'hashed', _id: 1 } when you need both even distribution and range queries within a tenant.

Q11What is GridFS, and when would you use it?

GridFS is MongoDB's protocol for storing files larger than the 16 MB document limit. It chunks the file into ~255 KB pieces in fs.chunks, with metadata in fs.files. Use it when you need files to live inside the database — for transactional guarantees with related data, for change streams on the metadata, or when you can't use an external store. For most production use cases (images, videos, PDFs), an object store like S3 or Cloudinary is cheaper and faster.

Q12How do you back up and monitor a MongoDB database in production?

Backup: on Atlas, use Cloud Backup / Point-in-Time Recovery — no scripts needed. Self-hosted: mongodump scheduled via cron, stored off-host (S3, another server). Monitoring: db.serverStatus() for connections, memory, opcounters; db.currentOp() for live slow queries; the profiler (setProfilingLevel(1, { slowms: 100 })) for anything above a threshold; and Atlas metrics for visual dashboards. Add application-level metrics — request latency, error rate — and alert on them.
