What React is

a library for building UI out of components · declarative · the mental model

React is a JavaScript library for building user interfaces out of components — small, reusable functions that take inputs (props) and return markup. You describe what the UI should look like for a given state, and React figures out the most efficient way to make the DOM match. That's what "declarative" means.

The shift from imperative to declarative

Imperative (plain JS)Declarative (React)
document.getElementById('c').textContent = count; find the element, change it <p>{count}</p>; just say what it should be
Remember which nodes need updating in which order Let React decide — it has the full picture
Bugs from partial updates, stale references Every render is a fresh description of the truth
The one sentence

A React component is a function that returns UI as a function of its props and state. When state changes, React re-runs the function and reconciles the result with the real DOM, touching only what changed.

Quick check · 01
What does "declarative UI" mean in React?
Declarative means describing the result, not the steps. React compares the description to what's on screen and updates the difference.

JSX

what it compiles to · expressions · conditionals · lists · fragments

JSX is HTML-looking syntax that compiles to React.createElement() calls. It's not a template language — it's JavaScript, so everything you can do in JS, you can do inside { }.

jsx-to-js
// This JSX…
const el = <h1 className="title">Hello, {name}!</h1>;

// …compiles to this
const el = React.createElement(
  'h1',
  { className: 'title' },
  'Hello, ', name, '!'
);

Expression, conditionals, lists

jsx.tsx
function Card({ user, isAdmin, tags }) {
  return (
    <div className="card">
      {/* expression */}
      <h2>{user.name.toUpperCase()}</h2>

      {/* ternary */}
      <p>{isAdmin ? 'Admin' : 'Member'}</p>

      {/* && for optional rendering */}
      {user.age >= 18 && <p>Adult</p>}

      {/* list — each child needs a stable key */}
      <ul>
        {tags.map(t => <li key={t.id}>{t.label}</li>)}
      </ul>
    </div>
  );
}

Fragments

A component must return a single root. Use a fragment to return multiple siblings without adding a DOM node:

fragments.jsx
return (
  <>
    <h1>Title</h1>
    <p>Body</p>
  </>
);
⚠️
Three JSX rules you'll forget at least once. 1) className, not class. 2) Every element must be closed, even <img /> and <br />. 3) Attribute names are camelCase — onClick, htmlFor, tabIndex — not the HTML lowercase versions.
Quick check · 02
Why does {items.map(x => <li>{x} produce a React warning?
Keys let React match items across renders. Without them React falls back to index-based matching, which causes bugs when the list reorders or items are added/removed.

Components & props

function components · props · children · composition · one-way data flow

components.jsx
// A component is just a function. Name it with a capital letter.
function Greeting({ name, emoji = '👋' }) {
  return <p>Hi {name} {emoji}</p>;
}

// Usage — props look like HTML attributes
<Greeting name="Aarav" />
<Greeting name="Priya" emoji="🎉" />

// children — nested JSX is passed as a prop called `children`
function Card({ title, children }) {
  return (
    <div className="card">
      <h3>{title}</h3>
      <div className="body">{children}</div>
    </div>
  );
}
<Card title="Hello"><p>Anything goes here</p></Card>

Props are read-only

A component must never mutate its own props. If a child needs to change something, it calls a function passed down by the parent. This is one-way data flow — state always flows from parent to child, changes flow back up via callbacks.

Composition beats inheritance

React has no class inheritance for components. Instead, you compose: <Card> takes children, <Layout> takes content in slots. Everything flexible is built from composition, which is simpler and less error-prone than inheritance.

Quick check · 03
A child component wants to change a value that lives in the parent's state. What should it do?
Props are read-only. The parent owns its state. To change it, the parent gives the child a callback that calls the parent's state setter. That's one-way flow with change events bubbling up via function props.

State — useState

what triggers re-render · functional updates · state is a snapshot

State is data that changes over time and should trigger a re-render when it does. useState returns the current value and a setter function.

useState.jsx
import { useState } from 'react';

function Counter() {
  const [count, setCount] = useState(0);

  return (
    <div>
      <p>{count}</p>
      <button onClick={() => setCount(count + 1)}>+1</button>
      <button onClick={() => setCount(c => c + 1)}>+1 (functional)</button>
    </div>
  );
}

Functional updates — when the new value depends on the old

setCount(count + 1) uses the value from the current render. setCount(c => c + 1) uses the latest value when the update runs. In an event that fires three times in one render, the first adds 1; the second adds 3.

batching
// ✗ Ends up +1, because all three use the same `count`
setCount(count + 1);
setCount(count + 1);
setCount(count + 1);

// ✓ Ends up +3, because each sees the previous result
setCount(c => c + 1);
setCount(c => c + 1);
setCount(c => c + 1);
State is a snapshot

Inside a single render, count is constant — it's a snapshot of state at that render. Setting state schedules a new render; it doesn't change count in the current one. If you log count immediately after setCount(count + 1), you see the old value.

Updating objects and arrays

Never mutate state directly — always create a new object or array:

immutable updates
// object
setUser(u => ({ ...u, name: 'Aarav' }));

// array push
setItems(arr => [...arr, newItem]);

// array update by index
setItems(arr => arr.map((x, i) => i === idx ? { ...x, done: true } : x));

// array remove
setItems(arr => arr.filter(x => x.id !== id));
Quick check · 04
What does this log?
setCount(count + 1); console.log(count);
The current render is frozen. setCount queues an update that produces a future render with a new count. The local variable doesn't change retroactively.

useEffect — side effects

dependencies · cleanup · avoiding loops · what belongs in effects

An effect is code that runs after the render, for things that reach outside React: fetching data, subscribing to events, timers, DOM APIs. useEffect takes a function and a dependency array.

useEffect patterns
// Run after EVERY render (rarely what you want)
useEffect(() => { /* ... */ });

// Run ONCE on mount
useEffect(() => { /* fetch initial data */ }, []);

// Run on mount AND whenever `userId` changes
useEffect(() => { /* fetch this user */ }, [userId]);

// With cleanup — unsubscribe, cancel, clear
useEffect(() => {
  const id = setInterval(tick, 1000);
  return () => clearInterval(id);   // runs on unmount AND before next run
}, []);

The dependency array, precisely

DepsEffect runs
OmittedAfter every render
[]Once on mount (and cleanup on unmount)
[a]On mount + whenever a changes
[a, b]On mount + whenever a or b changes
⚠️
The infinite loop. If you set state inside an effect and that state appears in its own deps, you'll loop forever. useEffect(() => setX(x + 1), [x]) never stops. Fix: remove x from deps if it isn't needed, or use a functional update and only depend on the inputs that actually changed.

What NOT to put in an effect

  • Derived values. If total = items.length, don't store it in state — compute it in the render. State for derived data causes sync bugs.
  • Event handlers. Attach them via JSX onClick, not via addEventListener in an effect.
  • Fetching on every keystroke. Debounce the value first, then depend on the debounced value.
Quick check · 05
What happens if you return a cleanup function from useEffect?
Cleanup runs before the next run of the effect, and on unmount. That's how subscriptions stay correct across dep changes — old subscription is torn down, new one is set up.

The hooks tour

useRef · useReducer · useMemo · useCallback · useContext · custom hooks

useRef — a value that persists but doesn't trigger re-renders

useRef.jsx
// DOM ref
const inputRef = useRef(null);
<input ref={inputRef} />
<button onClick={() => inputRef.current.focus()}>Focus</button>

// Mutable box that survives renders
const renderCount = useRef(0);
renderCount.current += 1;   // no re-render

useReducer — for complex state transitions

useReducer.jsx
function reducer(state, action) {
  switch (action.type) {
    case 'increment': return { count: state.count + 1 };
    case 'decrement': return { count: state.count - 1 };
    case 'reset':     return { count: 0 };
    default: return state;
  }
}

const [state, dispatch] = useReducer(reducer, { count: 0 });
dispatch({ type: 'increment' });

Use useReducer when state is a small state machine (loading / success / error) or when multiple pieces of state always update together.

useMemo & useCallback — memoize expensive work or stable references

memo.jsx
// useMemo — cache the RESULT of a computation
const sorted = useMemo(() => [...items].sort((a, b) => a.score - b.score), [items]);

// useCallback — cache the FUNCTION itself (stable reference across renders)
const handleClick = useCallback(() => {
  setOpen(o => !o);
}, []);

// Common: pass a stable handler to a memoized child
const MemoizedChild = React.memo(Child);
⚠️
Don't wrap everything. useMemo and useCallback have a cost (comparison + cache). Use them when you've measured a slow render, or when a memoized child is re-rendering because a callback identity changed. Premature memoization makes code harder to read for no gain.

useContext — share data without prop drilling

useContext.jsx
const ThemeContext = React.createContext('light');

// Provider at the top
<ThemeContext.Provider value="dark">
  <App />
</ThemeContext.Provider>

// Any descendant — however deep
const theme = React.useContext(ThemeContext);

Context isn't a state manager — it's a way to pass a value through the tree. Pair it with useState or useReducer when the value needs to change.

Custom hooks — reusing stateful logic

useLocalStorage.js
function useLocalStorage(key, initial) {
  const [value, setValue] = useState(() => {
    try { return JSON.parse(localStorage.getItem(key)) ?? initial; }
    catch { return initial; }
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue];
}
Quick check · 06
What does useRef give you that useState doesn't?
Refs are for things you want to track without causing renders — DOM nodes, interval IDs, previous values, whether something has mounted.

Lists & keys

why keys exist · identity vs index · reordering bugs

A key is how React identifies which list item is which between renders. Without a stable key, React can't tell that a "rename" is a rename — it just sees a list of similar elements and reuses DOM nodes incorrectly.

keys.jsx
// ✓ Best: stable, unique id from the data
{items.map(item => <Row key={item.id} item={item} />)}

// ✓ Acceptable: id doesn't exist, but list is static and never reorders
{items.map((item, i) => <Row key={i} item={item} />)}

// ✗ Wrong: random keys force a full re-render of every row on every change
{items.map(item => <Row key={Math.random()} item={item} />)}
The index-key bug in one example

You have [A, B, C] rendered with index keys 0, 1, 2. You delete A → list becomes [B, C]. React sees key 0 (was A, now B) and key 1 (was B, now C) and reuses the same DOM nodes — but their internal state (input value, focus, scroll) belonged to A and B. The values "shift up". The fix is a stable id per item.

Quick check · 07
A list of todos uses key={index} and each todo has a text input. When the user deletes the first todo, values shift up. Why?
Index keys are positional. Delete the first item and every following item's index shrinks by 1, so the DOM nodes get re-associated. Stable ids prevent this because the identity travels with the item.

Forms — controlled components

value + onChange · multi-field forms · validation · uncontrolled escape hatch

In a controlled component, the input's value lives in React state. The state is the single source of truth: it renders into the input, and every keystroke calls onChange which updates state.

LoginForm.jsx
function LoginForm({ onSubmit }) {
  const [form, setForm] = useState({ email: '', password: '' });

  const handleChange = e => {
    const { name, value } = e.target;
    setForm(f => ({ ...f, [name]: value }));
  };

  const handleSubmit = e => {
    e.preventDefault();
    onSubmit(form);
  };

  return (
    <form onSubmit={handleSubmit}>
      <input name="email"    value={form.email}    onChange={handleChange} />
      <input name="password" value={form.password} onChange={handleChange} type="password" />
      <button type="submit">Log in</button>
    </form>
  );
}

Why controlled forms win

  • Validation while typing — state has every keystroke.
  • Conditional rendering — disable submit if email is empty, because you can read form.email.
  • Reset and prefill — set state to initial values and inputs update.
  • Transform input — uppercase, strip whitespace, format a phone number as they type.
Quick check · 08
What's missing if <input value={form.email} /> is "read-only" and ignores typing?
A controlled input with a value but no onChange has no way to update. React warns about this explicitly. Add the handler and the input becomes editable again.

A reusable data-fetching hook

useTodos.js
import { useState, useEffect } from 'react';
import { api } from './api';

export function useTodos() {
  const [todos, setTodos] = useState([]);
  const [loading, setLoading] = useState(true);
  const [error, setError] = useState(null);

  const load = async () => {
    setLoading(true);
    try {
      const { data } = await api.get('/todos');
      setTodos(data);
    } catch (err) {
      setError(err.message);
    } finally {
      setLoading(false);
    }
  };

  useEffect(() => { load(); }, []);

  // CREATE
  const create = async (title) => {
    const { data } = await api.post('/todos', { title });
    setTodos(t => [...t, data]);
  };

  // UPDATE
  const update = async (id, patch) => {
    const { data } = await api.patch(`/todos/${id}`, patch);
    setTodos(t => t.map(x => x.id === id ? data : x));
  };

  // DELETE
  const remove = async (id) => {
    await api.delete(`/todos/${id}`);
    setTodos(t => t.filter(x => x.id !== id));
  };

  return { todos, loading, error, reload: load, create, update, remove };
}

The component

TodosPage.jsx
export default function TodosPage() {
  const { todos, loading, error, create, update, remove } = useTodos();
  const [title, setTitle] = useState('');

  if (loading) return <p>Loading…</p>;
  if (error) return <p>Error: {error}</p>;

  return (
    <div>
      <form onSubmit={e => { e.preventDefault(); create(title); setTitle(''); }}>
        <input value={title} onChange={e => setTitle(e.target.value)} />
        <button>Add</button>
      </form>
      <ul>
        {todos.map(t => (
          <li key={t.id}>
            <input type="checkbox" checked={t.done}
              onChange={() => update(t.id, { done: !t.done })} />
            {t.title}
            <button onClick={() => remove(t.id)}>×</button>
          </li>
        ))}
      </ul>
    </div>
  );
}
💡
For production, consider TanStack Query. The hand-rolled useTodos above is perfect for learning and small apps. The moment you have multiple components fetching the same data, want cache + background refetch + dedup + optimistic updates for free, use TanStack Query (there's a dedicated note in this library).
Quick check · 09
After POST /todos succeeds, what should the UI do?
The whole point of optimistic or post-response updates is that the UI reflects the change instantly. Either push the server's returned item into state (which is what we do above) or refetch.

Authentication in React

auth context · storing the token · protected routes · refresh handling

Auth in a React app has three moving pieces: (1) a place to store the current user and token, (2) a login/logout flow, (3) a way to protect pages so unauthenticated users get redirected to login.

1. Auth context

AuthContext.jsx
import { createContext, useContext, useState, useEffect } from 'react';
import { api } from './api';

const AuthContext = createContext(null);

export function AuthProvider({ children }) {
  const [user, setUser]       = useState(null);
  const [loading, setLoading] = useState(true);

  // On mount, restore the session from the token
  useEffect(() => {
    const token = localStorage.getItem('token');
    if (!token) { setLoading(false); return; }

    api.get('/auth/me')
      .then(({ data }) => setUser(data))
      .catch(() => localStorage.removeItem('token'))
      .finally(() => setLoading(false));
  }, []);

  const login = async (email, password) => {
    const { data } = await api.post('/auth/login', { email, password });
    localStorage.setItem('token', data.token);
    setUser(data.user);
  };

  const logout = () => {
    localStorage.removeItem('token');
    setUser(null);
  };

  return (
    <AuthContext.Provider value={{ user, loading, login, logout }}>
      {children}
    </AuthContext.Provider>
  );
}

export function useAuth() {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error('useAuth must be used within <AuthProvider>');
  return ctx;
}

2. Protected route

ProtectedRoute.jsx
import { Navigate, useLocation } from 'react-router-dom';
import { useAuth } from './AuthContext';

export function ProtectedRoute({ children }) {
  const { user, loading } = useAuth();
  const location = useLocation();

  if (loading) return <p>Checking session…</p>;
  if (!user) return <Navigate to="/login" state={{ from: location }} replace />;

  return children;
}

Login form that redirects back

Login.jsx
function Login() {
  const { login } = useAuth();
  const navigate = useNavigate();
  const location = useLocation();
  const [email, setEmail] = useState('');
  const [password, setPassword] = useState('');
  const [error, setError] = useState(null);

  const submit = async e => {
    e.preventDefault();
    try {
      await login(email, password);
      navigate(location.state?.from?.pathname || '/', { replace: true });
    } catch (err) {
      setError(err.response?.data?.message || 'Login failed');
    }
  };

  return (
    <form onSubmit={submit}>
      <input value={email} onChange={e => setEmail(e.target.value)} />
      <input type="password" value={password} onChange={e => setPassword(e.target.value)} />
      {error && <p>{error}</p>}
      <button>Log in</button>
    </form>
  );
}
⚠️
localStorage is XSS-readable. Any script that runs on your page can read the token. If your app has any XSS risk (user-generated HTML, unsanitized markdown, a compromised dependency), the token is one exploit away. For high-security apps, store tokens in httpOnly cookies set by the backend and use withCredentials on Axios. localStorage is fine for many internal apps — understand the trade-off.
Quick check · 10
Where should a protected route redirect an unauthenticated user?
Saving the intended destination (via router state or a query param) makes the login flow feel seamless — after logging in, the user lands exactly where they wanted to go.

The data router — loaders & actions

React Router 6.4+ introduced a data router where each route can declare loader (fetch data before rendering) and action (handle form submissions). Data is available via useLoaderData(). It removes the fetch-in-useEffect dance.

data-router.jsx
import {
  createBrowserRouter, RouterProvider,
  useLoaderData, Form, redirect,
} from 'react-router-dom';

async function todosLoader() {
  const res = await fetch('/api/todos');
  return res.json();
}

async function createTodoAction({ request }) {
  const form = await request.formData();
  await fetch('/api/todos', {
    method: 'POST',
    body: JSON.stringify({ title: form.get('title') }),
    headers: { 'Content-Type': 'application/json' },
  });
  return redirect('/todos');
}

function Todos() {
  const todos = useLoaderData();
  return (
    <>
      <Form method="post">
        <input name="title" />
        <button>Add</button>
      </Form>
      <ul>{todos.map(t => <li key={t.id}>{t.title}</li>)}</ul>
    </>
  );
}

const router = createBrowserRouter([
  {
    path: '/todos',
    element: <Todos />,
    loader: todosLoader,
    action: createTodoAction,
  },
]);

export default function App() {
  return <RouterProvider router={router} />;
}

Quick check · 11
What does a route loader in the data router give you that a useEffect fetch doesn't?
The router waits for all matched loaders to resolve before rendering. The component reads data with useLoaderData() and there's no "loading" state to manage manually.

Behind the scenes

reconciliation · Fiber · render vs commit · batching · StrictMode

Understanding React internals isn't required to build apps, but it makes interview answers sharp and explains otherwise-mysterious bugs.

The render → commit cycle

  1. A state setter is called. React schedules a re-render of the component that owns the state. Multiple setState calls in the same event handler are batched into a single re-render.
  2. Render phase. React calls the component function, then its children's functions, producing new React elements. It builds a "work-in-progress" Fiber tree from those elements. This phase is pure — no DOM changes yet, no side effects. In concurrent mode it can be paused and resumed.
  3. Reconciliation. React compares the new tree to the previous one: same type + same key → update, different → replace. The diffing algorithm makes this fast — O(n) — because it uses two heuristics: different types mean replace, and keys identify list items.
  4. Commit phase. React walks the work-in-progress tree and applies only the diffs to the real DOM. This phase is synchronous and uninterruptible — the user sees a consistent update. Then the browser paints.
  5. Effects. After paint, React runs useEffect callbacks and their cleanups. This is why effects don't block paint. useLayoutEffect runs before paint — use it only for measurements that must happen before the user sees the frame.
Step 1 / 5

Virtual DOM & reconciliation

  • The virtual DOM is a plain JS object tree that describes what should be on screen. It's cheap to create and compare.
  • Reconciliation is the algorithm that diffs the new virtual tree against the old one and produces a minimal set of DOM operations.
  • React's diffing makes two simplifying assumptions: (1) elements of different types produce different subtrees (replace, don't diff), (2) key identifies list items across renders.
  • Result: O(n) diffing instead of the theoretical O(n³) tree diff.

Fiber

Fiber is the data structure that replaced the old stack reconciler. Each component instance is a Fiber node holding its state, hooks, effects, and pointers to child, sibling, and return (parent). This lets React:

  • Pause and resume work (concurrent rendering).
  • Prioritise updates — input keystrokes before a heavy list render.
  • Discard work in progress if state changes again before commit.

Batching

Multiple setState calls within the same synchronous event handler are batched into one re-render. Since React 18, this also applies to promises, timeouts, and native event handlers — not just React events.

batching.jsx
function handleClick() {
  setA(1);   // all three batched into ONE re-render
  setB(2);
  setC(3);
}

StrictMode

In development, <StrictMode> intentionally double-invokes some functions — component renders, effects, reducers — to catch impure code. A useEffect that runs twice in dev is supposed to happen. If your effect breaks on double-run, it has a bug: it probably didn't clean up its subscription, or it's mutating external state in a non-idempotent way. Production doesn't double-invoke.

Quick check · 12
Which phase is synchronous and cannot be interrupted?
The render phase can be interrupted and resumed (that's what Fiber enables). The commit phase must be synchronous because the DOM mutations have to happen together — you can't leave the UI half-updated.
Quick check · 13
Your useEffect fetches data and it fires twice in development. Is something broken?
StrictMode is a dev-only safety check. If the double-fetch bothers you, use an AbortController in the effect — the cleanup cancels the first fetch. That's exactly the bug StrictMode is trying to surface.

Interview questions

what you'll actually be asked

Q1What is React, and why is it declarative?

A JavaScript library for building user interfaces out of components. Declarative means you describe what the UI should look like for a given state, and React reconciles the DOM to match. You don't write DOM update steps yourself — React handles the diff.

Q2Props vs state?

Props are inputs passed from parent to child — read-only inside the child. State is data owned by a component that changes over time and triggers re-renders when updated. Props come from outside; state is internal.

Q3Why do we need keys in lists?

Keys give each list item a stable identity across renders. Without them React matches items positionally (by index), which breaks when items are inserted, removed, or reordered — especially when those items hold state (input values, focus, scroll). Use a stable unique id.

Q4What's the difference between controlled and uncontrolled components?

In a controlled component, the input's value comes from React state, and every keystroke goes through onChange to update state. In an uncontrolled component, the DOM owns the value; you read it via a ref on submit. Controlled components are the default choice — they enable validation, transforms, and conditional rendering.

Q5What does useEffect do, and how does the dependency array work?

It runs a side effect after render. With no deps, it runs after every render. With [], once on mount (and cleanup on unmount). With [a, b], whenever a or b changes. Cleanup runs on unmount and before the next run. Effects are for things outside React: fetching, subscriptions, timers, DOM APIs.

Q6What's the difference between useMemo, useCallback, and React.memo?

useMemo caches the result of an expensive computation between renders. useCallback caches a function so its reference stays stable. React.memo wraps a component so it skips re-render if its props are shallow-equal to the previous render. They're optimisations — measure before applying.

Q7What's the difference between useEffect and useLayoutEffect?

useEffect runs after the browser paints — non-blocking. useLayoutEffect runs synchronously before paint — blocking. Use useLayoutEffect only when you need to measure DOM and update layout before the user sees the frame (e.g. tooltip positioning). Otherwise, useEffect.

Q8Explain the virtual DOM and reconciliation.

The virtual DOM is an in-memory JS tree that describes the UI. On state change, React builds a new virtual tree, diffs it against the previous one (reconciliation), and applies the minimal set of DOM operations. The diffing is O(n) because React uses two heuristics: different types mean replace, and key identifies list items.

Q9What is React Fiber?

React's internal data structure and reconciliation engine. Each component is a Fiber node with state, effects, and pointers to child/sibling/parent. It enables concurrent rendering: React can pause, prioritise, resume, and abandon renders — which is what makes features like useTransition possible. The commit phase is still synchronous.

Q10What are the render and commit phases?

The render phase runs component functions, computes the new tree, and diffs it — pure, can be interrupted. The commit phase applies the DOM mutations and is synchronous/uninterruptible. useEffect runs after commit (after paint); useLayoutEffect runs after commit but before paint.

Q11Why does StrictMode double-run effects in development?

To surface missing cleanups and impure code. If your effect subscribes to something, the second run should be preceded by the cleanup from the first — otherwise you leak subscriptions. In production, effects run once. If double-run breaks your code, the fix is in your cleanup, not in React.

Q12How would you implement authentication in a React app?

(1) An AuthContext holding the current user + token, with login/logout functions. (2) A ProtectedRoute wrapper that redirects to /login if the user is null, saving the intended destination in router state. (3) An Axios interceptor that attaches the Authorization header to every request. (4) On mount, restore the session by calling /auth/me with the stored token. For security: prefer httpOnly cookies over localStorage if XSS is a concern.

Q13How do you do CRUD in React against a REST API?

Wrap the API in an Axios instance with a base URL and interceptors. Put data-fetching and mutation logic in a custom hook (useTodos) that owns loading/error/data state. The component calls the hook's create/update/remove functions and renders from todos. After mutations, update local state from the server response or refetch. For production-grade caching/invalidation, use TanStack Query.

Q14What's the difference between BrowserRouter and createBrowserRouter?

BrowserRouter is the classic component-based router with Routes/Route and data fetching inside components. createBrowserRouter (React Router 6.4+) is the data router: routes can declare loader (fetch before render) and action (handle form submissions), plus errorElement for route-level error handling. Use the data router when data loading is central; the classic one for simple apps.

Q15When does a component re-render?

On its own state update, on a parent re-render (unless memoized), on a context value change, or on a hook inside it updating (like useReducer dispatch). Setting state to the same value bails out. React batches multiple state updates in the same event into one render.

Q16Why is setState asynchronous?

Not truly async — it schedules an update. State in the current render is a snapshot; setting it produces a future render with a new snapshot. This is what makes batching and consistent rendering possible. If you need the latest value immediately, use a functional updater or a ref.

Q17How do you prevent unnecessary re-renders?

Measure first with React DevTools Profiler. Then: memoize heavy child components with React.memo; stabilize callback references with useCallback; memoize expensive computed values with useMemo; split state so unrelated updates don't re-render the whole tree; virtualize long lists; split code with React.lazy + Suspense.

Q18What's a custom hook, and what makes a valid one?

A function whose name starts with use that calls other hooks inside. It lets you extract stateful logic so multiple components can share it without duplicating the code. Rules: the name must start with use, it can only be called at the top level of a component or another hook, and it can call other hooks — useState, useEffect, useContext, and other custom hooks.

Q19How would you do optimistic updates in React?

Before the network call, update local state as if it succeeded. Store a snapshot of the previous state. On success, replace the optimistic item with the server's version. On failure, restore the snapshot and show an error. In TanStack Query, this is onMutate + cancelQueries + setQueryData, with rollback in onError.

Q20Should state go in React state, Context, Zustand, or TanStack Query?

Local state for anything only one component cares about (form input, modal open). Context for a value that rarely changes and is needed across the tree (theme, auth user). Zustand for client state shared across distant components (cart, UI flows). TanStack Query for server state (fetched data with caching and refetching). Using the right tool per concern keeps each simple.
