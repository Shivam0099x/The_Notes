01

Why Zod exists

TypeScript disappears at runtime · validation belongs at the boundary

Here's the fundamental problem Zod solves. TypeScript types are erased at compile time — they exist only while you're writing the code. When your Express server receives a request, it has no idea whether the body matches your User type. JSON.parse returns any. Whatever shape the client sent is now in your database.

the gap
interface User {
  email: string;
  age: number;
}

app.post('/users', (req, res) => {
  const user: User = req.body;  // TypeScript says this is fine
  // but req.body could be { email: 42, age: "hello" } at runtime
  // and TypeScript will NEVER check
});
The one thing Zod does

Zod defines a schema — a runtime object that knows how to validate data. The same schema also produces a TypeScript type via z.infer. So one definition gives you both:

· a function that checks data at runtime
· a TypeScript type you use everywhere else

There is exactly one source of truth. If the schema changes, the type changes. If the type changes, validation changes. Drift is impossible.

TypeScript aloneTypeScript + Zod
Types at compile timeYesYes
Validation at runtimeNoYes
Trusts external inputYes (danger)No — validates first
Frontend + backend agreeOnly by conventionSame schema imported on both sides
Error messages for the userYou write them by handCome from the schema
Works with form librariesNo direct integrationFirst-class via @hookform/resolvers
Quick check · 01
Your TypeScript interface says age: number, but the client sends "22" (a string). What does TypeScript do at runtime?
TypeScript compiles to JavaScript with the types stripped out. At runtime there is no age: number constraint — just the value the client sent. Zod adds a runtime check at the boundary so the string fails immediately with a clear error, before it reaches your logic.
02

Install & first schema

npm install · define · parse · infer

terminal
npm install zod

A schema is built from primitives, chained with validations, and then used to parse data. Parsing returns the typed value if the data is valid, and throws (or returns an error result) if not.

first-schema.ts
import { z } from 'zod';

// 1. Define the schema
const userSchema = z.object({
  name:  z.string().min(2),
  email: z.string().email(),
  age:   z.number().int().min(0),
});

// 2. Infer the TypeScript type from it
type User = z.infer<typeof userSchema>;
// { name: string; email: string; age: number }

// 3. Validate data at runtime
const input = { name: 'Aarav', email: 'a@x.com', age: 22 };
const user = userSchema.parse(input);    // typed User

const bad = { name: 'A', email: 'nope', age: -5 };
userSchema.parse(bad);   // throws ZodError with three issues
💡
Two outputs from one definition. z.infer<typeof schema> gives you the TypeScript type. schema.parse(data) gives you runtime validation. Use both. Never hand-write a TypeScript interface that duplicates a schema — the schema is the source of truth.

z.string().parse('hello');
z.number().parse(42);
z.boolean().parse(true);

Quick check · 02
What type does z.enum(['light', 'dark']) infer?
Enums narrow the type to the exact members. You get autocomplete on the two allowed values, and any other string fails validation. That's the whole reason to use z.enum instead of z.string().
04

String validations

min · max · length · email · url · uuid · regex · trim

strings.ts
// length
z.string().min(2);                  // at least 2 chars
z.string().max(100);                // at most 100
z.string().length(10);               // exactly 10

// format
z.string().email();
z.string().url();
z.string().uuid();
z.string().cuid();
z.string().datetime();
z.string().ip();
z.string().regex(/^[A-Z]{3}-\d{4}$/);   // custom pattern

// content checks
z.string().startsWith('https://');
z.string().endsWith('.pdf');
z.string().includes('admin');

// transformation
z.string().trim();                     // strips whitespace before further checks
z.string().toLowerCase();
z.string().toUpperCase();

// combine
z.string()
  .trim()
  .min(2, 'Name must be at least 2 characters')
  .max(80, 'Name must be under 80 characters');

z.string().email('Please enter a valid email');

Custom error messages

Every validator takes an optional message as the last argument, or an object with message (and optionally other data for error maps):

custom-messages.ts
z.string().min(8, 'Password must be at least 8 characters');
z.string().email({ message: 'That email looks invalid' });

// `required_error` fires when the value is missing entirely
z.string({ required_error: 'Name is required' })
  .min(2, { message: 'Too short' });
Quick check · 03
You want to strip leading/trailing spaces from a name and enforce a minimum length. Which order?
Chained validators run in order. .trim() first strips whitespace; then .min(2) checks the trimmed result. With .min(2).trim(), the length check happens before trimming — ' a' (length 3) would pass min(2) and then trim to 'a' (length 1, invalid).
05

Numbers & dates

int · positive · min/max · date ranges

numbers.ts
// numeric checks
z.number().int();
z.number().positive();       // > 0
z.number().nonnegative();    // >= 0
z.number().negative();       // < 0
z.number().min(0).max(150);
z.number().multipleOf(5);
z.number().finite();

// dates
z.date().min(new Date('2000-01-01'));
z.date().max(new Date());              // not in the future
💡
Money in Zod. Don't validate money with z.number() — floating-point numbers can't represent decimals exactly. Store in paise/cents as integers (and validate with z.number().int().nonnegative()), or use a string with a regex for exact decimal representation. Postgres NUMERIC columns + string schemas are the safest combination.
06

Objects

z.object · strip vs strict vs passthrough · extend · merge · pick · omit

Objects are where Zod shines most. A schema is a shape; Zod validates the shape and provides three different policies for extra fields you didn't define.

objects.ts
const userSchema = z.object({
  name:  z.string(),
  email: z.string().email(),
  age:   z.number().int().positive(),
});

userSchema.parse({
  name: 'Aarav', email: 'a@x.com', age: 22,
  role: 'admin',       // extra field
});
// result: { name, email, age }  (role is dropped)
MethodBehaviour on extra fieldsUse when
z.object({...})Strips them silentlyDefault — you don't want to accept unknown data
.strict()Errors on any extra fieldYou want to catch typos and unsupported fields
.passthrough()Keeps them in the resultYou're extending a partial shape and preserving fields
.catchall(schema)Validates extras against a schemaObjects with a known base + arbitrary additional data
strict vs strip vs passthrough
const strict = userSchema.strict();
strict.parse({ ..., role: 'admin' });      // throws: unrecognized key

const pass = userSchema.passthrough();
pass.parse({ ..., role: 'admin' });        // { ..., role: 'admin' }

const withMeta = userSchema.catchall(z.unknown());
withMeta.parse({ ..., anything: 42 });   // keeps extras

Extend, merge, pick, omit, partial, required

Object schemas compose. Every method returns a new schema — the original is unchanged.

composition.ts
// Extend — add fields
const adminSchema = userSchema.extend({
  role:     z.literal('admin'),
  permissions: z.array(z.string()),
});

// Merge — combine two schemas
const withTimestamps = userSchema.merge(z.object({
  createdAt: z.date(),
  updatedAt: z.date(),
}));

// Pick — keep only some fields
const userPreview = userSchema.pick({ name: true, email: true });

// Omit — drop some fields
const userCreate = userSchema.omit({ age: true });

// Partial — all fields optional (update payloads)
const userUpdate = userSchema.partial();

// Required — all fields required (even previously optional)
const userRequired = userSchema.required();

// DeepPartial — recurse into nested objects
const deepPartial = nestedSchema.deepPartial();
The most useful pattern for APIs

One base schema for the entity, then derive the API shapes:

createSchema = base.omit({ id: true, createdAt: true })
updateSchema = createSchema.partial()
responseSchema = base.extend({ id: z.string().uuid() })

Change the base once, and create/update/response are always in sync. Never hand-write three schemas that are almost the same.

Quick check · 04
Your server schema is z.object({ email: z.string().email() }). A client sends { email: 'a@x.com', admin: true }. What does parse return?
The default behaviour is strip — unknown keys are removed. This is a security feature: if the client sends admin: true but your schema doesn't include admin, it never reaches your code. Use .strict() to error instead of strip.
07

Arrays & tuples

z.array · min · max · length · nonempty · tuples

arrays.ts
// basic array
z.array(z.string());
z.array(z.number()).min(1);
z.array(z.string()).max(10);
z.array(z.string()).length(5);
z.array(z.string()).nonempty();      // at least one item

// array of objects
z.array(z.object({ id: z.number(), name: z.string() }));

// tuple — fixed length, fixed position types
const point = z.tuple([z.number(), z.number()]);
point.parse([10, 20]);        // ok
point.parse([10, 20, 30]);     // throws

// array with refine — unique items
z.array(z.string()).refine(
  arr => new Set(arr).size === arr.length,
  'Items must be unique'
);

Records (dynamic-key objects)

When you need an object whose keys you don't know in advance — like a map of settings, or a lookup table:

records.ts
z.record(z.string(), z.number());       // Record<string, number>
z.record(z.enum(['light', 'dark']), z.string());

// You can restrict key names with a regex
z.record(z.string().regex(/^[a-z]+$/), z.string());
08

Unions, intersections & literals

z.union · z.intersection · z.discriminatedUnion

unions.ts
// Union — any one of these
z.union([z.string(), z.number()]);       // string | number

// Intersection — all of these (object merge)
z.intersection(
  z.object({ id: z.number() }),
  z.object({ name: z.string() })
);                                      // { id: number; name: string }

// Literal
z.literal('admin');                    // 'admin'
z.literal(null);                       // null

// Enum
z.enum(['pending', 'active', 'inactive']);
💡
Union vs Discriminated union. z.union([A, B]) tries A, then B, then C — the first one that validates wins. z.discriminatedUnion('type', [A, B, C]) looks at the type field first, then checks only the matching schema. Discriminated unions are much faster and produce better error messages. Use them whenever your union members have a shared literal field — see §14.
09

Optional, nullable & default

the three-way split that trips everyone up

Three separate concepts. Mixing them up is the most common Zod mistake.

MethodAcceptsInferred type
.optional()The value, or undefined (or the key missing)T | undefined
.nullable()The value, or nullT | null
.nullish()The value, null, or undefinedT | null | undefined
.default(x)The value, or nothing (uses x)T (never missing — has default)
optional-nullable.ts
z.string().optional().parse(undefined);   // ok → undefined
z.string().optional().parse(null);        // throws — null is not undefined

z.string().nullable().parse(null);        // ok → null
z.string().nullable().parse(undefined);   // throws

z.string().nullish().parse(null);        // ok
z.string().nullish().parse(undefined);   // ok

z.string().default('anonymous').parse(undefined);   // 'anonymous'
⚠️
Optional in a JSON body vs FormData. A missing field in JSON is undefined. But when a form submits email= with no value, the field is the empty string "", not undefined. A schema like z.string().email().optional() accepts undefined but rejects "". Preprocess empty strings to undefined if this matters (see §16).
Quick check · 05
z.string().optional().parse(null). What happens?
Optional and nullable are different. To accept both, use .nullish(). This is why APIs frequently document null | T and undefined | T as distinct — and why Zod forces you to be precise about which one you mean.

parse vs safeParse

throwing vs returning · when to use which

Zod has two ways to run a schema against data. Choosing wrong makes your code either ugly or fragile.

MethodOn successOn failureUse for
.parse(data)Returns the parsed valueThrows ZodErrorData you expect to be valid — config files, internal transforms, cases where you'll wrap in try/catch anyway
.safeParse(data){ success: true, data }{ success: false, error }External input where invalid data is normal — request bodies, form submissions, API responses
.parseAsync(data)Promise resolving to valueRejectsSchemas with async refinements (§12)
.safeParseAsync(data)Promise of { success, data }Promise of { success: false, error }Async refinements + normal-invalid path
parse-and-safe.ts
const schema = z.object({ email: z.string().email() });

// parse — throws on failure
try {
  const result = schema.parse(input);
  console.log(result.email);
} catch (err) {
  if (err instanceof z.ZodError) {
    console.log(err.errors);
  }
}

// safeParse — returns a discriminated result
const result = schema.safeParse(input);
if (result.success) {
  console.log(result.data.email);    // typed
} else {
  console.log(result.error.errors);  // array of issues
}
Rule of thumb

parse for data you have no reason to doubt — an object you constructed in code, a config file you control, a response from your own service that you're about to use internally. safeParse for anything you don't control — request bodies from clients, third-party API responses, form submissions, environment variables. Error handling with safeParse is clean; with parse you end up wrapping everything in try/catch.

Type inference with z.infer

the schema IS the type

You almost never hand-write a TypeScript interface alongside a Zod schema. Use z.infer instead.

infer.ts
const userSchema = z.object({
  id:        z.string().uuid(),
  email:     z.string().email(),
  age:       z.number().int().positive(),
  nickname:  z.string().optional(),
  role:      z.enum(['user', 'admin']),
  createdAt: z.date(),
});

type User = z.infer<typeof userSchema>;
// type User = {
//   id: string;
//   email: string;
//   age: number;
//   nickname?: string;
//   role: 'user' | 'admin';
//   createdAt: Date;
// }

// Input type — useful when transforms change the shape
type UserInput = z.input<typeof userSchema>;
type UserOutput = z.output<typeof userSchema>;
// for schemas without transforms, input === output
⚠️
Don't duplicate types. If you have both interface User { ... } and const userSchema = z.object({ ... }), they will drift. One of them will eventually be updated and the other won't. Delete the interface and use z.infer. This is the single most important discipline when using Zod in a TypeScript codebase.

refine & superRefine

custom validation logic · multiple issues · field-level paths

Built-in validations cover formats. When you need logic — password match, cross-field checks, business rules — you add a refinement.

refine — one custom rule

refine.ts
// single rule
z.string().refine(
  (val) => val === 'admin' || val === 'user',
  { message: 'Role must be admin or user' }
);

// multiple rules, one field
z.string()
  .min(8)
  .refine((pw) => /[A-Z]/.test(pw), { message: 'Must contain an uppercase letter' })
  .refine((pw) => /\d/.test(pw),    { message: 'Must contain a digit' });

// refine can look at other fields — pass the whole object
const passwordSchema = z.object({
  password:        z.string().min(8),
  confirmPassword: z.string().min(8),
}).refine((data) => data.password === data.confirmPassword, {
  message: 'Passwords do not match',
  path:    ['confirmPassword'],   // attach the error to this field
});
💡
The path option is critical for forms. Without it, a cross-field refinement error attaches to the whole object — errors in react-hook-form shows nothing useful. With path: ['confirmPassword'], the error appears right under the confirm-password input where the user needs to see it.

superRefine — multiple issues from one refinement

refine adds one error per call. superRefine gives you a raw ctx so you can add as many issues as you need, with per-field paths.

superRefine.ts
const passwordSchema = z.object({
  password:        z.string(),
  confirmPassword: z.string(),
}).superRefine((data, ctx) => {
  if (data.password.length < 8) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: 'Password must be at least 8 characters',
      path: ['password'],
    });
  }
  if (!/[A-Z]/.test(data.password)) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: 'Password must contain an uppercase letter',
      path: ['password'],
    });
  }
  if (data.password !== data.confirmPassword) {
    ctx.addIssue({
      code: z.ZodIssueCode.custom,
      message: 'Passwords do not match',
      path: ['confirmPassword'],
    });
  }
});

Async refinements

Check uniqueness against the database (email already taken, username exists) with an async refine:

async-refine.ts
const userSchema = z.object({
  email: z.string().email(),
}).refine(
  async (data) => {
    const exists = await User.findOne({ email: data.email });
    return !exists;
  },
  { message: 'Email already in use', path: ['email'] }
);

// MUST use parseAsync / safeParseAsync
const result = await userSchema.safeParseAsync(data);
Quick check · 06
A cross-field validation fails ("passwords do not match"), but the error doesn't show under any input in your form. What's missing?
Form libraries read errors by field name. Without path, the error is a top-level issue and has no field to display. With path: ['confirmPassword'], RHF puts it on the confirm field.
13

transform

convert during validation · trim · parse ints · normalise emails

.transform() lets the schema change the value as part of validation. The type of the result is whatever the transform returns, not the input type.

transform.ts
// lowercase emails
const emailSchema = z.string()
  .email()
  .transform((s) => s.toLowerCase());
// input type: string, output type: string
// parse('AARAV@X.COM') → 'aarav@x.com'

// trim strings
z.string().trim();     // shorthand for transform(s => s.trim())

// parse a number from a string
const quantitySchema = z.string()
  .transform((s) => Number(s))
  .refine((n) => !isNaN(n), { message: 'Not a number' });
// input: string, output: number

// convert comma-separated string to array
const tagsSchema = z.string()
  .transform((s) => s.split(',').map((x) => x.trim()).filter(Boolean));
// parse('a, b, c') → ['a', 'b', 'c']
Input vs Output types

When a schema has a transform, the input type and the output type differ:

z.infer<typeof schema> → the output type (what comes out)
z.input<typeof schema> → the input type (what goes in)

For a form, useForm needs both: the form's internal values match the input type (e.g. a string the user typed), and the submit handler receives the output type (e.g. the parsed number).

⚠️
Don't transform to a different type in a form field. If the user is typing into a text input and your schema transforms the string to a number, the input will show a number — but the input's value prop expects a string. React will warn and the input breaks. Use transform for the final submit payload, or use z.coerce with care and pass strings to the input. See §19 for the react-hook-form pattern.
Quick check · 07
You have z.string().transform(s => Number(s)). What is z.infer<typeof schema>?
z.infer gives the output type. Use z.input if you need the input type. For a form, both matter — useForm's values match the input, and the submit handler receives the output.

Discriminated unions

the cleanest way to model state, events, API responses

A discriminated union is a union of object schemas that all share one literal field — the "discriminant". Zod uses that field to pick the right schema immediately, without trying each one in turn.

discriminated.ts
const paymentSchema = z.discriminatedUnion('method', [
  z.object({
    method: z.literal('card'),
    cardNumber: z.string().length(16),
    cvv:        z.string().length(3),
    expiry:     z.string().regex(/^\d{2}\/\d{2}$/),
  }),
  z.object({
    method: z.literal('upi'),
    upiId:  z.string().regex(/^[\w.-]+@[\w]+$/),
  }),
  z.object({
    method: z.literal('cod'),
    note:   z.string().optional(),
  }),
]);

type Payment = z.infer<typeof paymentSchema>;

// TypeScript narrows automatically
function handle(p: Payment) {
  switch (p.method) {
    case 'card': return p.cardNumber;    // TS knows this field exists
    case 'upi':  return p.upiId;         // and this one
    case 'cod':  return p.note;          // and this one
  }
}

Why it beats z.union

z.union([A, B, C])z.discriminatedUnion('type', [A, B, C])
SpeedTries A, then B, then CLooks at the discriminant and picks the right one
Error messages"Did not match any union member" — vague"cardNumber must be 16 characters" — precise
NarrowingWorks, but the compiler can't always tell which memberPerfect — TypeScript narrows on the discriminant
When to useMembers without a shared literal tagAnything that has a shared literal field (almost always)
Where you'll actually use this

· API responses — { status: 'success', data } | { status: 'error', message }
· Form state — { step: 'input' } | { step: 'processing' } | { step: 'done', id }
· Events — analytics events with different payloads per type
· Payments / checkout — different fields per payment method
· Notifications — different data per notification kind

Recursive schemas

z.lazy · trees, categories, comment threads

A recursive schema refers to itself. Since you can't use a variable before it's defined, wrap the schema in z.lazy(() => ...) to defer evaluation.

recursive.ts
type Category = {
  name:     string;
  children: Category[];
};

const categorySchema: z.ZodType<Category> = z.lazy(() =>
  z.object({
    name:     z.string().min(1),
    children: z.array(categorySchema),   // refers to itself
  })
);

// Now validates a tree of any depth
categorySchema.parse({
  name: 'Electronics',
  children: [
    { name: 'Phones', children: [{ name: 'Android', children: [] }] },
    { name: 'Laptops', children: [] },
  ],
});

Recursive comments

comments.ts
interface Comment {
  id:       string;
  body:     string;
  author:   string;
  replies:  Comment[];
}

const commentSchema: z.ZodType<Comment> = z.lazy(() =>
  z.object({
    id:      z.string(),
    body:    z.string().min(1),
    author:  z.string(),
    replies: z.array(commentSchema),
  })
);
16

preprocess, coerce & pipe

prepare data before validation · run schemas in sequence

z.preprocess — prepare data before validation

Useful when the incoming data is almost the right shape. You can convert it into the shape the schema expects before any validators run.

preprocess.ts
// empty strings become undefined (so optional() works with form data)
const optionalString = z.preprocess(
  (val) => (val === '' ? undefined : val),
  z.string().optional()
);

// parse JSON string into an object before validating
const jsonString = z.preprocess(
  (val) => {
    if (typeof val === 'string') {
      try { return JSON.parse(val); } catch { return val; }
    }
    return val;
  },
  z.object({ a: z.number() })
);

z.coerce — auto-cast, then validate

For values that come in the wrong type but are trivially convertible — query strings, form fields, headers.

coerce.ts
z.coerce.number().parse('42');       // 42
z.coerce.boolean().parse('true');    // true
z.coerce.date().parse('2024-01-01'); // Date
z.coerce.bigint().parse('123');     // 123n

// Useful for query params and env vars
const paginationSchema = z.object({
  page:  z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().max(100).default(10),
});

// Express: req.query is always strings
paginationSchema.parse({ page: '2', limit: '20' });
// { page: 2, limit: 20 }
⚠️
z.coerce.number().parse("") returns 0. Because Number("") === 0. That's often not what you want for a form field left empty. Handle it with preprocess (empty string → undefined) or by not coercing on form fields, and using string-based schemas there instead.

z.pipe — chain schemas

Pipe runs schema A first, then schema B on A's output. Different from .transform(): you can use a full Zod schema (with its own validations) as the second stage.

pipe.ts
// string → parse int → validate int range
const pageParam = z.string()
  .regex(/^\d+$/, 'Must be a number')
  .pipe(z.coerce.number().int().min(1));

pageParam.parse('5');    // 5
pageParam.parse('abc');  // throws "Must be a number"
17

Error handling

ZodError · flatten · format · field errors · global error map

When a schema fails, Zod throws (or returns) a ZodError whose .errors property is an array of ZodIssue objects, one per failure. Two helpers turn that into shapes you actually want.

error-shape.ts
const schema = z.object({
  email: z.string().email(),
  age:   z.number().min(18),
});

Backend: Express with Zod

validating body, query, params · a reusable middleware · typed handler

The pattern that scales: one middleware that takes schemas for body, query, and params, validates each, and passes the typed, parsed data to the handler via req.validated.

src/middleware/validate.js
import { z } from 'zod';

export function validate(schemas) {
  return (req, res, next) => {
    const errors = {};

    for (const source of ['body', 'query', 'params']) {
      if (!schemas[source]) continue;

      const result = schemas[source].safeParse(req[source]);
      if (!result.success) {
        Object.assign(errors, result.error.flatten().fieldErrors);
      } else {
        if (!req.validated) req.validated = {};
        req.validated[source] = result.data;
      }
    }

    if (Object.keys(errors).length > 0) {
      return res.status(400).json({ message: 'Validation failed', errors });
    }
    next();
  };
}

Using it — a full users route

src/routes/users.js
import { z } from 'zod';
import express from 'express';
import { validate } from '../middleware/validate.js';
import User from '../models/User.js';

const router = express.Router();

const createUserSchema = z.object({
  name:     z.string().trim().min(2).max(80),
  email:    z.string().email().transform(s => s.toLowerCase()),
  password: z.string().min(8).regex(/[A-Z]/).regex(/\d/),
  age:      z.coerce.number().int().min(0).max(150).optional(),
});

const listQuerySchema = z.object({
  page:  z.coerce.number().int().min(1).default(1),
  limit: z.coerce.number().int().min(1).max(100).default(20),
});

const idParamSchema = z.object({
  id: z.string().regex(/^[a-f\d]{24}$/i, 'Invalid user id'),
});

router.post(
  '/users',
  validate({ body: createUserSchema }),
  async (req, res) => {
    const user = await User.create(req.validated.body);
    res.status(201).json({ user });
  }
);

router.get(
  '/users',
  validate({ query: listQuerySchema }),
  async (req, res) => {
    const { page, limit } = req.validated.query;
    const users = await User.find().skip((page - 1) * limit).limit(limit);
    res.json({ users, page, limit });
  }
);

router.get(
  '/users/:id',
  validate({ params: idParamSchema }),
  async (req, res) => {
    const user = await User.findById(req.validated.params.id);
    if (!user) return res.status(404).json({ message: 'Not found' });
    res.json({ user });
  }
);
Why req.validated instead of overwriting req.body

You could overwrite req.body with result.data. Two reasons to use req.validated instead: (1) the parsed data has transforms applied (lowercased email, coerced numbers), and you want that separate from the raw input for logging and debugging; (2) some middleware runs after yours (rate limiting, logging) and expects the original req.body untouched. Keeping both means you can read the raw value if you need it.

Environment variables

This is where Zod earns its place immediately. Parsing process.env once at startup catches every missing or malformed environment variable before your app ever serves a request.

src/config/env.js
import { z } from 'zod';
import dotenv from 'dotenv';
dotenv.config();

const envSchema = z.object({
  NODE_ENV:     z.enum(['development', 'test', 'production']).default('development'),
  PORT:         z.coerce.number().default(3000),
  DATABASE_URL: z.string().url().startsWith('postgres'),
  JWT_SECRET:   z.string().min(32, 'JWT_SECRET must be at least 32 characters'),
  REDIS_URL:    z.string().url().optional(),
});

const parsed = envSchema.safeParse(process.env);

if (!parsed.success) {
  console.error('❌ Invalid environment variables:');
  console.error(parsed.error.flatten().fieldErrors);
  process.exit(1);
}

export const env = parsed.data;
💡
Fail fast. This file is imported once at startup. If JWT_SECRET is missing or too short, the process exits before serving a request. Without this, your app would run fine until the first login attempt, then crash — the "silent failure" that takes hours to debug.
Quick check · 09
Why is validating req.body with Zod better than trusting the TypeScript Body type?
The compiler can't know what arrives over HTTP. Zod is the runtime gatekeeper that makes the TypeScript type actually true — the handler can trust the parsed data because Zod verified it.

The standard integration is @hookform/resolvers/zod. It turns a Zod schema into a resolver that react-hook-form uses for validation, and it wires per-field errors automatically.

RegisterForm.jsx
import { useForm } from 'react-hook-form';
import { zodResolver } from '@hookform/resolvers/zod';
import { z } from 'zod';

const schema = z.object({
  name:     z.string().min(2, 'Name must be at least 2 characters'),
  email:    z.string().email('Enter a valid email'),
  password: z.string().min(8, 'Password must be at least 8 characters'),
  confirm:  z.string(),
}).refine((d) => d.password === d.confirm, {
  message: 'Passwords do not match',
  path: ['confirm'],
});

type RegisterInput = z.infer<typeof schema>;

export default function RegisterForm() {
  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm<RegisterInput>({
    resolver: zodResolver(schema),
    mode: 'onTouched',
  });

  const onSubmit = async (data: RegisterInput) => {
    await api.post('/auth/register', data);
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register('name')} />
      {errors.name && <p>{errors.name.message}</p>}

      <input {...register('email')} />
      {errors.email && <p>{errors.email.message}</p>}

      <input type="password" {...register('password')} />
      {errors.password && <p>{errors.password.message}</p>}

      <input type="password" {...register('confirm')} />
      {errors.confirm && <p>{errors.confirm.message}</p>}

      <button disabled={isSubmitting}>Register</button>
    </form>
  );
}

Displaying server-side errors

Zod validates on the client, but the server also validates. When the server says "email already taken", you need to display it on the same field.

server-error.ts
const { register, handleSubmit, setError, formState: { errors } } = useForm({
  resolver: zodResolver(schema),
});

const onSubmit = async (data) => {
  try {
    await api.post('/auth/register', data);
  } catch (err) {
    const serverErrors = err.response?.data?.errors;   // { email: ['Email already in use'] }
    if (serverErrors) {
      for (const [field, messages] of Object.entries(serverErrors)) {
        setError(field, { message: messages[0] });
      }
    }
  }
};
Two layers of validation, one schema

The client validates for UX — instant feedback, no round-trip. The server validates for trust — the client can be bypassed. Both use the same schema, imported from a shared file. The client can't send something the server rejects for format reasons; the server catches everything the client couldn't (like uniqueness against the database).

What this achieves

The exact same schema drives: the client form validation, the client's TypeScript type, the server's request validation, and the server's TypeScript type. Change min(2) to min(3) in the shared file, and both sides update at the next build. There is no "the frontend allows 2 characters but the server requires 3" bug — ever.

⚠️
Don't put frontend-only or backend-only logic in the shared schema. The shared schema must contain only the shape and rules that both sides agree on. Uniqueness checks (which require the database), password hashing, and access control belong on the backend. If a rule is truly frontend-only (like "confirm passwords match" if you never check it server-side), keep it in the frontend form schema, and merge it with the shared schema using .extend().

Interview questions

what you'll actually be asked

Q1What is Zod, and what does it solve?

A TypeScript-first schema declaration library. It validates data at runtime and infers TypeScript types from the same schema. It solves the gap between "TypeScript knows the type" and "data at runtime is guaranteed to match" — the gap that exists because TypeScript types are erased during compilation. With Zod, one definition gives both the compile-time type and the runtime check.

Q2How does Zod work with TypeScript?

You define a schema, and z.infer<typeof schema> gives you the TypeScript type. The schema is the single source of truth — both the runtime behaviour and the compile-time type come from it. Change the schema, and the type changes. No drift.

Q3What's the difference between parse and safeParse?

parse returns the parsed value or throws a ZodError. safeParse returns a discriminated result — { success: true, data } or { success: false, error }. Use safeParse for external input (request bodies, form submissions) because invalid data is normal and shouldn't throw. Use parse for internal data you expect to be valid, when you're already in a try/catch.

Q4What's the difference between optional, nullable, and nullish?

.optional() allows the value or undefined (or the key missing). .nullable() allows the value or null. .nullish() allows the value, null, or undefined. They're separate concerns; conflating them is the most common Zod mistake.

Q5What does z.object do with extra fields by default?

It strips them — they're silently removed from the parsed output. This is the default and it's a security feature: if your schema is { name, email } and the client sends { name, email, role: 'admin' }, role never reaches your handler. Use .strict() to error on extras, or .passthrough() to keep them (be careful with the latter).

Q6How would you validate a form in React using Zod?

Use react-hook-form with zodResolver(schema). Register fields with register('fieldName'). RHF runs the schema on submit (and on change if mode says so), populates formState.errors from the Zod issues, and calls your submit handler with the parsed data if valid. Cross-field refinements work as long as you add path so the error lands on the right field.

Q7How would you validate a request body in Express using Zod?

Write a middleware that takes schemas for body, query, params. For each, safeParse the corresponding req property. If it fails, respond 400 with error.flatten().fieldErrors. If it passes, attach the parsed data to req.validated and call next(). The handler reads req.validated.body and can trust it's typed and valid.

Q8What is a discriminated union, and why is it better than a plain union?

A union of object schemas that all have a shared literal field (the discriminant, like type or method). Zod reads that field to pick the right schema — faster, better error messages ("cardNumber must be 16 chars" instead of "did not match any union member"), and TypeScript narrows perfectly on the discriminant. Use it whenever members have a shared literal tag.

Q9What's the difference between refine and transform?

refine adds a rule — it returns a boolean and either passes or adds an error. The value is unchanged. transform changes the value — the schema's output type becomes whatever the transform returns. Often you use both: transform first (e.g. trim, lowercase), then refine (e.g. "must contain a digit").

Q10How do you handle async validation (like checking if an email is already taken)?

Use .refine(async (data) => ..., { message, path }). Then parseAsync or safeParseAsync — sync parse throws on async refinements. On the frontend with react-hook-form + zodResolver, the resolver already awaits async refinements. But beware: async refinements run on every validation pass, so debounce the input or do the check in the submit handler to avoid hammering the DB.

Q11What is z.input vs z.infer?

z.infer<T> (aka z.output) is the type that comes out of parse — after transforms. z.input<T> is the type that goes in. When a schema has transforms, they differ. In a form, you care about both: useForm's values type is the input, the submit payload is the output. Most of the time (no transforms), they're identical.

Q12How do you share schemas between frontend and backend?

Put them in a shared package (monorepo workspace, or a folder published as a private npm package). Both the frontend and backend import from it. The client uses zodResolver(schema) for forms; the backend uses the same schema in a validation middleware. Changes to the schema update both sides, eliminating the "client allows X, server requires Y" class of bug.

Q13What is .superRefine used for?

Like refine, but gives you a raw ctx so you can add multiple issues from one refinement, each with its own path. It's the right tool when a single validation rule produces multiple independent errors (e.g. password strength rules), or when the shape of one error depends on another. refine adds one error per call; superRefine adds as many as you like.

Q14How do you validate environment variables with Zod?

Define a schema for the env vars you need, safeParse(process.env) at startup, and if it fails, log the errors and exit the process. Export the parsed object typed. This catches missing or malformed env vars before your app serves a single request, instead of failing hours later when the first endpoint that needs them is called.

Q15How would you validate a nested object where some parts are optional?

Mirror the nesting in the schema. Use .optional() on the nested object itself: z.object({ address: z.object({ street: z.string() }).optional() }). Or use .partial() on the nested schema if all its fields should be optional. Use .deepPartial() if the whole tree should be optional (PATCH payloads). Avoid making everything optional — say what's actually optional.
