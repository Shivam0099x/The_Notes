What SQL is

declarative language · categories of SQL · how to read a query

SQL is a declarative language for querying relational databases. You don't tell the database how to find the data — you describe what you want, and the query optimizer figures out the fastest way to get it.

How to read a SELECT

You write a query in one order, but the database executes it in another. Understanding this internal order is the single biggest jump in SQL competence. See the animated stepper in the next section.

  1. FROM / JOIN runs first. It defines the source rows — one table, or multiple joined together. Nothing else can happen until the source is defined.
  2. WHERE filters individual rows. Any row failing the condition is gone. This is where you can't reference aggregates — they don't exist yet.
  3. GROUP BY collapses rows that share grouped columns into one row per group. Aggregates (COUNT, SUM) then operate on each group.
  4. HAVING filters groups, not rows. HAVING COUNT(*) > 5 works; WHERE COUNT(*) > 5 does not.
  5. SELECT computes expressions and applies aliases. This is the first point where aliases exist — which is why ORDER BY alias works but WHERE alias doesn't.
  6. ORDER BY sorts the result. Aliases from SELECT are available here.
  7. LIMIT / OFFSET returns a slice of the sorted result. Deep offsets are slow because the query still computes rows 1..offset internally.
Step 1 / 7
select.sql
-- all columns, all rows
SELECT * FROM users;

-- specific columns
SELECT id, name, email FROM users;

-- with alias
SELECT name AS full_name, age * 12 AS age_months FROM users;

-- filtered
SELECT * FROM users WHERE age >= 18 AND city = 'Pune';

-- sorted, paginated
SELECT * FROM users ORDER BY created_at DESC LIMIT 10 OFFSET 20;

-- distinct values
SELECT DISTINCT city FROM users;
Quick check · 01
Why can you use a column alias in ORDER BY but not in WHERE?
Execution order: FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT. Aliases are created in SELECT, so they're not available in WHERE or HAVING, but they are in ORDER BY.
03

WHERE & operators

comparison · logical · range · set · pattern · NULL handling

where.sql
-- comparison
WHERE age = 22
WHERE age <> 22            -- also !=
WHERE age > 18 AND age < 30

-- range (inclusive)
WHERE age BETWEEN 18 AND 30

-- set membership
WHERE city IN ('Pune', 'Mumbai', 'Delhi')
WHERE city NOT IN ('Test', 'Deleted')

-- pattern (LIKE) — % = any string, _ = single char
WHERE name LIKE 'A%'          -- starts with A
WHERE name LIKE '%singh'      -- ends with singh
WHERE name LIKE '%singh%'     -- contains singh
WHERE name LIKE '_arav'       -- 5 chars, ends in 'arav'

-- NULL: must use IS / IS NOT, never =
WHERE age IS NULL
WHERE age IS NOT NULL

-- logical operators
WHERE age >= 18 AND (city = 'Pune' OR city = 'Mumbai')
WHERE NOT active
⚠️
NULL is not 0, not '', not false. NULL means "unknown". Any comparison with NULL returns NULL (which WHERE treats as false). So age = NULL is never true — not even for rows where age is null. Always use IS NULL / IS NOT NULL. And be careful with NOT IN (list_with_null) — the whole predicate becomes unknown, so no rows match.

Quick check · 02
Why does WHERE age = NULL return zero rows?
NULL is not a value — it's the absence of a value. Any comparison with it returns NULL, and WHERE only keeps rows where the condition is true. IS NULL is the correct null test.

-- string

  CASE
    WHEN age < 18 THEN 'minor'
    WHEN age < 65 THEN 'adult'
    ELSE 'senior'
  END AS age_group
FROM users;
💡
CASE is the query builder's workhorse. Most "conditional column" logic in dashboards, reports, and data pipelines is CASE WHEN ... THEN ... END. Combined with aggregates, it lets you do multiple conditional sums in one query — e.g. SUM(CASE WHEN status = 'paid' THEN amount ELSE 0 END).
05

Aggregates & GROUP BY

COUNT · SUM · AVG · MIN · MAX · grouping · HAVING · conditional aggregates

aggregates.sql
-- single aggregate
SELECT COUNT(*), AVG(age), MIN(age), MAX(age) FROM users;

-- COUNT(*) counts rows; COUNT(col) counts non-null values
SELECT COUNT(*) AS total,
       COUNT(phone) AS with_phone
FROM users;

-- GROUP BY: one output row per group
SELECT city, COUNT(*) AS total_users
FROM users
GROUP BY city;

-- HAVING filters groups (WHERE can't — aggregates don't exist yet)
SELECT city, COUNT(*) AS total_users
FROM users
GROUP BY city
HAVING COUNT(*) > 10;

-- Conditional aggregates — multiple counts in one pass
SELECT
  COUNT(*) FILTER (WHERE active)     AS active_users,
  COUNT(*) FILTER (WHERE NOT active) AS inactive_users
FROM users;

-- Same with CASE (works in any database)
SELECT
  SUM(CASE WHEN status = 'paid'    THEN amount ELSE 0 END) AS paid_total,
  SUM(CASE WHEN status = 'pending' THEN amount ELSE 0 END) AS pending_total
FROM orders;
FunctionReturns
COUNT(*)Number of rows (includes nulls)
COUNT(col)Number of non-null values
COUNT(DISTINCT col)Number of distinct non-null values
SUM(col)Sum (null if all null)
AVG(col)Average of non-null values
MIN(col) / MAX(col)Smallest / largest value
STRING_AGG(col, ',')Concatenate values across rows
ARRAY_AGG(col)Collect values into an array
⚠️
Every non-aggregated column in SELECT must be in GROUP BY. SELECT name, COUNT(*) FROM users GROUP BY city fails because name isn't grouped — the database doesn't know which name to pick for each city. MySQL used to allow this (picking a random row); Postgres and most modern databases reject it, which is correct.
Quick check · 03
What's the difference between COUNT(*) and COUNT(phone)?
This is the difference between "how many users" and "how many users have a phone number". The first is row count; the second is non-null count for a specific column.

Joins

INNER · LEFT · RIGHT · FULL · CROSS · self-join · the ON vs WHERE trap

The four join types, visually← → keys also work

  1. Two tables. Users have ids 1–4. Orders reference users via user_id. Order 103 references 99, which doesn't exist. User 4 has no orders.
  2. INNER JOIN — only rows with a match on both sides. Users 1, 2, 3 joined with their orders. User 4 and order 103 are excluded. Result: 3 rows.
  3. LEFT JOIN — all rows from the left side, NULL on the right when there's no match. User 4 appears with NULL order columns. Order 103 is still excluded (it's on the right). Result: 4 rows.
  4. RIGHT JOIN — mirror of LEFT. Order 103 appears with NULL user columns. User 4 is excluded. Result: 4 rows.
  5. FULL OUTER JOIN — keeps both sides. User 4 appears with nulls, order 103 appears with nulls. Result: 5 rows.
  6. CROSS JOIN — every row of the left with every row of the right. 4 users × 4 orders = 16 rows. Rarely what you want, but occasionally exactly right (generating combinations).
Step 1 / 6
joins.sql
-- INNER: only matched rows
SELECT u.name, o.total
FROM users u
INNER JOIN orders o ON o.user_id = u.id;

-- LEFT: all users + their orders (null if none)
SELECT u.name, o.total
FROM users u
LEFT JOIN orders o ON o.user_id = u.id;

-- Users who have NOT placed an order: LEFT JOIN + IS NULL
SELECT u.name
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE o.id IS NULL;

-- Self-join: employees and their managers
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON e.manager_id = m.id;

-- Multiple joins
SELECT u.name, o.id AS order_id, p.name AS product
FROM users u
JOIN orders o ON o.user_id = u.id
JOIN order_items oi ON oi.order_id = o.id
JOIN products p ON p.id = oi.product_id;
⚠️
Filter on the right table belongs in ON, not WHERE, for a LEFT JOIN. LEFT JOIN orders o ON o.user_id = u.id WHERE o.status = 'paid' turns into an INNER JOIN — users with no orders have status = NULL, and NULL = 'paid' is false, so they get filtered out. Move the condition to the ON clause and the LEFT JOIN keeps its "keep all left rows" semantics.
Quick check · 04
"Find all users who have never placed an order." Which pattern?
INNER JOIN drops users without orders entirely. LEFT JOIN keeps them with NULL columns on the right, and IS NULL isolates exactly those users.
07

Subqueries

scalar · IN · EXISTS · correlated · IN vs EXISTS vs JOIN

subqueries.sql
-- Scalar subquery (returns one value)
SELECT name FROM users
WHERE age = (SELECT MAX(age) FROM users);

-- IN subquery
SELECT name FROM users
WHERE id IN (SELECT user_id FROM orders);

-- EXISTS subquery — stops at first match
SELECT u.name FROM users u
WHERE EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);

-- Correlated: inner references outer (potentially slow)
SELECT u.name,
  (SELECT COUNT(*) FROM orders o WHERE o.user_id = u.id) AS order_count
FROM users u;
Use whenNotes
INSmall sub-result set, "value is in this list"Materialises the inner result
EXISTS"Does at least one matching row exist"Short-circuits on first match
JOINYou need columns from both tablesUsually the fastest if indexed
💡
The triple-nested query is a warning sign. If you find yourself writing SELECT ... WHERE x IN (SELECT ... WHERE y IN (SELECT ...)), a CTE or a JOIN is almost always more readable and often faster. The optimizer can rewrite some of these, but not all — help it by writing the shape you want.
08

CTEs — the WITH clause

readable pipelines · recursive CTEs · materialization

A CTE (Common Table Expression) is a named subquery you can reference later. It exists to make complex queries readable.

cte.sql
-- Chain of stages, each readable
WITH active_users AS (
  SELECT * FROM users WHERE active = TRUE
),
user_order_counts AS (
  SELECT user_id, COUNT(*) AS order_count
  FROM orders
  GROUP BY user_id
)
SELECT u.name, COALESCE(c.order_count, 0) AS orders
FROM active_users u
LEFT JOIN user_order_counts c ON c.user_id = u.id;

Recursive CTEs

A recursive CTE has a base case, UNION ALL, and a recursive step that references itself. Used for hierarchies: org charts, category trees, comment threads, graphs.

recursive.sql
-- All employees under a manager, at any depth
WITH RECURSIVE reports AS (
  -- base: the starting employee
  SELECT id, name, manager_id
  FROM employees
  WHERE id = 1

  UNION ALL

  -- recursive step: children of everyone found so far
  SELECT e.id, e.name, e.manager_id
  FROM employees e
  JOIN reports r ON e.manager_id = r.id
)
SELECT * FROM reports;
💡
CTE ≠ faster. In Postgres 12+, non-recursive CTEs are inlined like subqueries. If you want them computed once and reused, write WITH name AS MATERIALIZED (...). This matters when the CTE is expensive and referenced multiple times.

Window functions

OVER · PARTITION BY · ROW_NUMBER · RANK · LAG · running totals · top-N per group

Window functions compute across a set of related rows without collapsing them into one row per group like GROUP BY does. This is the biggest single step from intermediate to advanced SQL.

window.sql
-- Rank users by age within each city
SELECT
  name, city, age,
  RANK() OVER (PARTITION BY city ORDER BY age DESC) AS rank_in_city
FROM users;

-- Running total of amount by day
SELECT
  day, amount,
  SUM(amount) OVER (ORDER BY day) AS running_total
FROM daily_sales;

-- Change from previous day (LAG)
SELECT
  day, amount,
  amount - LAG(amount) OVER (ORDER BY day) AS day_over_day
FROM daily_sales;

-- Top 2 highest-paid employees per department
SELECT * FROM (
  SELECT name, department, salary,
    ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS rn
  FROM employees
) t
WHERE rn <= 2;
FunctionWhat it does
ROW_NUMBER()1, 2, 3 — never ties
RANK()1, 2, 2, 4 — ties share rank, then jump
DENSE_RANK()1, 2, 2, 3 — ties share rank, no jump
LAG(col, n) / LEAD(col, n)Value from n rows before / after
FIRST_VALUE() / LAST_VALUE()First / last value in the window
NTILE(n)Split into n roughly-equal buckets
SUM / AVG / COUNT OVER (...)Aggregate without collapsing rows
GROUP BY vs PARTITION BY

GROUP BY city → one row per city. PARTITION BY city inside OVER → every row kept, with an extra column that describes the row relative to its city. Use GROUP BY for summaries; use PARTITION BY for "each row annotated with its rank / running total / previous value".

Quick check · 05
You need the top 3 orders (by amount) per customer. Which approach works?
This is the classic top-N-per-group query. GROUP BY collapses rows and can't return 3 rows per group. Window functions keep all rows and rank them, so the outer filter can pick the top N per partition.

CREATE · types · constraints · ALTER · DROP · TRUNCATE

ddl.sql
CREATE TABLE users (
  id         SERIAL PRIMARY KEY,
  email      TEXT UNIQUE NOT NULL,
  name       TEXT NOT NULL,
  age        INT CHECK (age >= 0),
  active     BOOLEAN NOT NULL DEFAULT TRUE,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

  id         BIGSERIAL PRIMARY KEY,
  user_id    INT NOT NULL,
  total      NUMERIC(10,2) NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE
);

-- Change column type
ALTER TABLE users ALTER COLUMN age TYPE BIGINT;

-- Add a constraint

-- Drop a table entirely
DROP TABLE orders;

-- Remove all rows but keep the table structure (faster than DELETE for full clears)

DML — write data

INSERT · UPDATE · DELETE · RETURNING · UPSERT

dml.sql
-- INSERT one row
INSERT INTO users (email, name, age)
VALUES ('aarav@x.com', 'Aarav', 22);

-- INSERT many
INSERT INTO users (email, name, age) VALUES
  ('priya@x.com', 'Priya', 20),
  ('neha@x.com',  'Neha',  24);

-- RETURNING: get the generated id back in the same statement
INSERT INTO users (email, name)
VALUES ('karan@x.com', 'Karan')
RETURNING id, created_at;

-- UPDATE — always scope with WHERE
UPDATE users SET age = age + 1 WHERE city = 'Pune';

-- UPDATE with RETURNING
UPDATE users
SET active = FALSE
WHERE created_at < NOW() - INTERVAL '1 year'
RETURNING id, email;

-- DELETE
DELETE FROM users WHERE active = FALSE;

-- UPSERT: insert, or update if the unique key already exists
INSERT INTO users (email, name, age)
VALUES ('aarav@x.com', 'Aarav S', 23)
ON CONFLICT (email)
DO UPDATE SET name = EXCLUDED.name, age = EXCLUDED.age;
⚠️
UPDATE and DELETE without WHERE touch every row. Before a destructive write, run the equivalent SELECT with the same WHERE and confirm the row count. Or wrap in a transaction, inspect, then COMMIT or ROLLBACK.

Plan nodeWhat it means

Index ScanUses an index to find rows, then fetches them from the table.

Composite index order matters

(city, age) helps queries filtering by city, or by city AND age. It does not help a query filtering only by age. Left-prefix rule — same as MongoDB compound indexes. Order the columns by equality first, then range, then sort, matching the queries that actually run.

Quick check · 06
You query WHERE city = 'Pune' AND age > 25. Which composite index is more effective?
With (city, age), the index seeks to Pune, then range-scans by age within the block. With (age, city), the age values are scattered across cities — much less efficient, and useless for a query filtering only by city.

Views, triggers & procedures

saved queries · automatic functions · callable procedures

views.sql
-- View: a saved SELECT
CREATE VIEW active_users AS
SELECT id, name, email FROM users WHERE active = TRUE;

-- Materialized view: physically stored, needs manual refresh
CREATE MATERIALIZED VIEW user_order_counts AS
SELECT u.id, COUNT(o.id) AS orders
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP BY u.id;

REFRESH MATERIALIZED VIEW user_order_counts;

-- Trigger: a function that runs automatically on data changes
CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS TRIGGER AS $$
BEGIN
  NEW.updated_at = NOW();
  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER trg_users_updated_at
BEFORE UPDATE ON users
FOR EACH ROW
EXECUTE FUNCTION set_updated_at();

-- Stored procedure: callable with CALL
CREATE PROCEDURE deactivate_old_users(IN cutoff INT)
LANGUAGE sql
AS $$
  UPDATE users SET active = FALSE WHERE age > cutoff;
$$;

CALL deactivate_old_users(65);

Interview questions

what you'll actually be asked

Q1What's the difference between WHERE and HAVING?

WHERE filters individual rows before grouping. HAVING filters groups after grouping — that's why aggregates work in HAVING but not in WHERE. If you don't have a GROUP BY, use WHERE.

Q2INNER JOIN vs LEFT JOIN — what's the difference?

INNER JOIN returns only rows that match on both sides. LEFT JOIN returns all rows from the left, with NULL on the right when there's no match. "Find users with no orders" is LEFT JOIN ... WHERE orders.id IS NULL — a pattern that catches people who try INNER + IS NULL.

Q3Why does WHERE x = NULL return no rows?

Because NULL means "unknown", and any comparison with NULL returns NULL — which WHERE treats as not-true. Use IS NULL. Even NULL = NULL is NULL, not true.

Q4What's the difference between COUNT(*), COUNT(col), and COUNT(DISTINCT col)?

COUNT(*) counts rows. COUNT(col) counts non-null values in that column. COUNT(DISTINCT col) counts distinct non-null values. This is how you answer "how many users", "how many users have a phone", and "how many distinct cities users are in" — three different aggregates on the same table.

Q5What's a window function, and how is it different from GROUP BY?

A window function computes across a set of related rows without collapsing them. GROUP BY city gives one row per city; PARTITION BY city inside OVER() gives every row with an extra column that describes the row relative to its city (rank, running total, previous value). The classic example: top-N-per-group requires a window function because GROUP BY can't return 3 rows per group.

Q6Explain ROW_NUMBER vs RANK vs DENSE_RANK.

For values 10, 20, 20, 30: ROW_NUMBER → 1, 2, 3, 4 (no ties, arbitrary order). RANK → 1, 2, 2, 4 (ties share, then jump). DENSE_RANK → 1, 2, 2, 3 (ties share, no jump). Use ROW_NUMBER for "pick one row per group"; RANK or DENSE_RANK when you want tied items to share a position.

Q7What's a CTE, and when would you use one over a subquery?

A Common Table Expression (WITH name AS (...)) is a named subquery. Use it when a query has multiple stages and readability matters, or when you need recursion. In Postgres 12+, non-recursive CTEs are inlined like subqueries, so performance is generally the same — the win is clarity and reusability.

Q8Why can't you use an alias defined in SELECT inside WHERE?

Because WHERE runs before SELECT in the execution order (FROM → WHERE → GROUP BY → HAVING → SELECT → ORDER BY → LIMIT). Aliases don't exist yet when WHERE is evaluated. ORDER BY runs after SELECT, so aliases work there.

Q9What's the difference between UNION and UNION ALL?

UNION removes duplicates — it sorts both result sets and merges. UNION ALL keeps everything, including duplicates. UNION ALL is faster because it skips the dedup step. Use UNION ALL unless you actually need duplicates removed.

Q10What does EXPLAIN ANALYZE do?

EXPLAIN shows the query plan the optimizer chose. EXPLAIN ANALYZE actually runs the query and shows real timing and row counts. Read: (1) node types — Seq Scan on a large table is usually the problem; (2) estimated vs actual rows — big gaps mean stale statistics; (3) buffers to see cache hits vs disk reads; (4) loops for Nested Loop joins — the inner plan runs once per outer row.

Q11When should you use a composite index instead of two single-column indexes?

When your query filters on both columns together (or filters on the first and sorts by the second). A composite index on (a, b) allows one combined seek and gives pre-sorted results by b within a. Two separate indexes force a bitmap intersection, which is usually slower. Order matters: equality first, then range or sort. Composite (a, b) also covers queries on a alone — but not on b alone.

Q12How do you find the second-highest salary?

Three common answers. (1) Window function: SELECT salary FROM (SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS r FROM employees) t WHERE r = 2. (2) Subquery: SELECT MAX(salary) FROM employees WHERE salary < (SELECT MAX(salary) FROM employees). (3) Offset: SELECT DISTINCT salary FROM employees ORDER BY salary DESC LIMIT 1 OFFSET 1. The window function is the most flexible (works for "Nth highest"), the OFFSET version is the shortest.

Q13What's the difference between DELETE, TRUNCATE, and DROP?

DELETE removes rows (can filter with WHERE), is transactional (can roll back), fires triggers, and is slowest. TRUNCATE removes all rows quickly (no WHERE), and is transactional in Postgres. DROP removes the table entirely — structure and data both gone. DELETE for selective removal, TRUNCATE for a full clear, DROP when you never want the table again.

Q14What is an UPSERT, and how do you do one?

Insert a row, or update it if a unique key already exists. In Postgres: INSERT ... ON CONFLICT (unique_col) DO UPDATE SET .... In MySQL: INSERT ... ON DUPLICATE KEY UPDATE .... It avoids the race condition in "select, if exists update else insert", which can lose data under concurrent writes.

Q15How would you paginate efficiently on a large table?

LIMIT/OFFSET is easy but scales badly — offsetting 100,000 rows still computes rows 1–100,000 first. Use keyset pagination: WHERE created_at < $lastSeen ORDER BY created_at DESC LIMIT 20. With an index on created_at, each page is a single index seek. The trade-off is you can't jump to page 500 directly — fine for infinite scroll, not for a "page 3 of 20" UI.
