01

Why Docker exists

"works on my machine" · VMs vs containers · what problem it actually solves

Before Docker, moving an app from a laptop to a server meant installing the right Node version, the right Postgres, the right system libs, the right environment variables — and hoping it all matched. "Works on my machine" was the standard failure mode. Docker fixes that by shipping the app with its whole environment, as a single portable image.

What a container actually is

A container is a process running on the host, isolated by Linux features:

  • Namespaces — give the process its own view of the filesystem, network, process tree, hostname, etc. It can't see other containers' processes.
  • Cgroups — limit how much CPU, memory, and I/O it can consume.
  • Union filesystem — layered read-only image + a writable layer on top. This is why containers start fast and share disk space.
Virtual MachineContainer

The one sentence

Docker packages your application and everything it needs to run into an image; that image runs as one or more identical containers on any machine with Docker, regardless of what the host has installed. Same image → same behaviour.

Quick check · 01
Why do containers boot in milliseconds, while VMs take seconds to minutes?
A VM runs a full OS with its own kernel. A container is a process on the host kernel, isolated with namespaces and cgroups. Starting a process is fast; booting an OS is not.
02

Install & verify

Docker Desktop vs Engine · hello-world

Two ways to run Docker:

  • Docker Desktop — one-click install for macOS/Windows/Linux; includes the daemon, CLI, Compose, and a GUI. Fine for local dev, licensing restriction for big companies.
  • Docker Engine — the daemon and CLI, no GUI. Install via your package manager on Linux; on mac/Windows you'll use Desktop.
verify install
docker --version
docker run hello-world
docker info

If hello-world runs, you're set. If it fails with "Cannot connect to the Docker daemon", the daemon isn't running — start Docker Desktop, or sudo systemctl start docker on Linux.

💡
Docker needs Linux. On macOS and Windows it runs a tiny Linux VM underneath (Desktop does this for you). That's why docker run ubuntu works on your Mac — you're running a Linux process inside a Linux VM the GUI manages for you.

Images & containers

layers · the class/instance distinction · pulling · running

The core mental model: an image is a class, a container is an instance. You build an image once, then run as many containers from it as you like. Each container has its own writable layer; the image stays read-only and shared.

Images are layered

Every instruction in a Dockerfile adds a layer. Layers are cached, reused, and shared between images. Two images based on node:20-alpine share the Alpine base layer on disk.

Image layers, from base to app← → keys also work

FROM node:20-alpine~140 MBbase

what changes when…

build status
no cache yet
  1. FROM node:20-alpine — the base image. Alpine is a tiny Linux distro (5 MB) with Node installed; the whole layer is ~140 MB. Everything else builds on top of this.
  2. WORKDIR /app — a metadata-only layer. Nearly free, but every subsequent command runs from /app.
  3. COPY package*.json ./ — copies just the manifest files first. This layer is cached until package.json changes — which is rare.
  4. RUN npm ci --omit=dev — installs production dependencies. Because layer 3 rarely changes, this expensive step is almost always cached. Change one source file and you don't re-run npm ci.
  5. COPY . . — copies the app source. This layer changes on every code edit — which is exactly why it comes after the npm install. Ordering by "changes least often first" is the single biggest lever on build speed.
  6. CMD [ "node", "server.js" ] — the default command when the container starts. A container is just this process — when it exits, the container stops.

Pulling & running

# run a container — Docker pulls it if you don't have it
docker run node:20-alpine node -e "console.log('hi')"

docker ps

docker ps -a

# stop and remove
docker stop container_id
docker rm container_id

# remove an image
docker rmi node:20-alpine
💡
docker run does three things: pulls the image if missing, creates a container from it, and starts it. If the process inside exits (like node -e "..." which prints and ends), the container stops — you won't see it in docker ps, but it's still there in docker ps -a until you docker rm it.
Quick check · 02
You run docker run node:20-alpine node -e "console.log('hi')". Then docker ps shows nothing. Why?
A container lives exactly as long as its main process. Printing then exiting stops the container. It's still visible with docker ps -a until you docker rm it.

The Dockerfile

every instruction · CMD vs ENTRYPOINT · ARG vs ENV · .dockerignore

A Dockerfile is a plain text file with instructions, one per line. Every line adds a layer to the image. Learn the instructions once and you can read any Dockerfile.

The reference

InstructionWhat it does
FROM image:tagSets the base image. Always pin the tag (node:20-alpine, not node:latest) — latest moves under you.
WORKDIR /pathSets the working directory for later commands and the container's default cwd.
COPY src destCopies files from the build context into the image. COPY . . copies everything except what's in .dockerignore.
ADD src destLike COPY but also unpacks tarballs and fetches URLs. Prefer COPY — ADD is surprising.
RUN cmdRuns a shell command at build time (installs packages, builds assets). Creates a layer.
ENV KEY=valueSets an environment variable at build time and runtime. Visible to any process in the container.
ARG NAME=defaultBuild-time variable, not available at runtime. Passed with --build-arg.
EXPOSE 3000Documents that the image listens on a port. Doesn't actually publish it — use docker run -p for that.
USER nameSwitches to a non-root user for later instructions and the container's runtime.
VOLUME /dataDeclares a mount point. Usually you set volumes at run time with -v instead.
HEALTHCHECKPeriodically runs a command to check if the container is healthy.
CMD [...]Default command — can be overridden at docker run.
ENTRYPOINT [...]The fixed command — arguments from docker run are appended to it.

A production-grade Node Dockerfile

Dockerfile
FROM node:20-alpine

# pin to a non-root user that already exists in the alpine image
USER node

WORKDIR /app

# copy only manifests first — lets npm ci stay cached when source changes
COPY --chown=node:node package*.json ./

RUN npm ci --omit=dev

# copy the rest
COPY --chown=node:node . .

ENV NODE_ENV=production
ENV PORT=3000

EXPOSE 3000

CMD ["node", "server.js"]

⚠️
Never bake secrets into an image. Anything passed via ARG, ENV, or COPY at build time ends up in image layers, and layers are readable by anyone with the image. Pass secrets at runtime with -e, --env-file, or a secret manager. For builds that need secrets (private npm, private git), use BuildKit's --secret mount — it doesn't persist in layers.

Quick check · 03
You want to change node:20-alpine to node:22-alpine without editing the Dockerfile. What do you do?
ARG before FROM is the standard way to parameterise the base image. ENV only affects the runtime environment, not the base image the Dockerfile picks.

Ports & the run command

-p · EXPOSE vs publish · -d · -it · --name · --rm

docker run — the flags you'll use
docker run \
  -d \                                    # detach — run in background
  -p 8080:3000 \                          # publish host:container port
  --name myapp \                          # give it a readable name
  --rm \                                  # auto-remove when it exits
  -e NODE_ENV=production \                # set an env var
  --env-file .env \                       # load env vars from a file
  -v /host/path:/container/path \         # bind mount
  --network mynet \                       # join a user-defined network
  myapp:1.0                             # image:tag

# interactive container — useful for debugging
docker run -it node:20-alpine sh

-p host:container

EXPOSE in the Dockerfile documents the port but doesn't publish it. To reach the container from your machine, use -p hostport:containerport:

  • -p 8080:3000 — your laptop's port 8080 forwards to the container's 3000
  • -p 3000 — picks a random host port for container port 3000 (view with docker port)
  • No -p — the container is only reachable from other containers on the same network
Quick check · 04
Your Node app listens on 3000 inside the container. You run docker run -p 8080:3000 myapp. Where do you open a browser?
The host port (8080) is what your browser sees. Docker forwards it to the container's port 3000. Nothing inside the container is reachable directly from the host — only through the published mapping.

Volumes — persisting data

container filesystem is ephemeral · named volumes · bind mounts · tmpfs

A container's filesystem is ephemeral. Delete the container, and everything the process wrote is gone. That's fine for a stateless web server, but data (Postgres, uploads, cache) needs to survive. Docker gives you three ways:

TypeManaged byStored on hostUse for
Named volumeDocker/var/lib/docker/volumes/Persistent app data (DB files, uploads)
Bind mountYouAny host path you specifyDev: mount source code so live edits work
tmpfsKernelRAM (never disk)Secrets, temp files, never-persist data
volumes
# named volume — created if it doesn't exist
docker volume create pgdata
docker run -d --name pg -v pgdata:/var/lib/postgresql/data postgres:16

# list volumes
docker volume ls

# bind mount — mount a host directory
docker run -d -p 3000:3000 \
  -v $(pwd):/app \
  -v /app/node_modules \      # keep container's node_modules, don't overwrite with host's
  node:20-alpine npm run dev

# inspect a volume (path on host)
docker volume inspect pgdata
The dev workflow trick

For development, bind-mount your source code so edits on your laptop appear instantly inside the container:

-v $(pwd):/app

But that overwrites the container's /app/node_modules (installed during build) with your host's. So add an anonymous volume on top:

-v /app/node_modules

Docker mounts that path from a fresh volume, keeping the container's dependencies intact. Two -v flags, one line, and your dev loop works.

⚠️
docker rm deletes the container's writable layer, not its volumes. If you run docker rm -v container you explicitly delete anonymous volumes too. Named volumes (pgdata, redis-data) are only deleted with docker volume rm or docker volume prune. This is why Postgres data survives even if you rebuild the container.
Quick check · 05
You run Postgres in a container and rebuild it. Data is gone. What did you forget?
Every write inside a container lands in the writable layer, which is discarded on docker rm. Mount a named volume at the DB's data directory and the files survive container rebuilds.

Networks

bridge · host · none · DNS by container name · user-defined networks

Containers on the same network can reach each other by name. This is how app talks to db without you hard-coding IPs.

network basics
# create a user-defined network
docker network create mynet

# run two containers on it
docker run -d --name db --network mynet postgres:16
docker run -d --name app --network mynet myapp

# from 'app', the DB is reachable as 'db:5432'
# DATABASE_URL=postgres://user:pass@db:5432/mydb

# list networks
docker network ls

Network types

DriverBehaviourUse for
bridgePrivate subnet per network, NAT to the host. Default for docker run.Most apps and services
hostContainer shares the host's network stack. No port mapping needed, but no isolation.High-perf single-purpose containers; rare
noneNo network at all.Batch jobs, security-sensitive tasks
overlayMulti-host networking (Swarm or Kubernetes).Clusters
Why user-defined networks beat the default bridge

On the default bridge network, containers can only reach each other by IP — localhost and names don't work. On a user-defined bridge, Docker runs an embedded DNS server, so db, redis, app are reachable by name. Always create a network; it's one command and it eliminates most "why can't I connect" problems.

Quick check · 06
Your app container needs to connect to Postgres at db:5432. What must be true?
Port publishing (-p) is only needed to reach the container from outside Docker. Container-to-container traffic uses the Docker network, with DNS resolution by container name.

Docker Compose

one YAML for the whole stack · depends_on · dev vs prod · profiles

Running docker run five times with the right flags is a nightmare. Compose lets you define the whole stack — app, Postgres, Redis, Nginx — in one compose.yaml and start it with one command. Compose creates a network automatically and names services so they resolve each other by their service name.

compose.yaml
services:
  app:
    build: .
    ports:
      - "3000:3000"
    environment:
      DATABASE_URL: postgres://user:pass@db:5432/mydb
      REDIS_URL: redis://cache:6379
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_started
    volumes:
      - .:/app
      - /app/node_modules
    command: npm run dev

  db:
    image: postgres:16
    environment:
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
      POSTGRES_DB: mydb
    volumes:
      - pgdata:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U user -d mydb"]
      interval: 5s
      timeout: 3s
      retries: 5

  cache:
    image: redis:7-alpine

volumes:
  pgdata:
compose commands
docker compose up -d              # start everything in background
docker compose logs -f app         # tail logs of one service
docker compose exec app sh         # shell into a running container
docker compose ps                 # list running services
docker compose down               # stop and remove everything
docker compose down -v            # ... including volumes (fresh DB)
docker compose build --no-cache    # rebuild images from scratch
docker compose up --build          # rebuild then start

The gotchas

  • depends_on does not wait for a service to be ready — only started. Postgres can take 5 seconds to accept connections. Use healthcheck + condition: service_healthy (as above).
  • Compose service names are DNS names. db and cache in the YAML resolve to their containers' IPs from inside app. Your code uses db:5432, not localhost:5432.
  • localhost inside a container means the container itself. This confuses everyone at least once. Use the service name, not localhost, when connecting between services.
  • compose down -v deletes named volumes. Useful for a fresh DB; dangerous in production.
💡
Use compose.override.yaml for dev-specific config. Compose automatically merges it over compose.yaml. Put dev-only volumes (.:/app) and commands (npm run dev) in the override; leave the base file clean for production.
Quick check · 07
Your app container tries to connect to localhost:5432 for Postgres and fails. Why?
Every container has its own loopback interface. localhost inside app only refers to app. Compose gives each service a DNS name equal to its key in the YAML — use that.

Multi-stage builds

build stage ≠ runtime stage · smaller, safer images

A single-stage Dockerfile keeps compilers, test runners, and dev dependencies in your final image. That's hundreds of MB of attack surface you don't need in production. Multi-stage builds solve this: you build the app in one stage, copy only the artefacts into a fresh, minimal final stage.

Dockerfile — multi-stage for a React + Express app
# ---- stage 1: build the frontend + install ALL deps
FROM node:20-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build   # produces /app/dist

# ---- stage 2: minimal runtime
FROM node:20-alpine AS runtime
WORKDIR /app
USER node

# install only production deps
COPY package*.json ./
RUN npm ci --omit=dev

# copy built assets and server code from the build stage
COPY --from=build /app/dist ./dist
COPY --from=build /app/server ./server

ENV NODE_ENV=production
EXPOSE 3000
CMD ["node", "server/index.js"]
What gets dropped

The final image doesn't include dev dependencies, source files that aren't needed at runtime, the build cache, or any layer from the build stage you didn't explicitly COPY --from. A typical Node app shrinks from 900 MB (single-stage with devDeps) to 150–180 MB (multi-stage with only prod deps). A Go app can go from 900 MB (with compiler) to 10 MB (static binary on scratch).

Quick check · 08
In a multi-stage Dockerfile, what ends up in the final image?
Only the last stage is the final image. Earlier stages exist purely for building; whatever you want from them must be explicitly COPY --from=stage path.

Registries & pushing images

Docker Hub · GHCR · tagging strategy · pulling on a server

An image you build locally lives on your laptop. To deploy it, you push it to a registry — a server that stores images by name and tag.

push to Docker Hub
docker login                          # authenticate

# tag with the registry prefix + username + repo
docker tag myapp:1.0 myusername/myapp:1.0
docker tag myapp:1.0 myusername/myapp:latest

docker push myusername/myapp:1.0
docker push myusername/myapp:latest

# on a server:
docker pull myusername/myapp:1.0
docker run -d -p 80:3000 myusername/myapp:1.0

Tagging strategy

  • Never rely on latest in production. It moves. Pin to a version or a git SHA.
  • Tag with the git commit SHA in CI: myapp:sha-abc1234 — you can trace an image back to the exact commit.
  • Also tag a stable alias: myapp:1.4.2 or myapp:production. When you deploy, use the version tag.

Quick check · 09
Why should production not rely on the latest tag?
Version-pinned tags guarantee you deploy exactly what you tested. latest is a moving pointer — a rollback could pull a different image than the one that was running.

Security

non-root · pinned base · scanning · secrets · no docker socket

The defaults aren't all terrible, but several practices take minutes and prevent real incidents:

RuleWhy
Run as non-root (USER node)A compromised process can't touch system files or escalate easily
Pin base image tags (node:20.11-alpine, not node:20, not latest)Reproducible builds; avoid surprise breakage when the tag mutates
Use minimal base images (alpine, distroless, slim)Fewer packages, fewer CVEs
Scan images (docker scout, Trivy, Snyk)Catches known-vulnerable dependencies in the base image and your packages
Don't bake secrets into imagesLayers are readable by anyone who can docker pull. Use runtime -e, secret managers, or BuildKit --secret
Don't mount the Docker socket (/var/run/docker.sock)That gives the container root on the host — you're effectively disabling isolation
Read-only filesystem (--read-only) where possibleBlocks many attack patterns; combine with explicit tmpfs/volume mounts
Resource limits (--memory, --cpus)A runaway container can't take down the host
hardened run
docker run -d \
  --user 1000:1000 \
  --read-only \
  --tmpfs /tmp \
  --memory "256m" \
  --cpus "0.5" \
  --cap-drop ALL \
  --security-opt no-new-privileges \
  -e NODE_ENV=production \
  --env-file /etc/myapp.env \
  myapp:1.0
⚠️
/var/run/docker.sock is root. Containers that mount the socket (common in CI tools, "Docker-in-Docker" workarounds) can spawn privileged containers, read host files, and effectively own the host. If you need to build images inside a container, use rootless Docker, Kaniko, or BuildKit — never share the socket with a container running untrusted code.
Quick check · 10
What's the security problem with COPY .env .env in a Dockerfile?
Docker layer history is preserved even if a later instruction deletes the file — every RUN, COPY, or ADD is a permanent layer. Once secrets are in the image, they're in the registry forever. Use runtime env vars or BuildKit secret mounts.

Docker in production

logging · health checks · restart policies · zero-downtime · orchestration

Logging

Write logs to stdout/stderr. Docker captures them, and every log aggregator (Loki, Datadog, CloudWatch) reads from there. Don't write to files inside the container — those files disappear with the container.

logging
# in your app: use stdout, not a file
console.log('User created', { id });      // goes to docker logs

# view logs
docker logs -f container_name

# limit log size per container
docker run --log-driver json-file --log-opt max-size=10m --log-opt max-file=3 myapp

Health checks & restart policies

run with restart policy
docker run -d --restart=unless-stopped myapp:1.0
Restart policyWhen it restarts
no (default)Never
on-failureOnly if it exits with a non-zero code
alwaysAlways, even on clean exit
unless-stoppedAlways, unless you explicitly stopped it
Health check vs restart

A healthcheck tells Docker (and orchestrators) whether the container is actually serving — the process may be alive but the DB connection is dead. A restart policy reacts to the process exiting. A container can be running (process up) but unhealthy (endpoint failing) for hours without a restart policy doing anything. Use both in production.

Zero-downtime deploys — briefly

Docker by itself doesn't do rolling updates. In production, you usually run containers on an orchestrator — Kubernetes, ECS, Nomad, Docker Swarm — which handles rolling update strategies, health checks, and load-balancing across multiple replicas. For a single-server small app, a plain docker compose up -d with a reverse proxy (Nginx, Caddy) and two replicas + restart policy covers most of the same ground manually.

OrchestratorWhen to use
Docker ComposeSingle host, dev or small prod, no rolling deploys
Docker SwarmMulti-host, simple, but increasingly niche
KubernetesReal production, multi-service, auto-scaling, rolling deploys
AWS ECS / GCP Cloud Run / Fly.ioManaged alternatives — you push images, they orchestrate
Quick check · 11
Your container's main process crashes at 3 AM. What restart policy should you set so the container comes back automatically?
Both on-failure and unless-stopped cover crashes. unless-stopped is the standard production choice — it restarts even on clean exit, but respects a manual docker stop.

Interview questions

the ones you'll actually be asked

Q1What is Docker, and what problem does it solve?

Docker packages an application and its dependencies into a portable image that runs identically on any machine with Docker. It solves the "works on my machine" problem by removing the dependency on what the host OS has installed — the container carries its own environment.

Q2What's the difference between an image and a container?

An image is a read-only, layered filesystem plus metadata — a template. A container is a running instance of an image, with its own writable layer on top and its own isolated process, network, and filesystem view. One image, many containers.

Q3What's the difference between a VM and a container?

A VM includes a full OS and its own kernel, running on virtualised hardware. A container shares the host kernel and is isolated via Linux namespaces and cgroups. Containers are lighter (MBs vs GBs), start faster (ms vs seconds), and are easier to run many of — but they offer weaker isolation than VMs.

Q4Explain the Dockerfile instructions you use most.

FROM sets the base image. WORKDIR sets the working directory. COPY copies files in from the build context. RUN executes commands at build time (each creates a layer). ENV sets a runtime env var; ARG sets a build-time-only var. CMD is the default command; ENTRYPOINT is the fixed command. EXPOSE documents a port. USER switches to a non-root user. HEALTHCHECK defines a readiness probe.

Q5CMD vs ENTRYPOINT — when do you use which?

CMD is the default command and can be overridden by docker run image other-cmd. ENTRYPOINT is the fixed command; args from docker run are appended to it. Use CMD for most apps (the primary process), and ENTRYPOINT when you're building a wrapper/CLI where a specific binary must always run. Combined, ENTRYPOINT sets the binary and CMD sets default args.

Q6What are Docker volumes, and why do you need them?

A container's writable layer is ephemeral — deleting the container deletes it. Volumes let data persist outside that layer. Named volumes (managed by Docker, stored under /var/lib/docker/volumes) are the correct choice for DBs and uploads. Bind mounts (a host directory mounted into the container) are correct for dev — source code edits reflect instantly. tmpfs mounts exist only in RAM and are used for secrets and temp files.

Q7How does container networking work?

Each container gets its own network namespace. Docker attaches it to a network (a bridge by default, or a user-defined bridge). On a user-defined bridge, containers are reachable by container/service name because Docker runs an embedded DNS. Only containers whose ports are published with -p are reachable from the host. Container-to-container traffic never goes through the host port — it uses the internal network directly.

Q8Why would a container reach the DB by name (db:5432) rather than localhost?

localhost inside a container is the container itself. The DB is in a different container, with its own loopback. On the same Docker network, Docker's embedded DNS resolves the service/container name to its container IP. So db:5432 reaches the Postgres container; localhost:5432 reaches only the app's own (empty) port 5432.

Q9What does docker compose do that docker run doesn't?

Compose defines multi-container stacks declaratively in one YAML: services, networks, volumes, env files, healthchecks, dependencies. One command (docker compose up) starts everything, creates the network, and wires up DNS names. It handles rebuilds, logs, exec, and teardown per service. docker run is one container at a time with flags repeated by hand.

Q10What is a multi-stage build, and why use one?

A Dockerfile with multiple FROM stages. The first stage builds (compiles TypeScript, builds the frontend, installs devDeps). The final stage copies only the artefacts it needs, using COPY --from=build. This drops dev dependencies, build tools, and source from the final image — smaller, faster to deploy, smaller attack surface, fewer CVEs.

Q11Why should a container run as non-root?

If the process is compromised, root inside the container can (a) modify the container's filesystem freely, (b) potentially escalate to the host if any kernel or configuration weaknesses exist, and (c) trigger container-escape vulnerabilities. Running as a non-root user (via USER) limits damage. Combine with --cap-drop ALL, --read-only, and --security-opt no-new-privileges.

Q12How would you reduce Docker image size?

1) Use a small base (alpine, slim, distroless). 2) Multi-stage builds so build tools and dev dependencies don't ship. 3) .dockerignore to keep node_modules, .git, and tests out of the build context. 4) Combine related RUN instructions into one layer (or use RUN --mount=type=cache) so intermediate files don't accumulate. 5) Remove package manager caches (rm -rf /var/cache/apk/*) after installing. 6) Use npm ci --omit=dev or a .npmrc that excludes devDependencies in the runtime stage.

Q13What is a healthcheck, and how is it different from a restart policy?

A healthcheck periodically runs a command inside the container to check if it's actually serving (e.g. an HTTP endpoint returns 200, or pg_isready passes). It reports a status (healthy, unhealthy) and, in orchestrators, triggers restart or removal. A restart policy is about the process exiting — it restarts the container when it dies. Both are needed: a container can be running but unhealthy.

Q14How do you handle secrets in Docker?

Never bake them into the image (ENV, ARG, COPY all create permanent layers). At runtime, pass them as env vars with -e or --env-file, or inject from a secrets manager (AWS Secrets Manager, Vault, Doppler) as env vars when the container starts. For build-time secrets (private npm, private git), use BuildKit's RUN --mount=type=secret — the secret is mounted only during that build step and never persisted.

Q15How do you do zero-downtime deploys with Docker?

Docker by itself doesn't — you need an orchestrator or a manual pattern. The standard approach with Kubernetes/ECS: run N replicas of the service behind a load balancer, deploy a new version, wait for the new pods/containers to pass health checks, then drain and terminate the old ones. With Compose on a single host: run two replicas behind Nginx, update one at a time, and use docker compose up -d --no-deps --scale app=2 --no-recreate app plus a proxy that routes to healthy instances.

Q16What is .dockerignore, and why does it matter?

It excludes files from the build context — the directory Docker sends to the daemon. Without it, you upload node_modules (which can contain binaries built for the wrong OS) and .env (which can leak secrets). It also makes builds faster by shrinking the context. Standard contents: node_modules, .git, .env*, Dockerfile, .dockerignore, dist, coverage, *.md.

Q17Why is copying host node_modules into a container a bug?

Native dependencies (like bcrypt, sharp, node-sass) are compiled for a specific OS and CPU architecture. If you npm install on macOS and then COPY . ., the image contains macOS-built binaries that fail to load in a Linux container with Error: invalid ELF header. Always install dependencies inside the image (RUN npm ci) and always add node_modules to .dockerignore.

Q18Difference between docker stop and docker kill?

docker stop sends SIGTERM to the container's main process, waits up to a grace period (default 10s) for it to exit cleanly, then SIGKILLs it. Use it — apps can flush logs, close DB connections, finish requests. docker kill sends SIGKILL immediately — the process dies without cleanup. Reserve kill for genuinely stuck containers.

Q19What happens to data written inside a container when it exits?

It stays in the container's writable layer as long as the container exists. If you docker rm the container, that layer is deleted and the data is gone. Only data on a volume (named or bind mount) survives container removal. So containers should be treated as stateless; anything persistent belongs on a volume.

Q20How would you containerise a Node + Postgres + Redis stack?

Write a Dockerfile for the Node app (multi-stage: build stage installs all deps and compiles TypeScript/React, runtime stage installs only prod deps). Write a compose.yaml with three services: app (build from the Dockerfile, publishes 3000, env vars for DATABASE_URL and REDIS_URL pointing at db and cache, depends_on with healthchecks), db (image postgres:16, named volume at /var/lib/postgresql/data, healthcheck pg_isready), and cache (image redis:7-alpine). docker compose up -d starts the whole stack, wired on one network, with DNS names db and cache.
