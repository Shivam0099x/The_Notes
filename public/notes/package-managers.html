01

Why package managers matter

sourcing · versioning · the two problems every package manager solves

Every Node.js project depends on other people's code. A package manager does two things: it sources those dependencies (downloads them from a registry) and it manages their versions (so a build on your laptop matches a build in CI matches a build on your colleague's machine). [citation:2]

But the way each manager stores those dependencies on disk is where they diverge wildly — and it's the single biggest source of their differences in speed, disk usage, and correctness.

The three files you must know

package.json — declares your dependencies (ranges, not exact versions).
package-lock.json / yarn.lock / pnpm-lock.yaml — pins the exact versions of every dependency and their transitive dependencies so installs are reproducible.
node_modules/ — the actual files on disk. Never commit it.

Version consistencyA lockfile records exact resolved versions — everyone installs the same tree
DeduplicationMultiple packages may need the same dependency — the manager decides how many copies exist
IsolationCan your code import a package it never declared? This is the "phantom dependency" problem
MonoreposManaging several packages in one repo, linked together
02

npm — the default

the original · flat node_modules · phantom dependencies

What it is

npm ships with Node.js. Every Node developer has it. It's the oldest (2010), the largest ecosystem, and the most universally supported — some tools assume an npm-style node_modules layout. [citation:1][citation:2]

How npm stores dependencies — the flat tree

Since npm v3, dependencies are hoisted to the top of node_modules whenever possible. If you install package A that depends on lodash, and package B that also depends on lodash, npm will put one lodash at the top and both A and B will use it. [citation:15]

npm's flat node_modules
node_modules/
├── A/
├── B/
└── lodash/        // one copy, shared by A and B

This solved the old npm v2 problem where nested node_modules folders made paths so deep that Windows couldn't handle them. But it created a new problem: phantom dependencies.

⚠️
Phantom dependencies. Because everything is hoisted, your code can import lodash from 'lodash' even if you never declared lodash in your package.json — because some other package installed it and hoisted it. It works until that other package changes or removes lodash, and then your code breaks with no obvious reason. [citation:5][citation:15]

Where npm does well

  • Zero setup — it's already there.
  • Universal compatibility — every tool, every CI, every tutorial assumes npm works.
  • Workspaces — npm has native workspace support since v7, though less feature-rich than Yarn's or pnpm's. [citation:7]
  • Predictable — the flat layout is what most of the ecosystem was built against.

Where npm struggles

  • Slow cold installs — it downloads and writes more than pnpm, and the flat tree has to be recomputed.
  • Disk waste — multi-version dependencies still result in duplicates. The cache helps, but the node_modules folder itself is bloated.
  • Phantom dependencies — the flat layout doesn't enforce that you declared what you import.
npm commands
npm install                    // install everything from package.json
npm install express            // add a dependency
npm install -D typescript      // add a dev dependency
npm install -g nodemon         // global install
npm run dev                    // run a script from package.json
npm ci                         // clean install from lockfile (CI)
npx create-react-app my-app    // run a package without installing globally
💡
npm ci in CI. Never run npm install in a CI pipeline — it can modify the lockfile and resolve different versions. npm ci installs exactly what the lockfile says, fails if package.json and the lockfile disagree, and is faster because it skips resolution.

03

Yarn — the challenger, then the reinventor

Classic vs Berry · PnP · workspaces · resolutions

What it is

Yarn was released by Facebook in 2016 to fix npm's problems: slow installs and non-deterministic version resolution. It introduced the yarn.lock lockfile and parallel downloads. Then it evolved. Today "Yarn" means two different things — Classic (v1) and Berry (v2+). [citation:4][citation:10]

Yarn Classic (v1) — the npm-but-better era

Yarn v1 uses the same flat node_modules layout as npm, with the same phantom dependency problem. Its advantages were speed (parallel installs, aggressive caching) and deterministic lockfiles. It's been in maintenance mode since 2020. [citation:4]

Yarn Berry (v2+) — the reinvention

Berry introduced Plug'n'Play (PnP) as the default install strategy. Instead of writing a node_modules folder, Yarn stores a .pnp.cjs file that maps every dependency to its exact location in the cache, and patches Node's module resolution to use that map. [citation:1][citation:10]

Yarn PnP — no node_modules
Project/
├── .pnp.cjs               // the resolution map
├── .yarn/cache/           // the actual packages (can be committed)
├── package.json
└── yarn.lock

// No node_modules/ folder at all

What PnP gives you

  • No phantom dependencies — the loader enforces your declared tree. If you didn't declare it, you can't import it. [citation:1]
  • Zero-installs — commit the cache, and a fresh clone needs no install step at all.
  • Speed — no filesystem writes means very fast installs. [citation:1]

What PnP costs you

  • Ecosystem compatibility. Some tools break because they assume a real node_modules folder. Many teams fall back to Yarn's nodeLinker: node-modules mode, which behaves like npm. [citation:5]
  • Debugging is different — you can't open node_modules and look at a package. You use yarn unplug to extract one.

Yarn's monorepo strengths

Yarn Berry has the most opinionated workspace tooling: constraints (lint your entire dependency tree), workspace profiles, the catalog: protocol for sharing versions across workspaces, and a built-in task runner for running commands across packages. [citation:1]

Yarn commands
yarn                           // install
yarn add express               // add a dependency
yarn add -D typescript         // dev dependency
yarn dlx create-react-app      // Berry equivalent of npx
yarn set version berry         // upgrade a project to Berry
yarn unplug lodash             // extract a package out of PnP cache
⚠️
Which Yarn are you using? yarn --version — if it says 1.x, you're on Classic. If it says 2.x, 3.x, or 4.x, you're on Berry. The audit command changed: Classic uses yarn audit, Berry uses yarn npm audit. A CI pipeline that kept yarn audit after migrating to Berry has been silently doing nothing. [citation:9]

04

pnpm — the efficient one

content-addressable store · hard links · symlinks · strict by default

What it is

pnpm ("performant npm") takes a fundamentally different approach: it stores every file once in a global content-addressable store, and every project's node_modules contains hard links to those files, arranged into a dependency tree using symlinks. [citation:3][citation:8]

  1. Every package version is downloaded once to a global content-addressable store (usually under ~/.local/share/pnpm/store or similar). Files are identified by their content hash, so the same file is never stored twice. [citation:3]
  2. When you install in a project, pnpm doesn't copy files — it creates hard links from the store into a hidden node_modules/.pnpm folder. Hard links share the same inode on disk, so the file contents occupy zero additional space. [citation:8]
  3. Inside node_modules/.pnpm, pnpm builds the actual dependency tree using symlinks. Each package's own node_modules contains symlinks to its dependencies, matching Node's module resolution algorithm. [citation:8]
  4. Your project's top-level node_modules gets symlinks only to your direct dependencies. That's why pnpm blocks phantom dependencies: if you didn't declare it, there's no symlink at the top level. [citation:8]
  5. The result: a node_modules folder that's a fraction of the size (often 50%+ smaller), installs faster (no file copying for already-cached packages), and can't import packages you never declared. The trade-off is a slightly more complex node_modules structure to look at. [citation:5]
Step 1 / 5

Where pnpm does well

  • Disk efficiency — hard links + global store mean multiple projects share dependency files. [citation:5]
  • Speed — the fastest of the three for most cold installs, because there's no file copying for cached packages. [citation:10]
  • Strictness — symlink-based isolation prevents phantom dependencies without needing a custom Node loader (unlike Yarn PnP). [citation:1]
  • Monorepo support — excellent, with pnpm-workspace.yaml and a catalog for shared versions.

Where pnpm struggles

  • Compatibility with broken packages. Some packages in the wild import dependencies they didn't declare. pnpm's strictness breaks them. There's a hoist escape hatch, but it reintroduces the problem. [citation:8]
  • Not shipped with Node. Requires a separate install (corepack enable or a direct install).
  • Symlink-based node_modules can confuse debugging tools that expect real files.
pnpm commands
pnpm install                   // install
pnpm add express               // add a dependency
pnpm add -D typescript         // dev dependency
pnpm dlx create-react-app      // equivalent of npx
pnpm store path                // where is the global store?
pnpm store prune               // clean unused packages from the store
pnpm -w add lodash              // add to the workspace root
Quick check · 01
Why does pnpm's node_modules use both hard links and symlinks?
Two separate problems: storing files once (solved by hard links to a content-addressable store) and representing a dependency graph on disk (solved by symlinks that mirror Node's resolution). One without the other would break either disk efficiency or correctness.

The one-line summary for each

npm — the safe default. Everything works with it, because everything is built for it.

pnpm — the efficient default. Fastest installs, smallest disk footprint, phantom dependencies blocked. The modern choice for new projects.

Yarn Berry — the opinionated choice. PnP is elegant when it works, painful when it doesn't. Its monorepo tooling is genuinely best-in-class. [citation:1]

Yarn Classic — legacy. If you're still on it, the only real reason is inertia.

Quick check · 02
Which manager solves the phantom dependency problem without requiring a custom Node.js loader?
Yarn PnP solves phantom deps by patching Node's module resolution with a loader. pnpm solves it structurally: only declared dependencies get a symlink at the top level, so undeclared imports fail with a normal "module not found" — no loader involved. [citation:1]

Migrating

npm → pnpm
rm -rf node_modules package-lock.json
pnpm import                    // reads package-lock.json and creates pnpm-lock.yaml
rm package-lock.json           // after import succeeds
pnpm install
⚠️
Never mix package managers in one project. If package-lock.json, yarn.lock, and pnpm-lock.yaml all exist, different team members will get different trees depending on which command they run. Pick one, delete the other lockfiles, and add an .npmrc or packageManager field to enforce it.

The trade-off in one sentence

npm trades speed and efficiency for universal compatibility. pnpm trades a slightly unusual node_modules layout for speed, disk savings, and strictness. Yarn Berry trades ecosystem compatibility for purity and monorepo tooling.

Quick check · 03
A team runs a 15-package monorepo and their CI builds are slow because every job downloads hundreds of MB of dependencies. Which manager is the strongest first choice?
pnpm was built for exactly this. npm's flat tree re-downloads and re-writes more per project. Yarn Berry with a committed cache is also strong, but pnpm's disk savings and install speed make it the safer default for a large repo. [citation:1][citation:5]

08

Interview questions

what you'll actually be asked

Q1Explain the difference between npm, Yarn, and pnpm.

All three install Node.js dependencies from the npm registry. npm is the default, using a flat hoisted node_modules. Yarn was built to fix npm's speed and version determinism — Classic (v1) uses a flat layout; Berry (v2+) defaults to Plug'n'Play (no node_modules, a resolution map instead). pnpm uses a global content-addressable store with hard links and symlinks to build a strict, nested node_modules. The core difference is how they store dependencies on disk, which drives their speed, disk usage, and whether phantom dependencies are possible.

Q2What are phantom dependencies, and which managers prevent them?

Phantom dependencies are packages your code can import without declaring them in package.json, because another package's dependency was hoisted to the top of node_modules. npm and Yarn Classic have this problem due to flat hoisting. pnpm prevents it through symlink isolation (only declared deps get a top-level link), and Yarn Berry prevents it through PnP's runtime enforcement of the declared tree. [citation:1][citation:5]

Q3How does pnpm achieve disk savings?

pnpm stores every package version once in a global content-addressable store. Project installs create hard links from the store into a hidden node_modules/.pnpm directory — hard links share the same inode on disk, so the file content takes zero additional space per project. Symlinks then build the dependency tree structure on top. The result is that ten projects using the same lodash version share one copy of lodash's files. [citation:3][citation:8]

Q4What is Yarn's Plug'n'Play (PnP), and why doesn't everyone use it?

PnP replaces node_modules with a .pnp.cjs file that maps every dependency to its location in the Yarn cache, plus a Node loader that resolves imports through the map. Benefits: no phantom dependencies, faster installs (no filesystem writes), zero-installs (commit the cache). Downside: some tools assume a real node_modules folder and break. Adopting PnP requires testing your whole toolchain, which many teams won't do. [citation:1][citation:5]

Q5Why is npm ci preferred over npm install in CI?

npm ci installs exactly what the lockfile specifies, without modifying it, and fails if the lockfile and package.json are out of sync. npm install may update the lockfile and resolve slightly different versions depending on the registry state. npm ci is also faster in CI because it skips resolution.

Q6Which package manager should a new monorepo use?

pnpm is the strongest default for most monorepos — fast installs, excellent workspace support, and its strictness catches missing dependency declarations early. Yarn Berry is a strong alternative if the team wants PnP's zero-installs and the more opinionated constraint/catalog tooling. npm workspaces work but are less feature-rich and slower at scale. [citation:1]

Q7What's the difference between Yarn Classic and Yarn Berry?

Classic is v1 — a flat node_modules manager with parallel installs and yarn.lock. It's been in maintenance mode since 2020. Berry is v2+ — a rewrite with PnP as the default, a different lockfile format, built-in Node version management, richer workspace tooling, and different commands (e.g. yarn npm audit instead of yarn audit). They're effectively different tools that share a name. [citation:4][citation:9]

Q8How would you migrate a project from npm to pnpm?

Remove node_modules and keep package-lock.json temporarily. Run pnpm import to convert the npm lockfile into pnpm-lock.yaml. Delete package-lock.json and run pnpm install. Add an .npmrc or packageManager field to prevent accidental npm usage. Then update CI to use pnpm install --frozen-lockfile. Watch for phantom dependencies that were working silently before — pnpm will expose them, which is the point.

Q9Does pnpm use hard links or symlinks? Why both?

Both, for different reasons. Hard links connect a project's copy of a package file back to the single global store copy, saving disk space — the file content exists once. Symlinks build the dependency graph inside node_modules so Node's resolution algorithm finds the right package for each import. Hard links solve storage; symlinks solve resolution. [citation:8]

Q10When would you NOT choose pnpm?

When the ecosystem compatibility cost outweighs the gains: a legacy project with tools that break on symlinked node_modules, a team already productive on Yarn Berry, or an environment that mandates npm (some hosting platforms assume it). Also when a package you depend on imports dependencies it didn't declare — pnpm will break it, and fixing someone else's package is not your job. [citation:5]
