Forms in React — every pattern, ranked

Six ways to handle a form in React, from the naive multi-state approach to react-hook-form. Each gets full code, honest trade-offs, and a verdict on when to use it. Then: validation, file uploads, multi-step forms, and interview questions.

useState × N single state object one handleChange useRef (single & multiple) react-hook-form Yup / Zod
01

What "handling a form" actually means

reading values · tracking changes · validation · submit · reset

Every form pattern in React, no matter how it looks, is trying to solve five problems. The differences between patterns are entirely about where the values live (React state or the DOM) and how much boilerplate you're willing to write.

ConcernWhat you need to answer
Reading valuesWhat has the user typed right now?
Tracking changesEvery keystroke that updates a value (or not — some patterns read on submit)
ValidationIs the current input valid? Should the submit button be enabled?
SubmitWhen the form is submitted, what payload do I send?
ResetAfter submit, how do I clear the form?

The fundamental choice

Controlled (state-driven)Uncontrolled (ref-driven)
Value lives inReact stateThe DOM node (accessed via ref)
React sees every keystroke?YesNo
Re-renders per keystroke?Yes (one per input, batched)No
Easy live validation?YesOnly if you pull values on submit
Simplest code?For 1–3 fieldsFor many fields or file inputs
Used by react-hook-form?OptionalBy default
The one idea

A controlled input is one where React owns the value: value={x} + onChange. An uncontrolled input is one where the DOM owns the value: ref={r}, read r.current.value when you need it. Every pattern below is a variation on how many inputs are controlled and how they're batched.

Pattern 1 — Multiple useState

one state per field · the beginner's pattern

01 Multiple useState hooks beginner

Every field gets its own useState. Each input has its own inline onChange that sets that specific state. Submit reads all the variables together.

RegisterForm.jsx
import { useState } from 'react';

function RegisterForm() {
  const [name, setName]         = useState('');
  const [email, setEmail]       = useState('');
  const [password, setPassword] = useState('');
  const [age, setAge]           = useState('');
  const [city, setCity]         = useState('');

  const submit = e => {
    e.preventDefault();
    console.log({ name, email, password, age, city });
  };

  return (
    <form onSubmit={submit}>
      <input value={name}     onChange={e => setName(e.target.value)} />
      <input value={email}    onChange={e => setEmail(e.target.value)} />
      <input value={password} onChange={e => setPassword(e.target.value)} type="password" />
      <input value={age}      onChange={e => setAge(e.target.value)} />
      <input value={city}     onChange={e => setCity(e.target.value)} />
      <button>Register</button>
    </form>
  );
}

What it's good at: being readable. Anyone reading this file can see, at a glance, every field and its value. No abstraction to trace through. That's why every React tutorial starts here.

Where it breaks: the moment the form has 8 fields. You get 8 useState lines, 8 onChange inline functions (each a fresh function every render), and 8 setters to remember. Adding a field means editing the top of the component, the form body, and the submit handler. Resetting means calling 8 setters.

Verdict: use for 1–3 field forms — a login form, a search bar, a single checkbox. Do not use for anything that might grow. The moment you write the fourth useState, switch to Pattern 2 or 3.
Quick check · 01
What re-renders when you type in one of the five inputs in this pattern?
State lives in the parent component. Any state update re-renders the whole component, and React reconciles all five inputs. Usually fine — the component is cheap — but it's the reason react-hook-form exists.

Pattern 2 — One state object

everything in one useState · the mid-tier pattern

02 Single state object intermediate

One useState holds the whole form as an object. Each input updates the object with a spread. Submit reads form.

RegisterForm.jsx
function RegisterForm() {
  const [form, setForm] = useState({
    name: '', email: '', password: '', age: '', city: '',
  });

  const submit = e => {
    e.preventDefault();
    console.log(form);
  };

  return (
    <form onSubmit={submit}>
      <input value={form.name}
        onChange={e => setForm(f => ({ ...f, name: e.target.value }))} />
      <input value={form.email}
        onChange={e => setForm(f => ({ ...f, email: e.target.value }))} />
      {/* ...same pattern for every field... */}
      <button>Register</button>
    </form>
  );
}

What it's good at: submit becomes trivial — onSubmit(form) sends everything at once. Reset is one line: setForm(initialValues). The state shape mirrors the payload shape, so validation and API calls stay clean.

Where it breaks: the spread in every onChange. Once the object has 10 fields, every keystroke creates a new object with 10 properties. That's the cost of immutability, and it's fine at this scale — but it's also where people start writing a shared handleChange (Pattern 3) or reaching for a library.

Verdict: this is the best "manual" pattern. It scales to 6–10 fields, keeps the state clean, and avoids the eight-setter noise of Pattern 1. Use it whenever you're not ready to introduce react-hook-form.
Quick check · 02
Why must the state update use f => ({ ...f, name: value }) and not form.name = value?
Mutating the existing object doesn't change the reference, so React thinks state hasn't changed and skips re-rendering. Spreading into a new object produces a new reference — which triggers the render.

Pattern 3 — Single handleChange

one state object + one change handler · the "grown-up" manual pattern

03 Single handleChange, name-based recommended (manual)

Same single state object, but one handleChange function for all inputs. It reads e.target.name (the input's name attribute) to know which key to update. Adding a field means adding the field to state and to JSX — no new handler, no new setter.

RegisterForm.jsx
function RegisterForm() {
  const [form, setForm] = useState({
    name: '', email: '', password: '', age: '', city: '',
  });

  const handleChange = e => {
    const { name, value, type, checked } = e.target;
    setForm(f => ({
      ...f,
      [name]: type === 'checkbox' ? checked : value,
    }));
  };

  const submit = e => {
    e.preventDefault();
    console.log(form);
  };

  return (
    <form onSubmit={submit}>
      <input name="name"     value={form.name}     onChange={handleChange} />
      <input name="email"    value={form.email}    onChange={handleChange} />
      <input name="password" value={form.password} onChange={handleChange} type="password" />
      <input name="age"      value={form.age}      onChange={handleChange} />
      <input name="city"     value={form.city}     onChange={handleChange} />
      <button>Register</button>
    </form>
  );
}

Why name matters

The computed key [name] is the whole trick. Without a name attribute, e.target.name is "", and setForm sets an empty key — you'll see state like { name: '', email: 'x', "": 'y' }. Every input must have a name that matches its key in state.

Handling checkboxes and selects

Checkboxes use checked, not value. That's why the handler branches on type === 'checkbox'. Selects and textareas use value just like text inputs — no special case needed.

Verdict: this is the best pattern you can write by hand. It scales to 15–20 fields, resets in one line, submits as a single object, and centralises change logic in one place. The only reason to reach for Pattern 6 is if you need input-level validation, error display per field, or dirty/touched state tracking — those get painful manually.
Quick check · 03
You added a new input <input value={form.phone} onChange={handleChange} /> but typing in it doesn't update state. Why?
The generic handleChange reads the key from e.target.name. Without a name attribute, it has nothing to key on. Add name="phone" and make sure phone: '' is in the initial state object.
Quick check · 04
How should this generic handler treat a checkbox? (You want to include a "terms accepted" checkbox.)
A checkbox's value is a fixed string (usually "on"); its current state is in checked. Hence the type === 'checkbox' ? checked : value branch in the handler.

Pattern 4 — Single useRef

uncontrolled · the DOM owns the values

04 Uncontrolled with one ref niche

An alternative to Pattern 2's state object: store the entire form in a single ref. The DOM holds the values on every keystroke — React only reads them when you actually need them (on submit). No re-renders while typing.

RegisterForm.jsx
import { useRef } from 'react';

function RegisterForm() {
  const formRef = useRef({});

  const submit = e => {
    e.preventDefault();
    console.log(formRef.current);
  };

  return (
    <form onSubmit={submit}>
      <input ref={el => (formRef.current.name = el)}
             name="name"
             onChange={e => (formRef.current.name = e.target.value)} />
      <input onChange={e => (formRef.current.email = e.target.value)} />
      {/* ...and so on for every field... */}
      <button>Register</button>
    </form>
  );
}
⚠️
This is worse than it looks. You still need an onChange per field to capture the value — but now those values are invisible to React. You can't render validation errors, you can't disable the submit button based on current values, and you can't reset the fields without touching the DOM. This pattern is rarely the right choice for a text form.

Where it actually shines: file inputs. A file input's value can't be set programmatically (security), so a controlled <input type="file" /> is impossible. The standard approach is a ref:

file-upload.jsx
const fileRef = useRef(null);
<input ref={fileRef} type="file" />

const submit = async e => {
  e.preventDefault();
  const file = fileRef.current.files[0];
  if (!file) return;
  const body = new FormData();
  body.append('avatar', file);
  await api.post('/upload', body);
};
Verdict: use a ref for file inputs and for one-off "grab this value on submit" cases. Don't use refs for text inputs in a form that needs live validation or visual feedback — you'll end up fighting the framework.

Pattern 5 — Multiple useRef

one ref per field · the older uncontrolled pattern

05 Multiple refs, one per input legacy

Every field gets its own ref. On submit, you read nameRef.current.value for each. This is what `useRef for forms looked like before controlled inputs took over, and it's still common in codebases that predate hooks entirely (the class-component version used React.createRef).

RegisterForm.jsx
function RegisterForm() {
  const nameRef     = useRef(null);
  const emailRef    = useRef(null);
  const passwordRef = useRef(null);

  const submit = e => {
    e.preventDefault();
    console.log({
      name: nameRef.current.value,
      email: emailRef.current.value,
      password: passwordRef.current.value,
    });
  };

  return (
    <form onSubmit={submit}>
      <input ref={nameRef} />
      <input ref={emailRef} />
      <input ref={passwordRef} type="password" />
      <button>Register</button>
    </form>
  );
}

What it's good at

  • Zero re-renders while typing — nothing updates until submit. Fast for very large forms.
  • No controlled-input boilerplate — no value + onChange on every input.
  • Works for uncontrolled-friendly inputs — files, dates, third-party widgets.

Where it breaks

  • No live validation. You can't show "email is invalid" while typing — React doesn't know the email.
  • No conditional UI. Can't disable submit when empty, can't show "password is too short" in real time.
  • Resetting means touching the DOM. nameRef.current.value = '', one per field.
  • Ref null-checking. Before the DOM mounts, ref.current is null. Any code that reads it (e.g. auto-focus on mount) must handle that.
Verdict: use for a form with 15+ fields where you only care about the payload at submit time (a settings page with 30 toggles, a form inside a wizard). For anything that needs inline feedback, use Pattern 3 or Pattern 6.
Quick check · 05
Why can't you show real-time validation errors with Pattern 5?
Reading a ref doesn't trigger re-renders. Validation logic needs to run against the current value — which requires React to know the value — which is the whole point of controlled inputs.

Pattern 6 — react-hook-form

the modern default · uncontrolled inputs + controlled API · built-in validation

06 react-hook-form production default

react-hook-form solves the tension between Pattern 3 (easy validation, but re-renders on every keystroke) and Pattern 5 (fast, but no live feedback). Internally it uses refs to register inputs, so typing doesn't re-render — but it exposes a controlled API so you can still read values, validate, and show errors on change of specific fields.

terminal
npm install react-hook-form

The basics

RegisterForm.jsx
import { useForm } from 'react-hook-form';

function RegisterForm() {
  const {
    register, handleSubmit, reset, formState: { errors, isSubmitting },
  } = useForm();

  const onSubmit = async data => {
    await api.post('/auth/register', data);
    reset();
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register('name', { required: 'Name is required' })} />
      {errors.name && <p>{errors.name.message}</p>}

      <input
        type="email"
        {...register('email', {
          required: 'Email is required',
          pattern: { value: /\S+@\S+\.\S+/, message: 'Invalid email' },
        })}
      />
      {errors.email && <p>{errors.email.message}</p>}

      <input
        type="password"
        {...register('password', {
          required: 'Password is required',
          minLength: { value: 8, message: 'At least 8 characters' },
        })}
      />
      {errors.password && <p>{errors.password.message}</p>}

      <button disabled={isSubmitting}>
        {isSubmitting ? 'Registering…' : 'Register'}
      </button>
    </form>
  );
}

How it works — the mental model

  1. register('fieldName') returns props (name, onChange, onBlur, ref). When spread onto an input, it registers the input with the form. No value prop — the input stays uncontrolled.
  2. handleSubmit(onSubmit) wraps your submit handler. It runs validation first; if validation fails, onSubmit isn't called and errors fills in. If it passes, onSubmit(data) receives the whole form as an object.
  3. formState.errors holds one entry per failed field. It only updates when needed, not on every keystroke.
  4. reset() clears all fields and errors — no per-field reset calls.
  5. isSubmitting is true between handleSubmit starting and the returned promise resolving. Ideal for disabling buttons.

Validation modes

By default, errors appear on submit. Change the timing with the mode option:

modeWhen errors show
onSubmit (default)After the user submits
onBlurWhen the user leaves a field
onChangeAfter every keystroke — great for search inputs, aggressive for password fields
onTouchedOn blur first, then on change after the field has been touched — the best UX in most cases
allOn blur AND on change
mode + default values
const { register, handleSubmit, formState: { errors, isValid } } = useForm({
  mode: 'onTouched',
  defaultValues: { name: '', email: '', password: '' },
});

Watching a value in real time

By default react-hook-form doesn't re-render on keystrokes. When you want to react to a specific field (e.g. show a live password strength meter), use watch:

watch
const password = watch('password', '');

<input type="password" {...register('password')} />
<div className={password.length >= 8 ? 'good' : 'weak'}>
  {password.length} characters
</div>

Only that field re-renders when password changes — the rest of the form stays quiet. That's the biggest behavioural win over Pattern 3.

Cross-field validation

"Confirm password must match password" needs two fields. Use validate with the values argument, or getValues:

validate
const { register, handleSubmit, getValues, formState: { errors } } = useForm();

<input type="password" {...register('password', { required: true })} />
<input
  type="password"
  {...register('confirm', {
    validate: v => v === getValues('password') || 'Passwords do not match',
  })}
/>
{errors.confirm && <p>{errors.confirm.message}</p>}
Verdict: the default for anything beyond a login form. You get validation, error tracking, submit lifecycle, reset, watch, and field arrays — all with less code than Pattern 3. The mental model is one extra concept ("register returns props"); everything else follows.
Quick check · 06
Why does react-hook-form avoid re-rendering the whole form on every keystroke?
The `ref` from register() gives RHF a handle to the DOM node. It reads .value when it needs it (validation, submit) without a re-render — same trick as Pattern 5, wrapped in a clean API with errors and submit lifecycle.
Quick check · 07
What does handleSubmit(onSubmit) do that onSubmit alone doesn't?
It's the gate: validation → errors or onSubmit. If validation fails, your handler is never called — you don't need to write "if (errors) return".

when to pick which

3 · Single handleChange Whole component Easy Up to ~20 fields The best manual pattern

Rule of thumb

1–3 fields, no validation: Pattern 1. 4–10 fields, needs validation: Pattern 3. Beyond that, or any kind of arrays / dynamic fields / multi-step: Pattern 6 (react-hook-form). Patterns 4 and 5 are tools for specific inputs (files, third-party widgets), not general form strategies.

Validation — Yup & Zod

schema validation · resolvers · typed errors

For anything beyond basic required/pattern checks, define your validation as a schema. Two ecosystems dominate:

YupZod
StyleChainable APIComposable, method chain
TypeScript inferenceGoodExcellent — the schema is the type
Default in RHF examplesLong-time defaultIncreasingly the new default
Bundle sizeLargerSmaller
Works for API validation tooYesYes — very common for Express/Fastify request bodies

With Yup

yup.jsx
import { useForm } from 'react-hook-form';
import { yupResolver } from '@hookform/resolvers/yup';
import * as yup from 'yup';

const schema = yup.object({
  name:     yup.string().required('Name is required'),
  email:    yup.string().email('Invalid email').required(),
  password: yup.string().min(8, 'At least 8 characters').required(),
  age:      yup.number().min(18, 'Must be 18+'),
});

const { register, handleSubmit, formState: { errors } } = useForm({
  resolver: yupResolver(schema),
});

With Zod

zod.jsx
import { zodResolver } from '@hookform/resolvers/zod';
import { z } from 'zod';

const schema = z.object({
  name:     z.string().min(1, 'Name is required'),
  email:    z.string().email('Invalid email'),
  password: z.string().min(8, 'At least 8 characters'),
  age:      z.number().min(18, 'Must be 18+'),
});

type FormData = z.infer<typeof schema>;

const { register, handleSubmit, formState: { errors } } = useForm<FormData>({
  resolver: zodResolver(schema),
});
💡
Same schema, both sides. Zod schemas work as API request validation on Express and as form validation in React. Define it once, import it on both sides — no drift between "what the form allows" and "what the server accepts". This is one of the strongest reasons to prefer Zod over Yup in modern MERN stacks.

Dynamic fields — useFieldArray

add/remove rows · the pattern react-hook-form makes trivial

Any "add another phone number" / "add line item" UI. Pattern 3 handles this badly (you'd manage an array in state, then map it, then give each row its own handler). useFieldArray turns it into three calls.

addresses.jsx
import { useForm, useFieldArray } from 'react-hook-form';

function Addresses() {
  const { register, control, handleSubmit } = useForm({
    defaultValues: { addresses: [{ line1: '' }] },
  });
  const { fields, append, remove } = useFieldArray({ control, name: 'addresses' });

  return (
    <form onSubmit={handleSubmit(d => console.log(d))}>
      {fields.map((field, i) => (
        <div key={field.id}>
          <input {...register(`addresses.${i}.line1`)} />
          <button type="button" onClick={() => remove(i)}>Remove</button>
        </div>
      ))}
      <button type="button" onClick={() => append({ line1: '' })}>
        Add address
      </button>
      <button>Submit</button>
    </form>
  );
}
💡
Use field.id as the React key, not the index. useFieldArray generates a stable id per row. Index keys break the same way they always do — remove row 1 and inputs shift values up.

The submit lifecycle, everywhere

double submit · network errors · reset on success

Whichever pattern you use, the submit handler needs to handle the same things: prevent double-submit, show loading, catch errors, reset or redirect on success. Here's the shape, using Pattern 3 (adapt to any other pattern):

submit.jsx
const [form, setForm] = useState({ email: '', password: '' });
const [submitting, setSubmitting] = useState(false);
const [serverError, setServerError] = useState(null);

const submit = async e => {
  e.preventDefault();
  if (submitting) return;                     // guard double submit

  setSubmitting(true);
  setServerError(null);
  try {
    await api.post('/auth/login', form);
    setForm({ email: '', password: '' });     // reset on success
    navigate('/dashboard');
  } catch (err) {
    setServerError(err.response?.data?.message || 'Something went wrong');
  } finally {
    setSubmitting(false);
  }
};

<button type="submit" disabled={submitting}>
  {submitting ? 'Submitting…' : 'Submit'}
</button>

In react-hook-form

The same lifecycle is built in: isSubmitting for the loading state, handleSubmit for the guard, and if onSubmit throws, RHF keeps isSubmitting true until the promise settles — no need to write your own flag.

rhf-submit.jsx
const onSubmit = async data => {
  try {
    await api.post('/auth/login', data);
    reset();
    navigate('/dashboard');
  } catch (err) {
    setError('root.server', { message: err.response?.data?.message });
  }
};

File uploads

file input is uncontrolled by nature · FormData · progress

File inputs cannot be controlled — the browser forbids setting input.value from JavaScript for security reasons. So the pattern is always "uncontrolled with a ref, plus state if you want to preview or validate".

AvatarUpload.jsx
import { useRef, useState } from 'react';

function AvatarUpload() {
  const fileRef = useRef(null);
  const [preview, setPreview] = useState(null);
  const [progress, setProgress] = useState(0);

  const onChange = e => {
    const file = e.target.files[0];
    if (file) setPreview(URL.createObjectURL(file));
  };

  const submit = async () => {
    const file = fileRef.current.files[0];
    if (!file) return;

    const body = new FormData();
    body.append('avatar', file);

    await api.post('/upload', body, {
      headers: { 'Content-Type': 'multipart/form-data' },
      onUploadProgress: e =>
        setProgress(Math.round((e.loaded * 100) / e.total)),
    });
  };

  return (
    <div>
      <input ref={fileRef} type="file" onChange={onChange} />
      {preview && <img src={preview} alt="" width="80" />}
      {progress > 0 && <progress value={progress} max="100" />}
      <button onClick={submit}>Upload</button>
    </div>
  );
}
⚠️
Never set Content-Type manually on FormData requests. Your browser must include the multipart boundary in the header. If you hard-code 'multipart/form-data', the boundary is missing and the server can't parse the body. Axios sets it correctly if you leave it alone — remove that header from the code above and it still works. Same story for fetch.

In react-hook-form

RHF supports files via register too — the browser gives you a FileList. You then wrap it in FormData before sending:

rhf-file.jsx
const { register, handleSubmit } = useForm();

const onSubmit = async ({ avatar }) => {
  const body = new FormData();
  body.append('avatar', avatar[0]);
  await api.post('/upload', body);
};

<input type="file" {...register('avatar')} />

Multi-step forms

shared state across steps · validation per step · back navigation

The classic onboarding wizard: step 1 collects the profile, step 2 the address, step 3 confirms. Two ways to structure it, and both are valid.

Option A — one form, one state, conditional UI

Wizard.jsx
function Wizard() {
  const [step, setStep] = useState(1);
  const [data, setData] = useState({ name: '', city: '', pin: '' });

  const next = () => setStep(s => s + 1);
  const back = () => setStep(s => s - 1);

  return (
    <>
      {step === 1 && <Step1 data={data} onChange={setData} onNext={next} />}
      {step === 2 && <Step2 data={data} onChange={setData} onNext={next} onBack={back} />}
      {step === 3 && <Confirm data={data} onBack={back} />}
    </>
  );
}

Each step receives the same state object and calls onChange. Going back loses nothing because the parent owns the data. Simple, no library needed.

Option B — RHF + one form instance across steps

rhf-wizard.jsx
const methods = useForm({ mode: 'onTouched' });
const [step, setStep] = useState(1);

const next = async () => {
  // validate only the fields on this step
  const ok = await methods.trigger(
    step === 1 ? ['name', 'email'] : ['city', 'pin']
  );
  if (ok) setStep(s => s + 1);
};

trigger(names) validates only the named fields — perfect for "validate this step, then advance". All fields stay in one form instance, so the final submit has the full payload.

Interview questions

forms specifically

Q1What is a controlled vs uncontrolled component?

Controlled: React state drives the input via value + onChange — the source of truth is React. Uncontrolled: the DOM holds the value; you read it via a ref when needed (typically on submit). Controlled is better for validation and conditional UI; uncontrolled is faster for large forms and required for file inputs.

Q2Why does typing in a controlled form cause the whole component to re-render?

Because state lives in the component. Every keystroke calls setState → the component re-renders → all its JSX (including every input) is reconciled. For a 3-input form this is negligible. For a 30-input form it starts to matter — that's the motivation for react-hook-form, which stores values in refs.

Q3How does the single handleChange pattern work?

All inputs share one handleChange. Each input has a name attribute that matches a key in the state object. The handler reads e.target.name and writes setForm(f => ({ ...f, [name]: value })). The computed key picks the right property. Adding a field is: add the key to initial state, add the input with the matching name. No new handler, no new setter.

Q4Why is a file input always uncontrolled?

Browsers forbid setting input.value for file inputs from JavaScript — for security, a script can't fabricate a file that the user didn't choose. So you use a ref and read ref.current.files, then package the file in a FormData object before sending.

Q5How does react-hook-form avoid re-renders on every keystroke?

register(name) returns a ref that RHF attaches to the DOM input. RHF reads the value from the DOM node when it needs it — on blur, on change of a field that has validation, on submit — instead of storing it in React state. So typing updates the DOM directly and RHF doesn't trigger a render. It re-renders only when you watch a field, or when an error appears.

Q6What does handleSubmit from react-hook-form do?

It returns an onSubmit handler for the form. When the user submits, it runs every registered field's validators. If any fail, it populates formState.errors and does NOT call your handler. If all pass, it calls your handler with the whole form data as an object. It also manages isSubmitting.

Q7How would you reset a form after submit?

Pattern 1: call each setter with its initial value. Pattern 2/3: setForm(initialValues). Pattern 5: assign ref.current.value = '' per field (painful). RHF: reset(). The shared idea: a single source of truth for "initial state", so reset is one operation.

Q8How do you handle validation in a large form?

Define the rules as a schema (Yup or Zod) and pass it to useForm({ resolver }). All validation logic lives in the schema, errors come out in formState.errors, and the same schema can be reused on the server for request validation. For one-off rules (like "confirm password must match"), use the validate option on that field with access to the rest of the form.

Q9How do you do cross-field validation?

In react-hook-form: use the validate option on a field, and inside it call getValues() to check against other fields. Or use .refine() / .superRefine() on the schema to express the rule at the schema level. Manually: run the check in the submit handler after reading all fields.

Q10How do you prevent double submits?

Track a submitting boolean in state, set it true at the start of submit, and disable the submit button while it's true. Guard the handler with if (submitting) return; for keyboard-triggered submits. RHF exposes isSubmitting for the same purpose.

Q11How do you display server-side validation errors (e.g. "email already in use")?

In RHF, use setError('email', { message: err.response.data.message }) — that error goes into formState.errors exactly like a client-side one. In manual patterns, keep a separate serverError state and render it above or below the form; you can also merge it into the field-level errors object if you want a unified display.

Q12How do you handle dynamic fields (add/remove rows)?

In RHF, use useFieldArray — append, remove, insert, move, prepend are provided. Field names use array index in dot notation: addresses.0.line1, addresses.1.line1. Use field.id as the React key. Manually: keep an array in state, map it, give each row a stable id, and pass the id to a per-row handler.

Q13How would you build a multi-step form?

Keep the data in one place (parent state or one RHF instance) and use a step counter to decide which step to render. Advancing validates only the current step's fields — RHF's trigger(fieldNames) is built for this. Going back is safe because the data hasn't been unmounted, just visually hidden (or the state was lifted).

Q14When would you choose react-hook-form over manual patterns?

As soon as you need any of: per-field errors, submit lifecycle (isSubmitting, isValid, isDirty), array fields, schema validation, or form sizes above ~10 fields. For a 2-field login form, manual state is simpler. For a signup / checkout / profile-edit form, RHF saves hundreds of lines and gives a better UX.

Q15Why is {...register('email')} a spread and not value={email}?

register('email') returns { name, onChange, onBlur, ref } — not a value. The input stays uncontrolled. Spreading gives the input everything RHF needs to track it. If you want a controlled field (e.g. to mask input as they type), use Controller or useController to wrap a controlled component.
