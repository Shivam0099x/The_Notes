01

Why TanStack Query exists

client state vs server state · the problem it solves

React has tools for managing client state — modal toggles, form drafts, tab indices. But most of the state in a real app is server state: data you don't own, that lives in your Express + MongoDB backend, that can change without you, and that you only have a cached copy of. React has no built-in answer for that. TanStack Query (formerly React Query) is that answer.

Client stateServer state
ExamplesModal open, dark mode, form inputUsers list, product catalogue, cart items from DB
Who owns itThe frontendThe backend — you only mirror it
Can it change without you?NoYes — another user could edit it right now
Is your copy fresh?AlwaysNo — it may be stale the second you receive it
Best tooluseState, Context, ZustandTanStack Query, Redux Toolkit Query, SWR

What people did before TanStack Query

Hand-rolled useEffect + useState for every API call:

the old pain
useEffect(() => {
  let ignore = false;
  fetch('/api/users')
    .then(r => r.json())
    .then(data => { if (!ignore) setUsers(data); })
    .catch(e => setError(e));
  return () => { ignore = true; };
}, []);

Then, once it works, you realise you also want: loading state, error state, retry on failure, refetch on window focus, a cache so navigating back doesn't reload, deduplication when two components ask for the same data, cancellation on unmount, and a way to invalidate after a mutation. Each of those is another bug waiting to happen. TanStack Query gives you all of them out of the box.

The mental model

TanStack Query is a cache manager, not a data fetcher. It doesn't know or care how you fetch — fetch, axios, GraphQL, GraphQL, your own wrapper. It takes the promise your function returns, caches the result under a query key, and manages everything about the lifecycle of that cached value: freshness, refetching, invalidation, garbage collection.

Quick check · 01
Which of these is "server state" that TanStack Query should own?
Server state is data you don't own — the backend does. It can change without you, may be stale the second you receive it, and needs caching, refetching, and invalidation. Drawer state belongs in useState.

Installation & setup

packages · QueryClient · QueryClientProvider

terminal
npm install @tanstack/react-query
# optional, but you'll want it in production:
npm install @tanstack/react-query-devtools

Create a QueryClient and wrap the app

src/main.jsx
import React from 'react';
import ReactDOM from 'react-dom/client';
import { QueryClient, QueryClientProvider } from '@tanstack/react-query';
import { ReactQueryDevtools } from '@tanstack/react-query-devtools';
import App from './App';

const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 60 * 1000,              // fresh for 1 minute
      refetchOnWindowFocus: false,
    },
  },
});

ReactDOM.createRoot(document.getElementById('root')).render(
  <QueryClientProvider client={queryClient}>
    <App />
    <ReactQueryDevtools initialIsOpen={false} />
  </QueryClientProvider>
);
💡
TanStack Query does not fetch for you. It calls the async function you provide. That function usually wraps fetch, axios, or your own typed API client — the choice is yours, and the rest of TanStack Query is the same.
Quick check · 02
What is a QueryClient responsible for?
The QueryClient owns the cache and default options. It never makes requests itself — that's the query function's job. QueryClientProvider puts the client into React context so hooks can find it.
03

useQuery — the core hook

queryKey · queryFn · what it returns

Every data-fetching concern in TanStack Query centres on one hook. Two things it must have:

OptionWhat it does
queryKeyAn array that uniquely identifies this piece of data in the cache. ['users'], ['user', 42], ['posts', { tag: 'react' }]. Used for caching, refetching, and invalidation.
queryFnThe async function that fetches the data. Must return a promise. Whatever it resolves with is what data becomes.
UsersList.jsx
import { useQuery } from '@tanstack/react-query';

async function fetchUsers() {
  const res = await fetch('/api/users');
  if (!res.ok) throw new Error('Failed to fetch users');
  return res.json();
}

export default function UsersList() {
  const { data, isLoading, isError, error, refetch } = useQuery({
    queryKey: ['users'],
    queryFn: fetchUsers,
  });

  if (isLoading) return <p>Loading…</p>;
  if (isError)   return <p>Error: {error.message}</p>;

  return <ul>{data.map(u => <li key={u._id}>{u.name}</li>)}</ul>;
}

The flags you actually use

ValueMeaning
dataThe cached value, or undefined if the first fetch hasn't resolved.
errorThe thrown error, or null.
isLoadingtrue only on the first fetch when there's no data yet. Show a full-page spinner with this.
isFetchingtrue whenever a fetch is in flight, including background refetches. Show a subtle "refreshing…" indicator with this.
isErrortrue if the last fetch failed.
isSuccesstrue if the last fetch succeeded.
isStaletrue if the data is past its staleTime. May refetch on next trigger.
refetchManual trigger, returns a promise.
⚠️
isLoading vs isFetching. Use isLoading for the "no data at all yet" spinner, and isFetching for the "refreshing in the background" indicator. If you show a full-page spinner on isFetching, the UI flickers on every window focus.

Passing arguments — the queryKey is the argument

To fetch one user by ID, put the ID inside the key. That way each user gets its own cache slot, and fetching user 42 doesn't overwrite user 7:

useUser(id)
export default function UserProfile({ id }) {
  const { data, isLoading } = useQuery({
    queryKey: ['user', id],          // id is part of the cache key
    queryFn: async () => {
      const res = await fetch(`/api/users/${id}`);
      if (!res.ok) throw new Error('User not found');
      return res.json();
    },
  });

  if (isLoading) return <p>Loading…</p>;
  return <h2>{data.name}</h2>;
}
💡
Query keys are hierarchical. ['users'] and ['users', 42] are separate caches, but invalidating ['users'] also invalidates every key that starts with it. This is how you invalidate "all users" in one line.
Quick check · 03
A component shows a full-page spinner. Which flag should it use?
isLoading = no data + fetching = first load. isFetching is also true during background refetches when data already exists — using it for a full-page spinner causes annoying flicker.
Quick check · 04
Component A calls useQuery({ queryKey: ['users'], queryFn }). Component B renders at the same time with the same key. What happens?
Same key = same cache entry. TanStack Query de-duplicates in-flight requests for identical keys — one network hit, both components update. This alone is worth adopting the library for.
04

Caching: staleTime and gcTime

fresh vs stale vs inactive vs garbage-collected

This is the single most misunderstood part of TanStack Query, and the part you'll be asked about in every interview. Two timers control every cached value:

OptionDefaultWhat it means
staleTime0 msHow long the data is considered fresh. While fresh, TanStack Query will not refetch on window focus, mount, or reconnect. After staleTime passes, data is stale — eligible for background refetch, but still served from cache.
gcTime5 minHow long unused data stays in memory before garbage collection. Timer only starts when the last subscriber unmounts. Formerly called cacheTime.
The one-line difference

staleTime = "when should I re-fetch?"
gcTime = "when should I delete it from memory?"

Data can be stale for hours and still cached — that just means the next component to mount will get the old data instantly, then a fresh request fires in the background to update it.

—
  1. A component mounts and calls useQuery. The cache has no entry for the key, so TanStack Query fires the query function. The entry is now fetching.
  2. The fetch resolves. Data is stored under the key, subscribers are notified, and the component re-renders with data. The entry becomes fresh.
  3. staleTime starts counting. While fresh, if the same component mounts again or the window refocuses, nothing refetches — TanStack Query just returns the cached data. This is the "instant navigation" magic.
  4. staleTime elapses. The entry is now stale. It is still in the cache — components still get it instantly — but the next trigger (mount, focus, reconnect) will fire a background refetch, and when it resolves, subscribers update smoothly without a spinner.
  5. The last component using this key unmounts. The entry is now inactive. gcTime starts counting. If the same query mounts before gcTime elapses, the timer is cancelled and the cache is reused.
  6. gcTime elapses with no subscribers. The entry is garbage-collected — freed from memory. A future mount starts cold again.
Step 1 / 6

Choosing values

Data typestaleTimeWhy
Real-time (chat, presence)0Any delay shows stale info. Combine with WebSockets for real updates.
Feeds, dashboards30s – 1 minFresh enough; avoids thrashing the server on every tab switch.
User profile, settings5 – 10 minRarely changes; refetching often is pure waste.
Static reference data (countries, categories)InfinityNever changes during the session. Manual invalidation after mutation.
Quick check · 05
staleTime: 5 * 60 * 1000, gcTime: 10 * 60 * 1000. A component fetches at t=0, then unmounts at t=6 minutes. What happens at t=8 minutes if no other component has mounted?
gcTime only starts when the last subscriber unmounts — not when the data becomes stale. From unmount at t=6, ten minutes of gcTime means garbage collection at t=16.
Quick check · 06
You set staleTime: 0 (the default). Does that mean data is deleted immediately?
Stale ≠ deleted. staleTime: 0 means "refetch aggressively", but the cache entry lives until gcTime expires after the last unmount — usually 5 minutes. Components still get instant data from cache; they just also get a background refetch.
05

useMutation — writing to the server

mutate · callbacks · onSuccess · onError · onSettled

Queries are for reading server data. Mutations are for changing it — POST, PUT, PATCH, DELETE. They look similar but behave differently: mutations don't run automatically, they don't cache the response (unless you tell them to), and they don't refetch anything on their own. They just execute when you call them and give you a clean set of callbacks.

AddUser.jsx
import { useMutation, useQueryClient } from '@tanstack/react-query';

async function createUser(newUser) {
  const res = await fetch('/api/users', {
    method: 'POST',
    headers: { 'Content-Type': 'application/json' },
    body: JSON.stringify(newUser),
  });
  if (!res.ok) throw new Error('Failed to create user');
  return res.json();
}

export default function AddUser() {
  const queryClient = useQueryClient();

  const mutation = useMutation({
    mutationFn: createUser,
    onSuccess: () => {
      // the users list is now out of date — invalidate it
      queryClient.invalidateQueries({ queryKey: ['users'] });
    },
    onError: (err) => {
      alert('Create failed: ' + err.message);
    },
  });

  return (
    <button
      disabled={mutation.isPending}
      onClick={() => mutation.mutate({ name: 'Aarav', age: 22 })}
    >
      {mutation.isPending ? 'Saving…' : 'Add user'}
    </button>
  );
}

What useMutation returns

ValueMeaning
mutate(vars)Fire and forget. Errors don't propagate to your component's try/catch.
mutateAsync(vars)Returns a promise; errors do throw, so try/catch works.
isPendingtrue while the mutation is running — disable the submit button with this.
isSuccess / isErrorResult of the last run.
dataWhat the mutation function resolved with — usually the server's response.
errorThe thrown error if it failed.
reset()Clear the mutation's state — handy after showing a success message.

mutate vs mutateAsync

⚠️
Prefer mutate unless you need to await. mutate routes errors to your onError callback. mutateAsync throws on the returned promise — if you forget to catch, you get an unhandled rejection. Use mutateAsync only when you must wait before doing something next (e.g. navigating after success).
Quick check · 07
You just ran a POST /api/users mutation successfully. What does TanStack Query do by default to the cached ['users'] query?
Mutations are not automatically reflected in query caches. That would be magical but also often unnecessary (a mutation might not affect anything). You invalidate manually in onSuccess — that's what invalidateQueries is for.
06

Invalidation — how data stays fresh after writes

invalidateQueries · hierarchical keys · setQueryData

After a mutation, the cached copies of the affected queries are out of date. invalidateQueries tells TanStack Query "this data is now stale — refetch it". If the affected queries are currently mounted, they refetch immediately. If not, they're marked stale and will refetch the next time a component mounts.

three flavours of invalidation
// 1. Invalidate everything under 'users' — including ['users', 42], ['users', 7], etc.
queryClient.invalidateQueries({ queryKey: ['users'] });

// 2. Invalidate only one specific user
queryClient.invalidateQueries({ queryKey: ['users', userId] });

// 3. Invalidate and force the refetch even if unmounted
queryClient.invalidateQueries({
  queryKey: ['users'],
  refetchType: 'all',
});
The prefix rule

Invalidating ['users'] invalidates every key that starts with ['users']. So if your keys are ['users', list], ['users', 42], ['users', 43], one call cleans them all. This is why the query key must be structured — it's not a string, it's a path.

Alternative: set the cache directly

Sometimes you already know what changed — you created a user, and the server returned the new user object. Instead of refetching (extra network hit), push it into the cache:

setQueryData
onSuccess: (newUser) => {
  queryClient.setQueryData(['users'], (old = []) => [...old, newUser]);
  // no refetch — the cache is now correct
}
When to invalidate vs setQueryDataUse
Server transformed the data, or computed fields you can't replicateinvalidateQueries — refetch to get the truth
Simple append / update / delete, and the mutation returns the changed objectsetQueryData — cheaper, no extra request
Broad change affecting many keysinvalidateQueries on the parent prefix
Quick check · 08
Your keys are ['posts'], ['posts', 1], ['posts', 2]. You run invalidateQueries({ queryKey: ['posts'] }). What gets invalidated?
Query keys are hierarchical. Invalidating a key invalidates every key that starts with it. So one invalidateQueries call cleans all posts, individual posts, and any nested variations.
07

Optimistic updates

update cache instantly · rollback on error

An optimistic update means: assume the server will succeed, update the UI immediately, and if the server actually rejects, roll the UI back. It makes apps feel instant — likes, todos, comments, carts. The cost is a little more code, and it's worth understanding properly because it's a classic interview question.

The pattern has three steps: cancel any in-flight refetches (so they don't overwrite your optimistic data), snapshot the current cache (so you can restore it), and update the cache optimistically. If the mutation fails, restore the snapshot.

useAddTodo.js
import { useMutation, useQueryClient } from '@tanstack/react-query';

export function useAddTodo() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: async (newTodo) => {
      const res = await fetch('/api/todos', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(newTodo),
      });
      if (!res.ok) throw new Error('Failed to add todo');
      return res.json();
    },

    // STEP 1 — cancel any in-flight refetches of the same query
    onMutate: async (newTodo) => {
      await queryClient.cancelQueries({ queryKey: ['todos'] });

      // STEP 2 — snapshot the old cache so we can restore on error
      const previousTodos = queryClient.getQueryData(['todos']);

      // STEP 3 — optimistically add the todo with a temporary id
      queryClient.setQueryData(['todos'], (old = []) => [
        ...old,
        { ...newTodo, _id: 'temp-' + Date.now(), pending: true },
      ]);

      // return context for use in onError
      return { previousTodos };
    },

    // On failure — restore the snapshot
    onError: (err, newTodo, context) => {
      if (context?.previousTodos) {
        queryClient.setQueryData(['todos'], context.previousTodos);
      }
      alert(err.message);
    },

    // Whether success or failure, refetch to sync with the server
    onSettled: () => {
      queryClient.invalidateQueries({ queryKey: ['todos'] });
    },
  });
}
Why cancelQueries first?

If a background refetch of ['todos'] was already in flight when the mutation started, it will resolve after your optimistic update and overwrite it with the stale server data. cancelQueries stops that refetch before it does damage.

CallbackWhen it runsWhat you do there
onMutateBefore the mutation function runsCancel refetches, snapshot the cache, apply the optimistic change, return context
onErrorIf the mutation throwsRestore the snapshot from context
onSuccessIf it succeedsOptionally replace the temp ID with the server's real ID
onSettledAfter either outcomeInvalidate to make sure the cache matches the server
Quick check · 09
You implement an optimistic update but forget cancelQueries. What could go wrong?
It's a classic race: an old refetch that started before the mutation finishes after it, clobbering your optimistic change. cancelQueries is the fix.
Quick check · 10
Where do you get the context passed to onError and onSettled?
That's the whole point of returning { previousTodos } from onMutate. It's the mutation's own per-call scratchpad.
08

Advanced patterns you'll use in production

pagination · infinite queries · dependent queries · enabled

Dependent queries — wait for a value before fetching

If you can't fetch until you have an ID from somewhere else, use enabled. This is how you avoid fetching /api/users/undefined:

dependent query
const { data: user } = useQuery({ queryKey: ['me'], queryFn: fetchMe });

const { data: posts } = useQuery({
  queryKey: ['posts', user?.id],
  queryFn: () => fetchUserPosts(user.id),
  enabled: !!user?.id,                 // don't run until user exists
});

Pagination with keepPreviousData

Naive pagination flashes empty on every page change. placeholderData: keepPreviousData keeps the previous page visible while the next one loads:

paginated query
import { keepPreviousData, useQuery } from '@tanstack/react-query';

export function UsersPage({ page }) {
  const { data, isPlaceholderData } = useQuery({
    queryKey: ['users', { page }],
    queryFn: () => fetch(`/api/users?page=${page}`).then(r => r.json()),
    placeholderData: keepPreviousData,   // show previous page while loading next
  });

  return (
    <div style={{ opacity: isPlaceholderData ? 0.5 : 1 }}>
      {/* render data.users */}
    </div>
  );
}

Infinite queries for feeds

useInfiniteQuery
import { useInfiniteQuery } from '@tanstack/react-query';

const { data, fetchNextPage, hasNextPage, isFetchingNextPage } = useInfiniteQuery({
  queryKey: ['feed'],
  queryFn: ({ pageParam = 0 }) =>
    fetch(`/api/posts?cursor=${pageParam}`).then(r => r.json()),
  initialPageParam: 0,
  getNextPageParam: (lastPage) => lastPage.nextCursor ?? undefined,
});
Quick check · 11
Your second query depends on an ID from the first. The first hasn't resolved yet. What stops the second from firing with an undefined ID?
enabled is the built-in dependent-query pattern. Until enabled: true, the query sits idle and doesn't fetch.

How it fits a MERN app

server state vs client state · one source of truth · structure

In a MERN stack, your Express API is the source of truth. TanStack Query is the mirror that lives in the browser and keeps that mirror up to date. That means:

StateLives inManaged by
User list, product catalogue, ordersServer → browser cacheTanStack Query
Current user (from /api/auth/me)Server → browser cacheTanStack Query
Auth tokenlocalStorage / cookieYour auth layer
Modal open/closed, tab indexComponentuseState
Multi-step form draft (not yet submitted)Component or Zustand/ReduxClient state store
The most important MERN rule

Don't copy TanStack Query data into Redux or Zustand "so it's all in one place". That's the #1 way to get two sources of truth that drift. Keep server data in TanStack Query's cache, and use the client store only for state the server doesn't know about.

A wrapper so your components never call fetch directly

src/api/client.js
const BASE = '/api';

async function request(path, options = {}) {
  const res = await fetch(BASE + path, {
    ...options,
    headers: {
      'Content-Type': 'application/json',
      ...(options.headers || {}),
      Authorization: 'Bearer ' + (localStorage.getItem('token') || ''),
    },
  });
  if (!res.ok) {
    const body = await res.json().catch(() => ({}));
    throw new Error(body.message || `Request failed: ${res.status}`);
  }
  return res.json();
}

export const api = {
  getUsers:  () => request('/users'),
  getUser:   (id) => request(`/users/${id}`),
  createUser: (body) => request('/users', { method: 'POST', body: JSON.stringify(body) }),
  updateUser: (id, body) => request(`/users/${id}`, { method: 'PUT', body: JSON.stringify(body) }),
  deleteUser: (id) => request(`/users/${id}`, { method: 'DELETE' }),
};

Then hooks become trivial

src/hooks/useUsers.js
import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { api } from '../api/client';

export function useUsers() {
  return useQuery({ queryKey: ['users'], queryFn: api.getUsers });
}

export function useCreateUser() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: api.createUser,
    onSuccess: () => qc.invalidateQueries({ queryKey: ['users'] }),
  });
}

export function useDeleteUser() {
  const qc = useQueryClient();
  return useMutation({
    mutationFn: api.deleteUser,
    onSuccess: () => qc.invalidateQueries({ queryKey: ['users'] }),
  });
}

You're migrating a MERN app from Redux (thunks storing server data) to TanStack Query. What should happen to the server-data slices in Redux?
Keeping both copies is the classic mistake that leads to drift. Migrate server data to TanStack Query fully; keep Redux only for state the server doesn't know about — or drop Redux entirely if nothing else uses it.

Pitfalls that bite in real projects

common mistakes · what to do instead

PitfallWhat happensFix
Wrong query key structureTwo components asking for the same data create separate caches; invalidation misses oneStandardise on a hierarchical key scheme: [entity], [entity, id], [entity, filters]
Passing objects that change every render into the keyCache is never reused; infinite refetchesKey must be stable. Pass the values, not the object.
Using isFetching for the main spinnerUI flickers on every background refetchUse isLoading (first load only) for full-page; isFetching for subtle indicators
Refetching everything after every mutationNetwork traffic explodes; components flickerinvalidateQueries only the affected keys — or setQueryData for simple cases
Copying query data into useState / ReduxTwo sources of truth that driftRead from useQuery directly; derive with useMemo, not useState
Optimistic update without cancelQueriesIn-flight refetch overwrites your optimistic writeAlways cancel first
QueryFn that closes over props directlyStale values, missed refetchesPut the value in the query key — TanStack Query calls your fn with the key's current values
Assuming errors are gone with isError onlySilent failures in productionAlso log errors in a global onError on QueryClient defaults
⚠️
The queryKey stability trap. queryKey: ['users', { page }] is stable — same object shape, same page value, deep-equal. But queryKey: ['users', filters] where filters is a new object every render is still fine, because TanStack Query deep-compares keys. What breaks is passing unstable values inside — like queryKey: ['users', { on: Date.now() }]. Keep keys made of primitives and plain objects and you'll never hit this.
11

Interview questions

what you'll actually be asked

Q1What problem does TanStack Query solve?

It manages server state — data you don't own, that changes without you, and is often stale. It gives you caching, background refetching, deduplication, loading/error states, pagination, and invalidation in one tool. Without it, every API call becomes a bespoke useEffect + useState + cancellation dance, and every app reinvents the same cache badly.

Q2What is a query key and why is it an array?

The unique identifier for a piece of cached data. Arrays are used because they're hierarchical: ['users'] is a prefix of ['users', 42], so invalidating ['users'] invalidates all users and each individual user. Array items can be strings, numbers, plain objects — TanStack Query deep-compares them.

Q3Explain staleTime vs gcTime.

staleTime is how long data is considered fresh and won't refetch on triggers like mount or window focus. gcTime is how long unused data stays in memory after the last component unmounts. They're independent: data can be stale for an hour but still cached. Default staleTime is 0 (refetch aggressively); default gcTime is 5 minutes.

Q4What's the difference between isLoading and isFetching?

isLoading is true only when there's no cached data and the first fetch is in flight — the "I have nothing to show" case. isFetching is true whenever a fetch is running, including background refetches when data is already shown. Use isLoading for full-page spinners, isFetching for subtle "refreshing…" indicators.

Q5How do you keep a query fresh after a mutation?

In onSuccess of the mutation, call queryClient.invalidateQueries({ queryKey: [...] }) for the affected keys. If the affected queries are mounted, they refetch immediately; if not, they're marked stale and refetch on next mount. For simple cases where the mutation returns the changed object, use setQueryData to update the cache directly and skip the refetch.

Q6How would you implement an optimistic update?

In onMutate: cancelQueries to stop in-flight refetches, getQueryData to snapshot the old cache, setQueryData to apply the optimistic change, and return { previous }. In onError: restore from the returned context. Optionally onSettled: invalidate to reconcile with the server. That's the standard three-step pattern.

Q7What is a dependent query and how do you implement one?

A query that needs a value from another query before it can run — e.g. fetching /api/users/:id/posts requires knowing the user ID. Implement it with enabled: !!id so the second query doesn't fire until the first has populated the value.

Q8What is the difference between useMutation.mutate and mutateAsync?

mutate is fire-and-forget — errors go to the onError callback, and no promise is returned for you to await. mutateAsync returns a promise that rejects on error, so you can try/catch it — but if you forget to catch, you get an unhandled rejection. Prefer mutate; use mutateAsync only when you must wait.

Q9How does TanStack Query prevent duplicate requests?

If two components mount with the same queryKey and a fetch is already in flight, both subscribe to the same cache entry — the second does not fire another request. Same with rapid refetches: while one is running, further triggers are coalesced. This is one of the biggest benefits over hand-rolled useEffect fetching.

Q10Would you use TanStack Query instead of Redux, or alongside it?

TanStack Query replaces the server-state half of Redux. Most apps don't need a client state store at all after migrating to TanStack Query — auth user, lists, forms-that-are-submitted, everything comes from cache. If you still have complex client-only state (multi-step form drafts, UI flows shared across pages), Zustand or Redux Toolkit is fine alongside TanStack Query. What you don't do is copy server data into Redux "for consistency".

Q11What happens if a query function throws?

TanStack Query catches the error, sets isError: true, stores the error, and by default retries up to 3 times with exponential backoff before giving up. Configure with retry and retryDelay on the query or globally. Mutations don't retry by default.

Q12How does TanStack Query integrate with SSR (e.g. Next.js)?

You create a QueryClient per request on the server, prefetch the required queries with prefetchQuery, dehydrate the cache state, pass it to the client, and hydrate on mount. This gives instant first paint with cached data and no waterfall on hydration. The package @tanstack/react-query ships HydrationBoundary and dehydrate/hydrate helpers for exactly this.
